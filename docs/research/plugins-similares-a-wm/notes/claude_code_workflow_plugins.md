## 1. Who maintains each plugin, what is its latest version and date, and how widely is it adopted (stars, forks, installs, release cadence)?

### Takeaway
Adoption in Oct 2026 is concentrated in markdown-only, instruction-driven libraries: Superpowers (296k stars; 1.15M unique installs in Anthropic's official marketplace), mattpocock/skills (278k) and ECC (274k) lead, while Compound Engineering (25k), wshobson/agents (40k), SuperClaude (24k, no release for 6+ months) and claude-flow/Ruflo (74k, contested claims) trail. Anthropic's own workflow plugins (feature-dev, code-review, hookify, ralph-loop, etc.) have 66k-492k unique installs but little recent maintenance in the marketplace repo (except security-guidance).

### Inferences
- Stars are a poor proxy for effective use: the 4th-ranked "plugin" is one CLAUDE.md file, and a third-party audit found it barely beats no instructions (see Q9). Anthropic's unique-install file (2026-10-02) is the only first-party usage metric, and it covers only the official marketplace; CE, wshobson, SuperClaude and Ruflo cannot be compared on it.
- Release cadence splits the field: Ruflo and CE ship weekly or daily (CE ~15 releases/month), Superpowers every 2-4 weeks, SuperClaude has stalled, wshobson has no tagged releases at all. A wm that wants trust should tag releases and keep `version` bumped (see Q10 for why).
- Superpowers is both the adoption leader and part of Anthropic's own marketplace, which makes it the de facto baseline wm will be compared with. wm cannot assume the official marketplace as a channel (the documented submission path for ordinary authors is unclear and third-party entries are pinned by SHA, so updates lag).

### Gaps
- No Claude Code install counts for CE, wshobson/agents, SuperClaude or Ruflo (they are not in the official install file); npm/PyPI numbers cover installers or converters, not Claude Code plugin installs.
- Star/fork counts could not be audited for inflation; contributor counts are first-page API values only.
- Reddit could not be queried directly (only third-party archives surfaced), so adoption sentiment from r/ClaudeAI and r/ClaudeCode is sampled, not systematic.

## 2. What does each contain (skills, agents, commands, hooks, MCP servers), how big is it, and what does it cost in always-on context tokens?

### Takeaway
Contents range from 15 skills and one SessionStart hook (Superpowers, ~840 always-on tokens measured) to ECC's 387 skills + 68 agents (~44.8k tokens if installed whole); CE is ~3.0k, the whole wshobson catalog would be ~43.8k (but ~480 per single-purpose plugin), and Anthropic's first-party plugins are 0-2.4k. Hook-injected context (Superpowers' and wm's SessionStart payload) is NOT counted by Anthropic's `claude plugin details` figure.

### Cited Findings

#### How Anthropic counts and limits context cost (platform facts)
- [PRIMARY] Every session with a plugin enabled carries the names and descriptions (plus `when_to_use`) of its skills, agents and commands; `claude plugin details <name>` prints "Always-on" and per-component "on-invoke" estimates; hooks are labelled "harness-only, no model context cost" and MCP tool schemas are "not counted". — [Measure plugin cost](https://code.claude.com/docs/en/plugins/measure)
- [PRIMARY] In `/plugin` the official marketplace shows a "Context cost" section before install, highlighted when "Every turn" is 2,000 tokens or more. — [Measure plugin cost](https://code.claude.com/docs/en/plugins/measure)
- [PRIMARY] Skill listing: `description` + `when_to_use` are truncated at 1,536 characters per skill (`skillListingMaxDescChars`); the listing always contains every skill name but drops descriptions, least-invoked skills first, to fit a budget of 1% of the model's context window (`skillListingBudgetFraction` / `SLASH_COMMAND_TOOL_CHAR_BUDGET`; `/doctor` estimates listing cost; `skillOverrides` can set low-priority skills to "name-only"; `/skill-doctor` flags skills that never run); an invoked skill's body stays in context for later turns; after auto-compaction each invoked skill keeps its first 5,000 tokens within a shared 25,000-token budget; `disable-model-invocation: true` removes a skill from Claude's context. — [Skills docs](https://code.claude.com/docs/en/skills)
- [PRIMARY] Combined custom-subagent descriptions should stay under 15,000 tokens (startup warning above that). — [Subagents docs](https://code.claude.com/docs/en/sub-agents) (page summary)

## 3. What orchestration pattern does each use, and how does it pass context between agents?

### Takeaway
Three families: (a) controller + fresh subagent per task + review gates (Superpowers SDD, GSD Core, CE `ce-work`/`ce-code-review`, Anthropic feature-dev), (b) role/persona or catalog routing (gstack, wshobson, SuperClaude, OMC), (c) loops and swarms (Anthropic ralph-loop, Ruflo). The newest and best-evidenced designs hand context over as files (task brief, report, diff package, ledger) rather than pasted text.

### Cited Findings

#### Superpowers: skill chain, then fresh implementer per task
- [PRIMARY] Triage in `brainstorming`: classify as Spike, Bounded or Architectural, say the classification out loud so the user can override, "when in doubt take the heavier path", and the ratchet is one-way ("Nothing downgrades mid-task"); a HARD-GATE forbids any implementation action until the path's approvals exist (approval of an idea does not approve a spec or plan not yet shown). Architectural path: questions, 2-3 approaches, design in sections, spec to `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`, spec self-review (placeholders, consistency, scope, ambiguity), user review, then `writing-plans`. — [brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)
- [PRIMARY] `writing-plans` (v6.4.2): plan header with Goal, Architecture, Tech Stack, Spec pointer, Global Constraints (verbatim spec values) and Review Focus (up to five inputs or failure modes the spec implies but no task's tests exercise, each pinned by a test); tasks list Files, Interfaces (Consumes/Produces exact signatures) and one-action steps; "A plan records decisions. It's not a transcript of the code"; self-review compares plan length to spec length. — [writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md), [v6.4.2 notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- [PRIMARY] `subagent-driven-development` (SDD): a fresh implementer subagent per task, one task reviewer per task returning a spec verdict and a quality verdict, a fix loop of at most five rounds (rounds 1-3 resume the same implementer; rounds 4-5 a fresh implementer on a more capable model; scoped re-review each round), a circuit breaker where the controller adjudicates and records "Ruling:" lines, one broad whole-branch review on the most capable model, then `finishing-a-development-branch`. "Never dispatch multiple implementation subagents in parallel (conflicts)"; implementers and reviewers may not spawn subagents. — [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- [PRIMARY] Implementer statuses are DONE, DONE_WITH_CONCERNS, NEEDS_CONTEXT, BLOCKED ("It is always OK to stop and say 'this is too hard for me.' Bad work is worse than no work"); the report goes to a file and only a ≤15-line status contract returns (status, commits, one-line test summary, concerns); TDD evidence (RED and GREEN command output) is part of the report. — [implementer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/implementer-prompt.md)
- [PRIMARY] Context handoff is by files: `scripts/task-brief PLAN N` writes the task text to a file; `scripts/review-package PLAN BASE HEAD` writes commit list + stat + diff to a file and rejects empty or non-descendant ranges (exit 3); `scripts/sdd-workspace` resolves a plan-scoped, git-ignored dir `.superpowers/sdd/<plan>/` holding `progress.md` (the ledger that survives compaction; "Controllers that lost their place have re-dispatched entire completed task sequences — the single most expensive failure observed"). Scratch moved out of `.git/` in v6.0.3 because Claude Code treats `.git/` as protected. — [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- [PRIMARY] Reviewer rules: read-only on the checkout, "Do Not Trust the Report" (treat the implementer's report as unverified claims; stated rationales never downgrade a finding), noisy test output is itself a finding, "Cannot verify from diff" and "Declined to judge" lists go back to the controller; the controller may not tell a reviewer what to ignore or pre-rate severity ("do not flag", "at most Minor" are banned). — [task-reviewer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md), [v6.0.0 notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- [CLAIM] v6.0.0: one reviewer per task instead of two, diffs/tasks as files instead of pasted text, mandatory model on every dispatch; "Claude Code and Codex produce similar high-quality results roughly twice as fast and while spending almost 50% fewer tokens". v6.4.1 adds Native execution (`executing-plans` runs the whole plan inline then one final review; "cheapest way to run a plan") and an opt-in nested controller on a mid-tier model ("about half the cost and wall clock"). — [RELEASE-NOTES.md](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)
- [PRIMARY] SDD has "Rulings, not stalls": plan conflicts and ambiguities get a recorded ruling and execution continues; only irreversible/destructive actions, security-sensitive actions, side effects outside the worktree (merge, push, publish) and a plan "so broken that every path forward is a guess" stop the run; all rulings are listed in the final message ("Rulings I made"). — [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)

#### Compound Engineering: brainstorm, plan, work, simplify, review, compound
- [PRIMARY] Core loop of six skills (`ce-brainstorm`, `ce-plan`, `ce-work`, `ce-simplify-code`, `ce-code-review`, `ce-compound`); `lfg` runs it hands-off, including commit, push, PR and a bounded CI-repair loop (3 fix rounds) but does not merge unless granted. Philosophy: "80% is in planning and review, 20% is in execution". — [README](https://github.com/EveryInc/compound-engineering-plugin/blob/main/README.md)
- [CLAIM] Every's article (Dec 2025): loop = plan, work, assess, compound; "roughly 80 percent of compound engineering is in the plan and review parts"; "a single developer can do the work of five developers a few years ago"; Every runs five products each "primarily built and run by a single person". — [Every](https://every.to/chain-of-thought/compound-engineering-how-every-codes-with-agents) (page summary)
- [PRIMARY] `ce-work` default engine: run each dependency layer's independent units "as a parallel wave of fresh workers" (cap ~3-5), after a Parallel Safety Check (dependencies, declared and hidden files, shared types/migrations/lockfiles, environment singletons, merge cost), in isolated worktrees (with an expected base SHA verified by the worker) or a shared workspace under a "wave contract"; workers get a bounded unit packet (never "read the whole plan"), report changed paths plus verification evidence, make no canonical commits and run no git index writes; the orchestrator inspects the real tree, runs authoritative verification and makes the commit per unit, then retires the worker ("fresh worker invariant"). — [execution-strategy.md](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-work/references/execution-strategy.md)
- [PRIMARY] `ce-code-review`: report-only by default; reviewer personas chosen by diff signals (correctness always; testing, maintainability >=200 changed lines, security, performance, api-contract, data-migration, reliability, adversarial >=50 changed lines or auth/payments, etc.); each persona writes full JSON to a run dir and returns a compact finding set; confidence anchors 50/75/100 with a mandatory quoted line (`first_evidence`) for 75/100 findings; a validation pass; and a cross-model adversarial peer (another provider's CLI) whose agreement counts only when `independence_verified` is true. — [persona-catalog.md](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-code-review/references/persona-catalog.md), [dispatch-reviewers.md](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-code-review/references/dispatch-reviewers.md)

#### wshobson/agents
- [PRIMARY] Two shapes: single-purpose plugins (agents + commands + skills per domain) and orchestrators. `conductor` implements "Context -> Spec & Plan -> Implement" with tracks (`spec.md`, `plan.md`, `metadata.json`) under `conductor/`, TDD red-green-refactor with verification checkpoints, semantic git revert by track/phase/task; `agent-teams` drives Claude Code's experimental agent teams (presets for review, debug, feature, fullstack, research, security, migration; file-ownership boundaries). — [conductor README](https://github.com/wshobson/agents/blob/main/plugins/conductor/README.md), [agent-teams README](https://github.com/wshobson/agents/blob/main/plugins/agent-teams/README.md)
- [PRIMARY] Docs describe "Hybrid Orchestration Patterns" such as Sonnet architect -> Haiku implementation -> Haiku test generation -> Sonnet review, but the same page's model-criteria text is internally inconsistent with the agent table (it lists "architecture" under Sonnet and "security audits" under Sonnet while the table gives Opus for architecture/security). — [docs/agents.md](https://github.com/wshobson/agents/blob/main/docs/agents.md)

#### SuperClaude
- [CLAIM] Slash-command-per-phase (`/sc:brainstorm`, `/sc:design`, `/sc:implement`, `/sc:test`, `/sc:pm`, ...), personas as agents, behavioral modes, a `confidence-check` skill ("≥90% confidence to proceed", five weighted checks) and Python helpers (ConfidenceChecker, SelfCheckProtocol, ReflexionPattern, ParallelExecutor) that ship in the pip package; context passes through the conversation and optional MCP memory. CHANGELOG 4.3.0 documents "Claude Code gap analysis: skills migration (critical), hooks integration (high), plan mode (medium)". — [README](https://github.com/SuperClaude-Org/SuperClaude_Framework/blob/master/README.md), [confidence-check](https://github.com/SuperClaude-Org/SuperClaude_Framework/blob/master/skills/confidence-check/SKILL.md), [CHANGELOG](https://github.com/SuperClaude-Org/SuperClaude_Framework/blob/master/CHANGELOG.md)

#### claude-flow / Ruflo
- [CLAIM] Swarms with hierarchical/mesh/adaptive topologies and queen-led consensus (Raft, Byzantine, Gossip), shared memory (AgentDB/HNSW), self-learning (SONA, ReasoningBank), federation across machines; hooks "automatically route tasks, learn from successful patterns, and coordinate agents in the background". — [README](https://github.com/ruvnet/ruflo/blob/main/README.md)
- [PRIMARY] The repo's own CLAUDE.md states "Ruflo is the coordination ledger and policy decision point. Claude Code executes code, tests, commands, and file changes. A Ruflo coordination call records work; it does not perform the implementation." — [CLAUDE.md](https://github.com/ruvnet/ruflo/blob/main/CLAUDE.md)
- [INDEPENDENT] Audits found `agent_spawn` creates only a map entry (no subprocess or LLM call): 85% of MCP tools mock/stub in Aug 2025 (issue #653, reproduced by commenters) and ~97% stubs in v3.5.51 (discussion #1513, 2026-04-04, no maintainer reply in the thread). A user also reported Claude not using swarms unless told to (#1476, 2026-03-29). — [#653](https://github.com/ruvnet/ruflo/issues/653), [#1513](https://github.com/ruvnet/ruflo/discussions/1513), [#1476](https://github.com/ruvnet/ruflo/issues/1476)

#### Anthropic first-party
- [PRIMARY] `feature-dev` is one command with 7 phases in the main session: Discovery, Codebase Exploration (2-3 `code-explorer` agents in parallel, each returning 5-10 key files that the main session then reads), Clarifying Questions ("DO NOT SKIP", wait for answers), Architecture Design (2-3 `code-architect` agents with different focuses: minimal change, clean, pragmatic; user picks), Implementation ("DO NOT START WITHOUT USER APPROVAL"), Quality Review (3 parallel `code-reviewer` agents), Summary. — [feature-dev.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/feature-dev/commands/feature-dev.md)

- [PRIMARY] Dynamic workflows: Claude writes a JavaScript script using `agent()`, `pipeline()`, `parallel()`, `phase()`; intermediate results stay in script variables; up to 16 concurrent agents by default, 1,000 agents per run, resumable in-session, no mid-run user input ("For sign-off between stages, run each stage as its own workflow"); plugins can ship workflows in a `workflows/` dir. — [Workflows docs](https://code.claude.com/docs/en/workflows)

### Inferences
- Superpowers SDD is the closest published analogue of wm's lead/implementer/reviewer split (fresh implementer with explicit statuses including BLOCKED, task review against the order, final review), but differs on who commits (the implementer commits in SDD; in wm the lead commits once per approved order), on who decides under ambiguity (the controller "rules" and continues; wm's implementer BLOCKS and the lead decides), and on enforcement (prose only).
- The convergence on file-based handoff (task brief, report file, diff package, ledger) across Superpowers and CE, and on "orchestrator commits" in CE, suggests wm's work-order/report/commit design is on the mainstream path.
- Nobody in the compared set has an equivalent of wm's T0-T4 ladder; the nearest is Superpowers' three-path triage and CE's lite vs full review paths. wm's finer ladder is novel but must prove it lowers cost (see CE #1703 in Q9).
- Native workflows and agent teams overlap with swarm-style plugins (Ruflo, wshobson `agent-teams`, OMC team mode); a lead-orchestrated, approval-gated model like wm is the use case workflows explicitly do NOT cover (no mid-run user input).

### Gaps
- GSD Core's per-task commit behavior and verifier mechanics were not read in detail; gstack's and OMC's orchestration internals were only skimmed.
- No timing or cost comparison of SDD vs CE `ce-work` vs feature-dev on the same task exists in the sources found.

## 4. Does each assign model tiers per agent (haiku, sonnet, opus), and on what basis?

### Takeaway
Static per-agent `model:` tiers appear in wshobson (202 agents: 70 sonnet, 54 opus, 52 inherit, 24 haiku, 2 fable), ECC (58 sonnet/6 haiku/4 opus), OMC (10 sonnet/7 opus/2 haiku) and Anthropic's agents; Superpowers and CE instead choose models at dispatch time ("always state the model"; CE: three reviewers inherit the session model, all others run on the mid-tier). No compared plugin offers an approval-gated top-model consult like wm's Fable advisor; the nearest are CE's `plan_model: fable` config and Claude Code's native advisor tool.

### Cited Findings
- [PRIMARY] Superpowers has no agents directory and no static tiers. SDD "Model Selection" says: use the least powerful model that can handle each role; mechanical 1-2 file tasks with a complete spec use a cheap model, integration work a standard model, design work the most capable; the final whole-branch review uses "the most capable available model, not the session default"; fix-loop rounds 4-5 go "at least one tier above" the stuck implementer; "Always specify the model explicitly when dispatching a subagent. An omitted model inherits your session's model"; "Turn count beats token price": use a mid-tier floor for reviewers and prose-spec implementers because the cheapest models "routinely take 2-3x the turns". — [SDD SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)
- [PRIMARY] Issue #1631 (closed) reported "Model Selection guidance is not enforced at worker dispatch, so workers inherit the parent model"; the v6.0.0 notes say "one run put all 26 of its reviewers on the top tier" and the templates now carry "model: [MODEL — REQUIRED]" (the notes do not link the two, but they describe the same failure). Enforcement is still prose in a template, not a hook. — [issue #1631](https://github.com/obra/superpowers/issues/1631), [implementer-prompt.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/implementer-prompt.md)
- [PRIMARY] CE `ce-code-review`: `correctness-reviewer`, `security-reviewer` and `adversarial-reviewer` "inherit the session model with no override" because they do the highest-stakes analysis; every other persona and prompt asset uses "the platform's mid-tier model" (Sonnet class in Claude Code); the override must be applied "on every Agent / spawn_agent / subagent call. A missed override is a silent cost-and-quality regression". The orchestrator inherits the session model. — [dispatch-reviewers.md](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-code-review/references/dispatch-reviewers.md)

## 5. Does each enforce anything deterministically with hooks (blocking, gates, verification), or rely on instructions alone?

### Takeaway
Most workflow plugins are instruction-only (Superpowers: one SessionStart injection; CE: no hooks; wshobson: hooks in 2 of 92 plugins; SuperClaude: advisory prompt hooks; Ruflo: hooks built never to block), while deterministic blocking exists in hookify, ralph-loop (a Stop gate on a self-reported string), GSD Core's PreToolUse guards, tdd-guard and gstack's careful/freeze/guard. A grep of 15 repos found no use of `SubagentHandback` and no role guards keyed on the caller's `agent_type`, so wm's design is distinctive, but `SubagentHandback` exists only in auto mode.

### Inferences
- The documented skipped-review incidents (#463, #2372, #1120) are the empirical case for wm's choice to gate by hook; the only comparable "hard guard" philosophy in the wild is GSD Core's, and it is explicit that prose backstops cannot fix prose defects.
- The closest thing to wm's done-gate elsewhere is the Stop-gate family (ralph-loop, hookify `require-tests-run`), which gates the main session on a string or transcript pattern rather than running the project's gates; wm's design (run gates from `.claude/working-model.json`, deny the subagent's hand-back) is stronger but depends on auto mode and on hooks not timing out.
- Coverage gap to verify for wm: outside auto mode a subagent returns text, not a `SubagentHandback` call, so a PreToolUse gate on that tool would not fire; a `SubagentStop` hook filtered on `agent_type` is the documented fallback.

### Gaps
- Did not execute any competitor hook; findings are from reading hook configs and scripts.
- tdd-guard's and cc-safety-net's detailed mechanisms are covered by a separate survey and were not re-read here.
- Official-doc statements marked "(page summary)" came through an extraction tool; the SubagentHandback, timeout and `agent_type` quotes were re-verified against the downloaded docs.

## 6. Does each have a learning or memory loop, and how is it curated?

### Takeaway
Only Compound Engineering (compound + refresh + packs) and ECC (instincts) ship real learning loops with explicit curation rules; Anthropic offers single-step tools (`/revise-claude-md`, hookify's conversation analysis); Superpowers has none in-product; Ruflo and SuperClaude advertise learning that audits or issues say was hollow or limited. mattpocock's `retro` adds the most useful classification rule: mechanical failures become deterministic checks, not prose rules.

### Gaps
- Could not measure whether CE's `docs/solutions/` actually reduces repeat errors; the only evidence is Every's claims and one reviewer's opinion.
- ECC's instinct quality (false positives) is unmeasured in the sources found.

## 7. How is each plugin itself tested or evaluated (evals, test suites, `claude plugin eval`)?

### Takeaway
Structural CI is common (CE ~80 test files, wshobson validate/garden/pytest), behavioral evals are rarer and expensive (Superpowers' Quorum lab, CE eval cells, agent-skills' three tiers with `claude plugin eval`), and Anthropic's official `claude plugin eval` (Claude Code 2.1.269+) now provides cases, graders and a with/without-plugin delta. ### Cited Findings

### Inferences
- wm already has the hard part most plugins lack (deterministic hooks that can be unit-tested with fixture JSON); the missing layer is behavioral: `claude plugin eval` cases per skill (trigger and no-trigger prompts, `tool_used: Skill` plus an output grader), run with pinned `--model`, with the with/without Δ reported, and ideally a placebo arm.
- Because skill invocation is stochastic (agent-skills data), wm's essentials should live in hooks and the SessionStart payload (deterministic) rather than depend on skill triggering.

### Gaps
- No source evaluates CE, wshobson or Ruflo end-to-end on a shared task; maintainer eval results (Superpowers, CE) are not independently reproducible without their labs and budgets.
- The Karpathy-guidelines and Superpowers audits come from one small repo (1 star) and should be treated as indicative.

- The strongest onboarding designs are manual-only (`disable-model-invocation: true`), explore first, present findings, lead each question with a recommendation, preview the draft, then write; CE adds a resolved-paths report and fail-closed config validation. ### Gaps
- Did not run any installer; behavior on a real brownfield repo is unverified for all plugins.

### Inferences
- Cost complaints cluster where review loops or fan-out are unconditional (SDD per-task reviews, CE's default `ce-code-review` after `ce-work`). Both maintainers' fixes were the same kind: make heavy paths conditional (Superpowers' bounded/spike paths and one reviewer per task; CE 3.4's "more optional" review). wm's T0-T4 ladder is the right lever but must be enforced mechanically for T0/T1.
- Criticisms of rigidity (cannot disable git workflow, worktrees, auto-trigger) are about missing opt-outs; wm should expose config for these from day one.

## 10. Concrete ideas wm could adopt (exact mechanism and where it lives) and pitfalls it should avoid

### Takeaway
No compared plugin combines wm's three distinguishing mechanisms (hook-enforced done-gate on the subagent hand-back, agent_type-keyed role guards, human-approved top-model consult), so wm is differentiated rather than redundant; the best borrowable ideas are file-based handoff and ledgers, read-only skeptical reviewers with bounded fix loops, CE's durable-bar learning curation, mattpocock's "mechanical failures become deterministic checks", GSD's fail-closed guards, official `claude plugin eval`/`details` measurement, and strict scope discipline for a published plugin. The main pitfalls are unconditional ceremony cost, instruction-only gates, fail-open hooks, always-on bloat, and platform assumptions (SubagentHandback exists only in auto mode).

### Cited Findings
Platform and ecosystem facts that bound the design (each cited in Q1-Q9; repeated here with sources for the writer):
- [PRIMARY] `SubagentHandback` availability, plugin hooks inside subagents, `agent_type`, `SubagentStop` blocking, command-hook timeouts that do not block, `if`/`asyncRewake`. — [Tools reference](https://code.claude.com/docs/en/tools-reference), [Hooks reference](https://code.claude.com/docs/en/hooks)
- [PRIMARY] Always-on measurement and the 2,000-token highlight, 1,536-character description cap, `disable-model-invocation`. — [Measure](https://code.claude.com/docs/en/plugins/measure), [Skills](https://code.claude.com/docs/en/skills)
- [PRIMARY] Native advisor (model-driven timing, whole conversation, no cap, Sonnet 5.5 + Fable pairing allowed, experimental, Anthropic API only) and dynamic workflows (no mid-run user input). — [Advisor](https://code.claude.com/docs/en/advisor), [Workflows](https://code.claude.com/docs/en/workflows)
- [PRIMARY] Superpowers helper scripts and templates that implement the handoff ideas: `skills/subagent-driven-development/scripts/{sdd-workspace,task-brief,review-package}`, `implementer-prompt.md`, `task-reviewer-prompt.md`, `re-review-prompt.md`. — [SDD dir](https://github.com/obra/superpowers/tree/main/skills/subagent-driven-development)
- [PRIMARY] CE learning and review internals: `skills/ce-compound/SKILL.md` (durable bar), `skills/ce-compound-refresh/SKILL.md`, `skills/ce-code-review/references/{persona-catalog,dispatch-reviewers,findings-schema.json}`, `skills/ce-work/references/execution-strategy.md`. — [skills](https://github.com/EveryInc/compound-engineering-plugin/tree/main/skills)

### Inferences

#### Ideas to adopt (mechanism -> where it lives -> wm mapping)
1. Handoff by files plus a plan-scoped ledger. Superpowers' `scripts/task-brief`, `review-package` (exit 3 on empty/non-descendant range) and `sdd-workspace` (`.superpowers/sdd/<plan>/progress.md`, kept outside `.git/`). For wm: a work-order folder with brief, implementer report, review package and a ledger line per order so a lead that loses context after compaction resumes from git + ledger; note `git clean -fdx` deletes the ledger.
2. Skeptical, read-only, bounded review. `task-reviewer-prompt.md`: read-only checkout, "Do Not Trust the Report", noisy test output is a finding, "Cannot verify from diff" and "Declined to judge" lists returned to the lead, lead may not pre-judge or tell the reviewer what to ignore; `re-review-prompt.md` scopes a re-review to the fix diff; max five fix rounds with the later rounds escalated one tier (Superpowers) or `max_escalations` (GSD). For wm: put the "lead may not coach the reviewer" rule in the lead's rules and enforce reviewer read-only with a role guard.
3. Finding quality gates from CE. Confidence anchors (50/75/100), a mandatory quoted line (`first_evidence`) for high-confidence findings, a validation pass, and selecting reviewer lenses by diff signals; and from Anthropic's `code-review`, a 0-100 score with a drop threshold of 80 and an exclusion list (what linters/CI catch, pre-existing issues). For wm: one Opus reviewer can still adopt the schema (quoted line, confidence, "pre-existing" flag).
4. Verify the model actually used. OMC's delegation enforcer and Superpowers #1631 show silent inheritance is a recurring failure; the hook docs expose `resolvedModel` on the Agent tool result. For wm: a PostToolUse audit on `Agent` that flags when `resolvedModel` differs from the role's intended model (Opus on an implementer, Sonnet on a reviewer).
5. Triage ratchet. Superpowers: announce the classification so the user can override, "when in doubt take the heavier path", one-way upgrade, hard-gate approvals per path; CE: lite vs full review paths (`lite_eligible`). For wm: T0-T4 should be announced, upgrade-only mid-task, and T0/T1 must skip multi-agent review by construction (CE #1703 is the cautionary case: 17.1M input tokens for a 32-line change).
6. Work orders as decisions, not code. Superpowers 6.4.2 "A plan records decisions. It's not a transcript of the code", exact signatures/test assertions/spec values, self-review comparing plan length to spec length, plus a "Review Focus" list (up to five inputs the spec implies but no test exercises, each pinned by a test) added because "every implementer shipped the same crash on an input the spec implied but never named". The 6.4.2 notes warn Opus 5.5 can over-build while planning, which is wm's lead model.
7. Learning-loop curation. CE's durable bar (counterfactual: would a future engineer repeat the mistake if this note vanished?), one learning per run, evidence-quoting refresh/prune (`ce-compound-refresh`), and mattpocock's `retro` classification (mechanical -> linter/hook/CI check, judgment -> reviewer standard, navigation -> pointer; "Default to building the check over writing the rule"). For wm: add a "promote to deterministic check" route and a "retire stale rule" route to the findings->rules loop, and cap SessionStart injection (ECC: 6 items, confidence >= 0.7, 8,000 chars).
8. Onboarding pattern. mattpocock's setup skill (manual-only, explore, present, one question at a time with a recommended answer, draft preview, then write), conductor's resumable `setup_state.json` and greenfield/brownfield detection, CE's health-check script that reports resolved paths and fails closed on bad config. For wm `/wm:adopt`: idempotent, dry-run diff, detect existing gates and rules, write `.claude/working-model.json`.
9. Fail-closed guards. GSD's isolation guard denies when it cannot read its own config ("a guard that cannot verify must not answer 'safe'"), whereas Claude Code lets a timed-out command hook through; set explicit short timeouts, catch exceptions and return deny on internal errors, and prefer exec-form hooks (no shell) and quoted `${CLAUDE_PLUGIN_ROOT}` (validator warns; Superpowers #2081 shows multi-process Windows startup cost). Use the `if` field (as security-guidance does) to avoid spawning hooks on irrelevant calls.
10. Measure and publish context cost. Run `claude plugin details wm` in CI and publish listing tokens plus the SessionStart payload separately; keep manual-only skills at `disable-model-invocation: true`; stay well under the 2,000-token "Every turn" highlight. Superpowers trimmed its bootstrap in 6.1.0 because it is "paid for constantly".
11. Behavioral evals with `claude plugin eval`. Cases for each skill (trigger and no-trigger prompts, `tool_used: Skill` plus a reply grader), pinned `--model`, report Δ vs no plugin, and a placebo arm as in `skill-receipts`; add pressure scenarios (time pressure, sunk cost, authority) from Superpowers' `writing-skills`/agent-skills; keep deterministic hook tests separate and CI-safe (Quorum split: static gates in CI, live runs on demand).
12. Scope discipline for a public plugin. `SCOPE.md` with an "observed failure" bar, `.out-of-scope/` records, frozen buckets, `needs-info` auto-close after 14 days; in-repo ADRs for the plugin's own decisions (mattpocock `.agents/adr`, GSD `docs/adr`). This limits bloat and issue noise.
13. Model-specific overlays. gstack's `model-overlays/*.md` (Fable 5 over-plans, Opus 4.8 is literal) rendered into skill docs; wm could keep 3-5 line notes per model for Opus 5.5 (over-building while planning), Sonnet 5.5 and Haiku 4.5.
14. Anti-recursion and subagent hygiene. Superpowers forbids implementers/reviewers from spawning subagents ("a worker-spawned reviewer is a defect to flag"); official controls: omit `Agent` from `tools`/`disallowedTools: Agent`, `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1`; the Reddit 166-subagent anecdote is the failure mode. wm's role guards should deny `Agent` for implementer, reviewer, scout, researcher.
15. Release hygiene. Tag with `claude plugin tag`, bump `version` on every release (otherwise users get "already at the latest version"), name permanently (`renames` otherwise), run `claude plugin validate --strict` in CI, and publish through an own marketplace file; add a second maintainer with registry/marketplace rights (the GSD incident).

#### Pitfalls to avoid
- Instruction-only gates for anything that must hold (Superpowers #463/#2372; CE #57). Keep wm's hook gates; do not move them into prose.
- Unconditional ceremony. Superpowers (#743, #2017, #1120, and a #1152 commenter who "can't afford to use it anymore") and CE (#726, #1703) drew cost complaints; keep T0/T1 cheap and make heavy review opt-in or signal-gated.
- Unbounded loops: ralph-loop defaults to unlimited iterations; CE reported a ~$114 loop session; always cap rounds and escalate to the user.
- Always-on bloat: CE 36k -> 12k -> 3k history, ECC 44.8k, Ruflo 15-25k (audit, may be outdated), wshobson 43.8k if everything installed. Do not register agents for roles that can be skills or references; keep the SessionStart payload terse.
- Aggressive persuasion text ("EXTREMELY_IMPORTANT", "1% chance you MUST") as a substitute for mechanisms: maintainers now report frontier models "insanely proactive" and skipping gates; a placebo-controlled audit shows prose that merely looks like process changes little. Prefer hooks plus short factual rules.
- Over-specified plans/work orders (Superpowers #895, 38 reactions) and models that build the project while planning (6.4.2 notes on Opus 5.5).
- Fail-open hooks and always-exit-0 hooks (Ruflo) for anything described as a gate; remember hook timeouts do not block.
- Platform assumptions: `SubagentHandback` only exists in auto mode (v2.1.271+), plugin agents ignore `hooks`/`mcpServers`/`permissionMode`, plugin subagents report `agent_type` as `wm:implementer` (scoped, regex-matched unless anchored with `^...$`, so an unanchored guard can over-match), the native advisor is experimental and API-only; add a `SubagentStop`-based fallback and test both modes and the anchored matchers.
- Unverifiable marketing numbers (Ruflo "75% lower costs", SuperClaude "30-50% fewer tokens") and audit-prone stubs; publish eval receipts instead of percentages. Star counts and install counts do not measure effect (karpathy-guidelines audit).
- Name and namespace collisions (wshobson 30 duplicate agent names, CE slash-name prefix issue); keep the `wm:` namespace and avoid generic names without prefix.
- Single-maintainer and registry-key risk (GSD) and marketplace pin lag (Superpowers pin one release behind; mattpocock notes days-to-weeks lag).
- Auto-extracted "learning" without review (ECC instincts, Ruflo SONA): Ruflo issues show it can silently persist nothing, and ECC needs hard caps; keep human-approved rules and add pruning.
