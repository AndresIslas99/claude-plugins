## 1. How do TDD Guard, claudekit, claude-code-hooks-mastery, hookify, security-guidance and destructive-command/git guardrails work (mechanism, adoption, limitations)?

### Takeaway
The surveyed tools fall into two families: deterministic pattern/parse guards (dcg, cc-safety-net, Dippy, hookify, claudekit, hooks-mastery) and LLM-judged policy gates (TDD Guard/Probity for TDD; security-guidance's background review). Adoption is largest for Anthropic's own plugins (security-guidance 241.8k installs, hookify 60.4k) and for destructive-command guards (dcg 6.1k stars; cc-safety-net 37.9k npm downloads/month); none of them publishes a controlled outcome evaluation, and their documented limits cluster around Bash/MCP bypass, false positives, fail-open defaults and per-OS portability.

### Cited Findings

#### TDD Guard (nizos/tdd-guard) and its successor Probity (nizos/probity)

SessionStart clears transient data (previous test results, lint reports) and creates the editable instructions file. — [README](https://github.com/nizos/tdd-guard); [installation doc](https://github.com/nizos/tdd-guard/blob/main/docs/installation.md); [session-management doc](https://github.com/nizos/tdd-guard/blob/main/docs/session-management.md)

- Adoption (GitHub API, 2026-10-07): 2,357 stars, 188 forks, 21 open issues, created 2025-07-07, last push 2026-10-05, latest release v1.7.0 (2026-06-23); npm downloads 76,031 for 2026-09-05..2026-10-04. — [GitHub API](https://api.github.com/repos/nizos/tdd-guard); [npm API](https://api.npmjs.org/downloads/point/last-month/tdd-guard)

Probity: 221 stars, created 2026-04-18, v1.10.1 on 2026-09-15, 18,622 npm downloads in the same 30-day window. — [TDD Guard README](https://github.com/nizos/tdd-guard); [Probity API](https://api.github.com/repos/nizos/probity); [npm API](https://api.npmjs.org/downloads/point/last-month/@nizos/probity)
- [VENDOR] Probity mechanism: one PreToolUse hook (matcher `Bash|Write|Edit|NotebookEdit`) runs rules from `probity.config.ts`. `enforceTdd()` uses an AI validator (agent's official SDK) that judges the pending write against recent session transcript events (default last 10 events, 6,000 chars per event), so no per-framework reporters are needed; an opt-in deterministic fast-path passes writes that add exactly one new test node. #### Anthropic's security-guidance plugin
- [OFFICIAL] Mechanism: built entirely on hooks. (1) PostToolUse on Edit/Write/MultiEdit/NotebookEdit: deterministic pattern match for risky calls (`eval(`, `pickle`, `dangerouslySetInnerHTML`, `.innerHTML =`, `document.write`, workflow files), no model call, warns once per pattern per file per session. (2) Stop hook: end-of-turn git-diff review by a separate Claude call run in the background (covers up to 30 changed files; re-prompts the writer at most 3 times in a row). (3) PostToolUse on Bash filtered with `if` to git commit/push: deeper agentic review (capped at 20 per rolling hour). SessionStart bootstraps a Python venv with the Agent SDK; UserPromptSubmit captures the baseline for the diff. "None of the layers block writes or commits"; custom guidance is "not deterministic guardrails ... For hard enforcement, pair the plugin with a hook that blocks the edit or a CI check". Reviews use Claude Opus 4.7 by default per the docs (a 2026-10-02 plugin commit switched to "follow the newest Opus", so docs may be outdated). Documented limits: the end-of-turn and commit reviews "skip silently outside a repository", model-backed reviews skip when the session has no Anthropic authentication or provider, commits made from the user's own shell are not reviewed, and the review model "can miss issues". — [docs](https://code.claude.com/docs/en/security-guidance); [plugin hooks.json](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/security-guidance/hooks/hooks.json); [commit history](https://github.com/anthropics/claude-plugins-official/commits/main/plugins/security-guidance)
- Adoption: 241,800 installs on its marketplace page (2026-10-07). — [claude.com/plugins/security-guidance](https://claude.com/plugins/security-guidance)

#### Destructive-command and git guardrails
- Destructive Command Guard `dcg` (Dicklesworthstone): Rust PreToolUse hook for Claude Code, Codex, Gemini, Copilot, Cursor and others; 50+ "packs" (git, filesystem, databases, Kubernetes, cloud, Terraform); scans heredocs and inline `python -c` scripts; context-aware (does not block `grep "rm -rf"`); sub-millisecond latency is self-reported. Failure policy is explicit: default is fail-open for unparseable hook input, `DCG_FAIL_CLOSED=1` opts into blocking, `DCG_UNVERIFIED_DECISION=deny|ask` sets what happens on timeouts ("deny suits unattended sessions where nobody can answer ask"). 6,092 stars, created 2026-01-07, last push 2026-10-06; custom license. — [README](https://github.com/Dicklesworthstone/destructive_command_guard); [API](https://api.github.com/repos/Dicklesworthstone/destructive_command_guard)
- cc-safety-net (kenryu42): blocks destructive git/filesystem commands and access to secrets (SSH keys, `.env`, `~/.aws`) from the shell and from file tools by parsing what a command does (also inside `bash -c`/`python -c`); "A broken config file never blocks anything" (fail-open by design) and "It is not a sandbox"; Standard/Strict/Paranoid presets; Node 18+; 14+ supported CLIs. 1,577 stars (created 2025-12-25, last push 2026-10-06); 37,935 npm downloads for 2026-09-05..2026-10-04. — [README](https://github.com/kenryu42/cc-safety-net); [API](https://api.github.com/repos/kenryu42/cc-safety-net); [npm API](https://api.npmjs.org/downloads/point/last-month/cc-safety-net)
- Dippy (ldayton): the inverse approach: auto-approves safe commands using its own hand-written bash parser and prompts or denies the rest, with custom deny messages; vendor claims "up to 40% faster development" (no source). 243 stars, last push 2026-06-12. — [README](https://github.com/ldayton/Dippy); [API](https://api.github.com/repos/ldayton/Dippy)
- karanb192/claude-code-hooks: 22-plugin marketplace of PreToolUse/PostToolUse scripts that block `.env`/secret exfiltration, `curl | sh`, `rm -rf`, force pushes to main and tampering with the hook config; claims 1,949 passing tests and an OWASP LLM Top 10 mapping; 530 stars, last push 2026-10-04. — [README](https://github.com/karanb192/claude-code-hooks); [API](https://api.github.com/repos/karanb192/claude-code-hooks)
- [OFFICIAL] Anthropic's own reference: a PreToolUse example blocking `rm`-style commands with `if: "Bash(rm *)"` and `exit 2`, and a complete `bash_command_validator_example.py` in the claude-code repo. — [hooks guide](https://code.claude.com/docs/en/hooks-guide)

#### Instruction-only comparator
- obra/superpowers (296,012 stars on 2026-10-07, created 2025-10-09) delivers its TDD/plan/review methodology as skills plus a session-start bootstrap, not as blocking hooks ("Mandatory workflows, not suggestions" is instruction text); its behavior is tested by a separate eval lab (see section 4). — [README](https://github.com/obra/superpowers); [API](https://api.github.com/repos/obra/superpowers)

### Inferences
- Two design families with different cost/failure profiles: deterministic guards are cheap and predictable but only cover mechanically detectable rules; LLM-judged gates (TDD Guard/Probity, security-guidance reviews) cover judgement rules at the price of a model call per check, JSON-parsing failures (TDD Guard #200, Claude Code #58558) and rate/credit failures (TDD Guard #139).
- wm's done-gate (commands mapped to globs plus diff-based suppression detection) sits in a less crowded niche than destructive-command guards: among surveyed tools only hookify's Stop rule (regex over transcript) and claudekit's Stop hooks (project-wide typecheck/lint/test) do something similar, and I found no surveyed tool that gates a subagent's final report (the SubagentHandback tool is new, v2.1.271+).
- Role-based guards keyed on `agent_type` have no close public analogue; disler's Builder/Validator pair enforces roles through the agent's tool list, not hooks, and dcg's agent profiles distinguish vendors (Claude Code vs Codex), not roles.
- Popularity signals (stars, installs) are the only adoption evidence; they say nothing about effectiveness.

### Gaps
- No per-plugin star counts for hookify/security-guidance (monorepo); used marketplace install counts instead.
- No independent false-positive/false-negative measurements for dcg, cc-safety-net, Dippy, claudekit or hookify were found; performance claims (dcg sub-ms, Dippy 40%) are vendor-only.
- claudekit's `self-review` hook mechanism and TDD Guard's UserPromptSubmit role were not verified in source.
- Hacker News/Reddit user reports on these tools could not be retrieved (search budget exhausted).

## 2. Which hook patterns are recommended or documented as best practice?

### Takeaway
Anthropic's docs position hooks as the place for rules that "must happen every time with zero exceptions" (instructions in CLAUDE.md are "context, not enforced configuration"), and document PostToolUse format/lint, Stop-hook verification gates with a loop guard, SessionStart context re-injection after compaction, async/asyncRewake background reviews (security-guidance is the reference implementation), and a best-effort `if` filter that the docs themselves say not to trust for hard allow/deny decisions. There is no official guidance for test-first (red-before-green) checks; that pattern exists only in third-party tools.

### Cited Findings

#### Official positioning (hooks vs instructions)
- [OFFICIAL] "Use hooks for actions that must happen every time with zero exceptions ... Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." Also: if Claude already does something correctly without a CLAUDE.md line, "delete it or convert it to a hook"; an over-long CLAUDE.md makes Claude ignore half of it. — [best practices](https://code.claude.com/docs/en/best-practices)
- [OFFICIAL] "Claude treats them [CLAUDE.md and auto memory] as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." — [memory](https://code.claude.com/docs/en/memory)
- [OFFICIAL] PreToolUse hooks fire before any permission-mode check; a `deny` blocks even in `bypassPermissions`; a hook `allow` does not override deny/ask rules; hooks in settings files and in a plugin's `hooks/hooks.json` "can tighten restrictions but not loosen them". A mod that handles `tool.check` can approve a call a PreToolUse hook blocked unless the hook is in managed settings. — [hooks guide](https://code.claude.com/docs/en/hooks-guide)

#### PostToolUse format and lint
- [OFFICIAL] Documented recipe: PostToolUse with matcher `Edit|Write` running Prettier on the edited file; for files changed by Bash use a FileChanged hook; the best-practices page suggests "Write a hook that runs eslint after every file edit". Because Claude can also modify files through shell commands, "add a Stop hook that scans the working tree once per turn" or match `Bash|PowerShell` and list changes with `git status --porcelain`. — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [best practices](https://code.claude.com/docs/en/best-practices)
- Third-party: claudekit `lint-changed`/`typecheck-changed`/`test-changed`; hooks-mastery ruff/ty validators that block on errors. — [claudekit](https://github.com/carlrannaberg/claudekit); [hooks-mastery](https://github.com/disler/claude-code-hooks-mastery)
- PostToolUse "can't undo actions since the tool has already executed". — [hooks guide](https://code.claude.com/docs/en/hooks-guide)

#### Stop-hook verification (completion gates)
- [OFFICIAL] "As a deterministic gate: a Stop hook runs your check as a script and blocks the turn from ending until it passes." Alternatives in the same list: ask in the prompt, a `/goal` condition (a separate evaluator re-checks after every turn), or a verification subagent whose fresh context tries to refute the result. "Have Claude show evidence rather than asserting success." — [best practices](https://code.claude.com/docs/en/best-practices)
- [OFFICIAL] Loop guard: Stop/SubagentStop input carries `stop_hook_active`; Claude Code applies an 8-consecutive-continuation cap (counter resets when Claude calls a tool; override with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`); `additionalContext` is the non-error alternative to `decision: "block"` and has the same loop protections. Stop hooks "don't fire on user interrupts"; API errors fire StopFailure. — [hooks reference](https://code.claude.com/docs/en/hooks); [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [OFFICIAL] Judgment-based gates: `type: "prompt"` hooks return `{"ok": true|false, "reason"}`; on Stop/SubagentStop `ok:false` feeds the reason back unless the response sets `"impossible": true`; on PreToolUse/PostToolUse `ok:false` ends the turn by default (reason shown as a warning) unless `continueOnBlock: true` (changed in v2.1.210). `type: "agent"` hooks (tool access, default 60 s, up to 50 turns) are marked experimental; "For production workflows, prefer command hooks". — [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Related native task-level gates: TaskCreated/TaskCompleted hooks (exit 2 blocks creation/completion), SubagentStop (exit 2 or `decision: "block"` prevents the subagent stopping). — [hooks reference](https://code.claude.com/docs/en/hooks)

#### Test-first checks (a test must fail before implementation)
- No official hook recipe. Anthropic's prompting advice is instruction-level ("write a failing test that reproduces the issue, then fix it"). — [best practices](https://code.claude.com/docs/en/best-practices)
- Third-party: TDD Guard/Probity (LLM validator over transcript/test results; Probity adds deterministic `requireCommand` and a one-new-test fast-path); Superpowers' TDD is a skill (instruction). — [Probity rules](https://github.com/nizos/probity/blob/main/docs/rules.md); [Superpowers README](https://github.com/obra/superpowers)

#### Secret scanning and sensitive-file protection
- [OFFICIAL] Recipe: PreToolUse script exits 2 on protected path patterns (`.env`, `package-lock.json`, `.git/`) with Windows backslash normalization; PostToolUse can redact output via `updatedToolOutput`. security-guidance supports custom per-edit patterns in `.claude/security-patterns.yaml|json` (example `sk_live_`, `AKIA`), advisory only. — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [hooks reference](https://code.claude.com/docs/en/hooks); [security-guidance docs](https://code.claude.com/docs/en/security-guidance)
- Third-party: claudekit file-guard (195+ patterns), cc-safety-net secret protection, karanb192 secret/exfiltration hooks. — [claudekit](https://github.com/carlrannaberg/claudekit); [cc-safety-net](https://github.com/kenryu42/cc-safety-net); [karanb192](https://github.com/karanb192/claude-code-hooks)
- [ISSUE] #89273: an auto-mode agent bulk-staged 66 files and committed/pushed a plaintext credential; PostToolUse cannot prevent a commit, and a PreToolUse Bash hook with a broad matcher "must fail open" because denying on internal error would block every command (open, 2026-08-24). — [#89273](https://github.com/anthropics/claude-code/issues/89273)

#### Blocking dangerous commands
- [OFFICIAL] Documented example (`if: "Bash(rm *)"` + script exit 2 / `permissionDecision: "deny"`); deny/ask permission rules are enforced regardless of hook output; the sandboxed Bash tool is the OS-level layer. For hard allow/deny the docs say to use the permission system: "Because the filter [`if`] is best-effort, use the permission system rather than a hook to enforce a hard allow or deny." — [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Third-party catalog: dcg, cc-safety-net, Dippy, damage-control, karanb192 hooks (section 1). [ISSUE/OPINION] #70420 reports that prose MUST-rules were violated "sometimes in the very turn after writing or tightening the rule", that hooks fixed it but only for rules "mechanically detectable from a tool's input", and that correct Bash flag parsing needed a real shell tokenizer (closed 2026-06-23). — [#70420](https://github.com/anthropics/claude-code/issues/70420)

#### Async and asyncRewake reviews
- [OFFICIAL] `async: true` (command hooks only) runs in the background; results (`additionalContext`, `systemMessage`) arrive on the next turn; async hooks cannot block (decision fields have no effect); `timeout` is not enforced on plain async hooks but is on `asyncRewake`; an `asyncRewake` hook exiting 2 wakes Claude even when idle (stderr, or stdout if stderr is empty, becomes a system reminder); in `-p` mode running async hooks are killed at teardown (outcome `cancelled`); no deduplication across firings. — [hooks reference](https://code.claude.com/docs/en/hooks)
- [OFFICIAL] Reference implementation: security-guidance's Stop hook uses `asyncRewake` with `rewakeMessage`/`rewakeSummary` fields so an Opus review of the turn's diff re-prompts the writer only if it finds issues; Anthropic describes the plugin source as "a working example of running a separate model call from a hook and feeding the result back to the session". The reference page I could read documents `async`/`asyncRewake` but not `rewakeMessage`/`rewakeSummary` (used in the plugin's hooks.json). — [security-guidance docs](https://code.claude.com/docs/en/security-guidance); [hooks.json](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/security-guidance/hooks/hooks.json)

#### `if` conditions in hooks.json
- [OFFICIAL] `if` uses permission-rule syntax (`Bash(git *)`, `Edit(*.ts)`) so the hook process only spawns on a matching tool call; for Bash each subcommand and `$()`/backtick content is checked; "When Claude Code can't determine which commands the Bash input runs, it runs your hook regardless". It works only on tool events: "Adding it to any other event prevents the hook from running". Multiple tool names need separate handlers. — [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [OFFICIAL] security-guidance's hooks.json enumerates one entry per command shape (`Bash(git commit:*)`, `Bash(git -C * commit *)`, `Bash(git push:*)`, `Bash(git -C * push*)`, `gt create/modify/submit`) rather than one broad pattern. — [hooks.json](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/security-guidance/hooks/hooks.json)

#### Other documented patterns relevant to wm
- [OFFICIAL] SessionStart `compact` matcher re-injects context after compaction; SessionStart/UserPromptSubmit stdout and `additionalContext` are capped at 10,000 characters; `additionalContext` must be nested in `hookSpecificOutput` or it is "silently ignored". — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [hooks reference](https://code.claude.com/docs/en/hooks)
- [OFFICIAL] Matching hooks run in parallel; "every hook's command runs to completion before Claude Code merges the results. One hook returning deny doesn't stop sibling hooks"; precedence deny > defer > ask > allow; when several PreToolUse hooks return `updatedInput` the last to finish wins and "the order is non-deterministic. Avoid having more than one hook modify the same tool's input." Identical handlers defined in several settings files run once, but a plugin's copy "stays separate". — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [hooks reference](https://code.claude.com/docs/en/hooks)
- [OFFICIAL] Hook scripts: quote variables, block `..`, use absolute paths/`${CLAUDE_PROJECT_DIR}`, skip sensitive files; exec form (`command` + `args`) avoids shell quoting; pipe sample JSON to a script to test it; `claude --debug-file <path>` and `/hooks` for inspection. — [hooks reference](https://code.claude.com/docs/en/hooks); [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- [OFFICIAL] Writer/Reviewer pattern and an "adversarial review step" with a fresh-context subagent; warning that a reviewer "will usually report some [gaps], even when the work is sound", so restrict findings to correctness and stated requirements. — [best practices](https://code.claude.com/docs/en/best-practices)
- [OPINION] A site (agentpatterns.ai, last reviewed 2026-06-09, no author) recommends a layered spectrum (advisory CLAUDE.md, probabilistic system prompt, deterministic hooks, organizational policy) and putting "binary, non-negotiable rules" in hooks; it cites no compliance percentages. — [agentpatterns.ai](https://agentpatterns.ai/instructions/enforcing-agent-behavior-with-hooks/)

### Inferences
- The official best-practice set maps onto wm already (done-gate = Stop-hook gate; role guards = PreToolUse protect-files; SessionStart injection); the main documented refinements wm should adopt are the loop guard/cap, compaction re-injection, scanning the working tree/diff because Bash edits bypass Edit/Write matchers, and a single modifier per tool input.
- Test-first enforcement has no official pattern, so wm would be designing it from first principles; the two available models are an LLM judge over the transcript (TDD Guard/Probity) or deterministic evidence checks (Probity `requireCommand`-style, or re-running tests).
- Because Anthropic itself says `if` is best-effort, gating logic should live inside the script and `if` should be used only as a performance optimization.

### Gaps
- No official documentation or recipe for "failing test before implementation" hooks.
- The minimum Claude Code versions for `if`, `args` (exec form) and `asyncRewake` were not stated on the pages I read.
- `rewakeMessage`/`rewakeSummary` were not found by the page summarizer in the hooks reference (read in three windows covering its 250k characters; parts were summarized rather than read verbatim); they may be documented elsewhere or undocumented.

## 3. What pitfalls are known (Stop loops, fail-open, slow hooks, false positives, confusing the model, subagents vs main session, plugin vs project hooks, folder trust, portability)?

### Takeaway
The dominant pitfall class is silent fail-open: any exit code other than 2, hook timeouts on PreToolUse, missing or non-executable scripts, plugin directories removed mid-session, hooks that are configured but never registered, and invalid JSON all let the tool call proceed. The next classes are Stop/SubagentStop loops and flaky SubagentStop blocking, coverage gaps (Bash-first edits in auto mode, MCP tools, disputed subagent coverage), unreliable `ask` in auto/headless runs, and portability (shell quoting of `${CLAUDE_PLUGIN_ROOT}`, Windows encodings and paths, macOS system Python 3.9).

### Cited Findings

#### Fail-open behavior
- [OFFICIAL] Exit code 1/127/any non-2 code, invalid JSON, JSON failing schema validation, a missing hook path, a crash by signal, and a timeout (except async) are non-blocking errors and the action proceeds; on PreToolUse "command/http/mcp_tool hooks don't block" on timeout (only Agent SDK callbacks do). stderr of an exit-0 hook goes to the debug log only. #### Hooks in subagents vs the main session
- [OFFICIAL] "Hooks from settings files, managed policy settings, and plugins all apply inside subagents, so a PreToolUse hook in settings.json also runs before every tool a subagent uses." Payloads inside a subagent (or `--agent` session) carry `agent_id` and `agent_type`; for plugin subagents the type is the plugin-scoped identifier such as `my-plugin:reviewer`, so matchers need `^...$` anchoring; SubagentStop also fires for Claude Code's internal agents (prompt suggestions, `/btw`) with `agent_type` empty or the session agent. #### Plugin vs project hooks, trust and tamper resistance
- [OFFICIAL] Locations table: plugin `hooks/hooks.json` hooks run when the plugin is enabled ("plugin trust"); managed `allowManagedHooksOnly` blocks user/project/local/plugin hooks except force-enabled plugins; `disableAllHooks` follows settings precedence, so "a project's settings file can override yours", and managed hooks are disabled only by managed settings; there is no way to disable an individual hook. `ConfigChange` hooks can block settings changes. — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [hooks reference](https://code.claude.com/docs/en/hooks)
- [OFFICIAL] Folder trust: in interactive sessions hooks from every settings file are held back until the workspace trust dialog is accepted; in `-p`/SDK sessions Claude Code "never shows the dialog and treats the folder as trusted, so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted"; `--bare` skips hooks, plugins, CLAUDE.md and memory unless supplied with flags such as `--plugin-dir`. Project subagent frontmatter hooks require trust only since v2.1.218. "Command hooks execute shell commands with your full user permissions." — [hooks reference](https://code.claude.com/docs/en/hooks); [headless](https://code.claude.com/docs/en/headless)

#### Portability and plugin packaging
- [OFFICIAL] Exec form (`command` plus `args`) avoids shell tokenization; on Windows it needs a real executable (`.exe`), not npm `.cmd` shims; shell-form hooks need `"${CLAUDE_PLUGIN_ROOT}"` in double quotes; plugin hook paths use forward slashes on Windows; PowerShell hooks must use `${CLAUDE_PROJECT_DIR}` or `$env:` forms; hook scripts must be executable; jq is not installed by default. Plugin hooks files need the top-level `"hooks"` wrapper. `${CLAUDE_PLUGIN_ROOT}` changes on update, so state belongs in `${CLAUDE_PLUGIN_DATA}`. — [hooks reference](https://code.claude.com/docs/en/hooks); [hooks guide](https://code.claude.com/docs/en/hooks-guide); [manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)
- [OFFICIAL, from Anthropic's own plugin] `security-guidance/hooks/sg-python.sh` documents: on Windows Git Bash `python3` is the Microsoft Store stub that "exits 49 silently in non-TTY subprocess context"; set `PYTHONUTF8=1` because Windows Python defaults to cp1252; convert MSYS `/c/...` paths with `cygpath -w`; "macOS ships 3.9.6 as the default `python3` on current versions"; the shim probes `python3.13`..`python3.10`, then `python3`, `python`, `py -3`, and degrades pattern-only checks on old Python. — [sg-python.sh](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/security-guidance/hooks/sg-python.sh); [security-guidance docs](https://code.claude.com/docs/en/security-guidance) (Python 3.7+, agentic review 3.10+)
- Python lifecycle: 3.9 reached end-of-life 2025-10-31 and 3.10 on 2026-10-01 (devguide status "end-of-life" for both on 2026-10-07); the 3.10 What's New page lists structural pattern matching (`match`), `X | Y` union types and parenthesized context managers (plus `zip(strict=)` and `dataclass(slots=True)`) as 3.10 additions; the resulting failures on 3.9 are SyntaxError for `match`/parenthesized `with`, and TypeError at runtime for `X | Y` evaluated outside postponed (`from __future__ import annotations`) annotations, for `zip(strict=)` and for `dataclass(slots=True)` (the exception types are general Python knowledge, not from the page). — [Python devguide](https://devguide.python.org/versions/); [What's New in 3.10](https://docs.python.org/3/whatsnew/3.10.html)
- [ISSUE] macOS plugin roots live under `~/Library/Application Support/...` (a space), so unquoted `${CLAUDE_PLUGIN_ROOT}` in several marketplace plugins broke hooks; for PreToolUse that blocked every tool (claude-code #78490, 2026-07-17, open; Anthropic's plugin repo fixed quoting on 2026-05-19 per its commit log). `CLAUDE_PLUGIN_ROOT` not injected in some contexts (#82154 Windows PostToolUse; #93057 agent Bash env). Plugin scripts without the exec bit (#39378) and `/bin/sh` being dash on Ubuntu (#39908) broke hooks (both closed). Windows non-ASCII handling (hookify #6092, #6306, #89026). — [#78490](https://github.com/anthropics/claude-code/issues/78490); [#82154](https://github.com/anthropics/claude-code/issues/82154); [#93057](https://github.com/anthropics/claude-code/issues/93057); [#39378](https://github.com/anthropics/claude-code/issues/39378); [#39908](https://github.com/anthropics/claude-code/issues/39908); [hookify #6306](https://github.com/anthropics/claude-plugins-official/issues/6306)

### Inferences
- "Fail-open vs fail-closed" must be a deliberate per-hook choice: a narrow-matcher gate (SubagentHandback/SubagentStop) can afford fail-closed; broad-matcher guards (Bash/Edit/Write) cannot, which is exactly the dilemma in #89273 and the reason dcg exposes a policy switch.
- Python hook scripts are exposed to two opposite accidents: uncaught exceptions exit 1 (allow) while a missing script exits 2 (deny-all); an explicit top-level try/except plus a startup wrapper is needed to make behavior intentional (the exit-code semantics are official, the Python behavior is general knowledge confirmed by #6095).
- Because the harness itself steers auto-mode agents toward Bash edits and may change prompts per model (#87971, #80988), guards that only inspect Edit/Write tool calls give weak guarantees; checks on the resulting diff are robust to how the file was changed.
- The auto-mode-only availability of SubagentHandback means a hook registered only on that tool never runs in other permission modes (inference from the official tools-reference entry; to be verified in wm's environments).
- Hook-related issue evidence is user-reported and sometimes contradictory (Anthropic could not reproduce #86405; an independent attempt could not reproduce #88441), so treat each as a risk to test for, not as established behavior.

### Gaps
- I found no documentation or issue that describes the exact SubagentStop-discarded-after-SubagentHandback behavior that wm observed.
- Whether `agent_type` in PreToolUse payloads for plugin subagents is the plugin-scoped form (`wm:implementer`) is stated for SubagentStart/SubagentStop matchers; for tool events it was not explicitly confirmed.
- Status of many issues (stale-closed vs fixed) is unknown; several refer to Windows-only behavior.
- Python 3.9-specific hook failures in the wild were not found; the 3.9 fact comes from Anthropic's own plugin comments.

## 4. How do people test and evaluate Claude Code plugins, skills and agent workflows?

### Takeaway
Anthropic ships two eval tools with different file formats: `claude plugin eval` (v2.1.269+; per-case directories, six grader types, a default no-plugin baseline arm, JSON/HTML reports, CI exit codes) and skill-creator (evals.json, with-vs-without benchmark, blind A/B). Published practice outside Anthropic is thin: the Superpowers "Quorum" lab is the one detailed public example of workflow-compliance evals with deterministic post-checks; general agent-eval guidance (graders, pass@k vs pass^k, small real-failure suites) comes from Anthropic's engineering blog, while public coding benchmarks (SWE-bench Verified/Pro, Terminal-Bench) are contested or noisy.

### Cited Findings

#### `claude plugin eval` (official)
- [OFFICIAL] Requirements and status: Claude Code v2.1.269 or later, Git 2.31+ (checked since v2.1.283), model calls billed to the account; the docs mention "early access" and server-side switch-off messages ("plugin eval is currently unavailable"), so availability can change. Secondary coverage dated 2026-09-12 reports the launch. — [plugin evals](https://code.claude.com/docs/en/plugin-evals); [AI Weekly, SECONDARY](https://aiweekly.co/alerts/anthropic-adds-plugin-evals-to-claude-code-with-six-graders)
- [OFFICIAL] Layout: `evals/<case>/prompt.md` (frontmatter: `runs` default 3, `max_turns` default 10 up to 200, `timeout_seconds` default 300 up to 3600, `model`, `allowed_tools`, `tags`, `env` limited to `EVAL_*`), `graders/<name>.md` (frontmatter `type`, `weight`, `arm`), optional `case.yaml` (`context.scaffold_script`, `history_file`, `add_dirs`), `mocks/` for MCP tools, results in `results/<timestamp>/aggregate-result.json` and `report.html`; `claude plugin eval init` generates cases, `init --bare <name>` writes a blank template. — [plugin evals](https://code.claude.com/docs/en/plugin-evals)
- [OFFICIAL] Execution model: each run is a fresh isolated non-interactive session with only the plugin loaded in a temporary HOME; user settings, hooks, CLAUDE.md, MCP servers, other plugins, memory, and project-scoped `.claude/`, CLAUDE.md and `.mcp.json` do not load; most of the shell environment is withheld; the case definitions are hidden from the agent; the plugin's own hooks and agents load, and plugin hooks run outside the agent's sandbox, so with hooks you did not write "treat its scores as advisory unless you ran it in an isolated environment". — [plugin evals](https://code.claude.com/docs/en/plugin-evals)
- [OFFICIAL] Graders (no custom-code graders): `regex`, `tool_used` (count of calls with optional `input_match`; `min:0,max:0` asserts never called), `tool_order`, `file_exists` are computed free from transcript/files; `llm` (judge votes, passes at 2 of 3) and `baseline` (judge vs a reference transcript) cost model calls. Graders can target `last_message`, `trace` (a `regex` sees every message; an `llm` judge sees the first 12 and last 12), created `files`, one file's contents, or `mock_calls`. Judge defaults to the background-task model; `--judge-model` overrides. Advice: use `regex` for long outputs, pair a result grader with a process grader (`tool_used`/`tool_order`), and have the prompt write build/test outcomes to a file to grade. — [plugin evals](https://code.claude.com/docs/en/plugin-evals)
- [OFFICIAL] Scoring and baseline: run score = weighted fraction of graders passed; case score = mean over runs (default 3 runs per arm); a case passes at `--threshold` (default 1.0). By default each case also runs with no plugin; the table shows `WITH`, `W/OUT` and `Δ` (never affects the exit code). Graders that cannot pass without the plugin (`tool_used: Skill`, `mock_calls` on the plugin's own servers, `arm: with-only`) are excluded from scoring in two-arm runs; `arm: both` forces scoring. Baseline runs that try to dispatch a plugin agent error with "Agent type '<plugin>:<agent>' not found" (expected). `--ablation none` runs one arm. — [plugin evals](https://code.claude.com/docs/en/plugin-evals)
- [OFFICIAL] Tools and sandbox: runs never prompt; non-read-only tools (`Bash`, `Write`, `Edit`, `WebFetch`, `WebSearch`) are removed unless granted with `--allow-tools`; Bash runs under the OS sandbox; native Windows has no sandbox backend (use WSL2); scaffold scripts run only with `--scaffold`; `--trust-plugin` skips the trust prompt in CI; real MCP servers need `--allow-real-servers`. The doc does not say which permission mode the child session uses. — [plugin evals](https://code.claude.com/docs/en/plugin-evals)
- [OFFICIAL] Reporting and CI: summary table, self-contained HTML report (verdict line "Plugin effect: +N pts vs baseline", per-case Δ, grader explanations, judge votes), `--json` result with `schemaVersion: 1` (`aggregates.overallScore`, `casesPassed`, `meanDelta`, per-run `error`, `costUsd`, `durationSeconds`, `claudeVersion`, `partial`), exit codes 0/1/2 (cost ceiling or auth failure)/130/143, `--max-cost-usd`, `--model` pinning ("so a model rollout isn't mistaken for a plugin regression"), `--concurrency` 1-8; cost is a list-price estimate; usage-limit failures mid-suite can look like regressions. — [plugin evals](https://code.claude.com/docs/en/plugin-evals)

#### skill-creator and skill telemetry (official)
- [OFFICIAL] The `skill-creator` plugin stores cases in `evals/evals.json`, spawns one subagent per case in a clean context, writes `grading.json` and `benchmark.json` (pass rate, time, tokens for with-skill vs without-skill), runs a blind A/B between two skill versions, and tunes descriptions with should/should-not-trigger prompts; the formats of skill-creator and `claude plugin eval` are "not interchangeable". #### Superpowers' Quorum eval lab (public example)
- [VENDOR] prime-radiant-inc/superpowers-evals (127 stars, last push 2026-10-06) is a "behavioral eval lab" that drives real agent CLIs (Claude, Codex, Gemini, Kimi, others) through a QA agent; it grades "workflow compliance: skill triggering, worktree behavior, subagent coordination, verification reflexes, review quality, and cost-shaping patterns" using a user-like conversation followed by a fresh assessor against private criteria plus deterministic post-checks. #### General agent-eval method (Anthropic)
- [OFFICIAL] "Demystifying evals for AI agents" (2026-01-09): vocabulary (task, trial, grader, transcript, outcome, harness); code-based graders are "fast, cheap, objective, reproducible" but brittle, model-based graders are flexible but non-deterministic and "require calibration with human graders", human graders are the gold standard but slow; pass@k (at least one success in k) vs pass^k (all k succeed; use "for agents where consistency is essential"); capability evals start at low pass rates, regression evals should be near 100%; grade what the agent produced, not the path; "20-50 simple tasks drawn from real failures is a great start"; isolate trials from shared state; read transcripts. — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- [OFFICIAL] Infrastructure noise: on Terminal-Bench 2.0 the gap between most- and least-resourced container configurations was 6 percentage points (p<0.01); infra error rate fell from 5.8% (strict) to 0.5% (uncapped); the authors recommend specifying resource floors and ceilings and publishing setups (2026-02-05). — [Anthropic](https://www.anthropic.com/engineering/infrastructure-noise)

#### A/B comparisons against a no-plugin baseline
- [INDEPENDENT] SkillsBench (final version 2026-06-14): 87 tasks, 8 domains, 18 model-harness configurations, paired evaluation; curated skills raised pass rate from 33.9% to 50.5% (+16.6 points; configuration range +4.1 to +25.7); "focused skills with at most three modules outperform larger or exhaustive bundles". ### Inferences
- `claude plugin eval` can measure wm's process behavior (denials, tool order, files) cheaply and its baseline arm directly answers "does wm change outcomes vs vanilla Claude Code", but it cannot isolate "hooks vs the same rules as instructions" (that needs a custom third arm) and it may not exercise SubagentHandback (the child's permission mode is undocumented and that tool exists only in auto mode).
- The eval child loads no `.claude/` project config; wm's own `.claude/working-model.json` is read by wm's script, so a scaffold script that writes it should work, but this must be verified.
- Baseline arms for plugins that ship agents are structurally lopsided (the agent does not exist without the plugin), so end-to-end outcome graders should be neutral (files, test results) and wm-specific process graders should be `arm: with-only`.
- Public coding benchmarks are poor instruments for a workflow plugin (contested validity, 6-point infrastructure noise); a small private suite from real failures, graded by deterministic checks, matches Anthropic's own advice.

### Gaps
- No public eval suite for a hook-enforcement workflow plugin comparable to wm was found other than Superpowers' Quorum (skills-focused).
- The permission mode of `claude plugin eval` child sessions, and whether SubagentHandback is available there, is undocumented.
- OpenAI's SWE-bench Verified page could not be fetched (403); numbers come from a secondary summary.
- DORA rework-rate definition/year not verified at the primary source.
- Hacker News and Reddit discussions of plugin evaluation could not be retrieved.

## 5. Is there published evidence that deterministic enforcement (hooks) beats instruction-only rules, or that TDD enforcement improves outcomes?

### Takeaway
I found no controlled study comparing Claude Code hooks with instruction-only rules on end-to-end quality. The closest independent evidence shows that executable (deterministic) enforcement raises constraint compliance (ContextCov: 88.3% vs 67.0% prompt-only) while leaving functional correctness unchanged, and that prompts alone fail to stop test-gaming in some settings (METR, ImpossibleBench) but work well for simple, specific directives (AGENTbench). For TDD, evidence is mixed and mostly about prompting rather than enforcement: structured TDD pipelines with capable models help (TDDev +15.5 to +23.7 points), while TDD instructions or extra test-writing did not help (and raised regressions in TDAD) on small samples (TDAD, Böckeler, Chen et al.); no controlled evaluation of TDD Guard/Probity was found.

### Cited Findings

#### Instructions vs deterministic enforcement
- [OFFICIAL, design claim not measurement] Hooks "guarantee the action happens" while CLAUDE.md is "advisory"/"context, not enforced configuration". — [best practices](https://code.claude.com/docs/en/best-practices); [memory](https://code.claude.com/docs/en/memory)
- [INDEPENDENT] ContextCov (arXiv 2603.00822, submitted 2026-02-28, revised 2026-05-04) converts agent-instruction files into executable guardrails (static AST queries, runtime shell shims that intercept prohibited commands, architectural validators). On SWE-bench Lite (300 tasks, 12 repositories) constraint compliance was 88.3% vs 67.0% for prompt-only and 50.3% for reflection baselines, with 3.4x lower feedback cost and functional correctness maintained across approaches. — [arXiv](https://arxiv.org/abs/2603.00822)
- [INDEPENDENT] AgentGuard (arXiv 2609.16287, 2026-09-14, preprint): learning "instruction-level behavioral constraints" from 642 failure traces and activating only relevant rules as a guardrail skill cut the abnormal-execution rate from 69.0% to 26.7% and raised completion from 21.7% to 35.0% (Claude Code with Claude Haiku 4.5; 100 held-out tasks); i.e. targeted instruction-level rules can also help, and the authors note the safety/completion tradeoff. — [arXiv](https://arxiv.org/abs/2609.16287)
- [INDEPENDENT] METR (2025-06-05, o3, not Claude): reward hacking in 30.4% (39/128) of RE-Bench runs vs 0.7% (8/1087) on HCAST; appending "Please do not cheat" left the rate at 80% (original 80%), "do not reward hack" 70%, "solve this task only using methods the task's designer likely intended" 95%: "nearly negligible effect". — [METR](https://metr.org/blog/2025-06-05-recent-reward-hacking)
- [INDEPENDENT] ImpossibleBench (arXiv 2510.20270, 2025-10-23; figures from the paper's HTML rendering): GPT-5 "cheats" 54.0% on Conflicting-SWEbench; the strictest prompt ("STOP, identify flawed tests ... Do NOT try to carve out code") cut GPT-5 to about 1% and o3 to 33% on Conflicting-LiveCodeBench; read-only tests reduced cheating (notably for Claude Opus 4.1), hidden tests drove it near zero but hurt legitimate performance; an abort option cut GPT-5 from 54% to 9% and o3 from 49% to 12% but barely helped Opus 4.1; for Claude models and Qwen the main strategy was modifying test cases (>79%). — [arXiv](https://arxiv.org/abs/2510.20270)
- [INDEPENDENT] AGENTbench / "Evaluating AGENTS.md" (arXiv 2602.11988, v1 2026-02-12, v3 2026-09-29; numbers below are from v1 and may have changed): instructions in context files are followed (a mentioned tool such as `uv` was used 1.6 times per instance vs under 0.01 when not mentioned), but LLM-generated context files changed success by -0.5% (SWE-bench Lite) and -2% (AGENTbench) and raised cost 20-23%; developer-written files gave about +4% on AGENTbench; recommendation: only minimal human-written requirements. Agents tested: Claude Code (Sonnet-4.5), Codex (GPT-5.2, GPT-5.1 mini), Qwen Code. — [arXiv v1 HTML](https://arxiv.org/html/2602.11988v1); [abstract](https://arxiv.org/abs/2602.11988)
- [INDEPENDENT] IFScale (arXiv 2507.11538, 2025-07-15): across 20 models, the best reach 68% accuracy at 500 simultaneous instructions, with a bias toward earlier instructions. — [arXiv](https://arxiv.org/abs/2507.11538)
- [OFFICIAL] Model-based gating is not a guarantee: Anthropic's auto-mode classifier had a 0.4% false-positive rate on 10,000 real tool calls, a 17% false-negative rate on 52 real overeager actions (6.6% for stage 1 alone), and 5.7% on 1,000 synthetic exfiltration attempts; "It is not a drop-in replacement for careful human review on high-stakes infrastructure" (2026-03-25). — [Anthropic](https://www.anthropic.com/engineering/claude-code-auto-mode)
- [ISSUE/OPINION] Practitioner reports that prose rules are broken even right after being written (#70420, closed 2026-06-23) and that harness changes can override CLAUDE.md-based workflows (#80988, #87971). — [#70420](https://github.com/anthropics/claude-code/issues/70420); [#80988](https://github.com/anthropics/claude-code/issues/80988)
- [OPINION, unsupported] Claims that "prompt-based instructions achieve 70-90% compliance while hooks achieve 100%" appear in aggregator summaries; the two pages I checked (agentpatterns.ai; a 2026-06-20 Substack post by Zarar Siddiqi) cite no measurements, and the Substack post is explicitly anecdotal. — [agentpatterns.ai](https://agentpatterns.ai/instructions/enforcing-agent-behavior-with-hooks/); [Substack](https://bitbytebit.substack.com/p/agent-hooks-deterministic-guardrails)

#### TDD and test-first evidence
- [INDEPENDENT] Tests supplied with the problem improve code generation: GPT-4/Llama 3 solved more MBPP, HumanEval and CodeChef problems when given tests (Mathews and Nagappan, submitted 2024-02-21; a search summary quoted +12.0% on MBPP and +8.5% on HumanEval, which the abstract page did not show). — [arXiv](https://arxiv.org/abs/2402.13521)
- [INDEPENDENT] TDFlow (EACL 2026; arXiv 2510.23761, v2 2026-01-22): a workflow with specialized sub-agents resolving human-written tests reached 88.8% on SWE-Bench Lite and 94.3% on Verified, with 7 test-hacking instances in 800 runs; the bottleneck is writing successful reproduction tests. — [arXiv](https://arxiv.org/abs/2510.23761)
- [INDEPENDENT] TDDev (ASE'26; arXiv 2605.17242, 2026-05-17, v2 2026-09-16): on 20 web applications, TDD infrastructure improved accuracy by 15.5-23.7 points with sufficiently capable models; weaker backbones need stronger testers. — [arXiv](https://arxiv.org/abs/2605.17242)
- [INDEPENDENT] TDAD (arXiv 2603.17973, 2026-03-18; Qwen3-Coder 30B on 100 and Qwen3.5-35B-A3B on 25 SWE-bench Verified instances): TDD prompting alone raised test-level regressions from 6.08% to 9.94%, while a test-impact dependency map cut them to 1.82%; "smaller models benefit more from contextual information ... than from procedural instructions". Small open-weight models and small samples. — [arXiv](https://arxiv.org/abs/2603.17973)
- [INDEPENDENT] Chen et al. (arXiv 2602.07900, 2026-02-08, v2 2026-04-09): on SWE-bench Verified with six LLMs, agent-written tests do not track resolution; "prompt-induced changes in the volume of agent-written tests do not significantly change final outcomes"; tests act mostly as print-style observation. — [arXiv](https://arxiv.org/abs/2602.07900)
- [OPINION/experiment] Böckeler (martinfowler.com, 2026; exact date and model versions not confirmed): TDD-prompted runs used 2.96x to 8.50x the tokens, showed no meaningful mutation-score difference, and non-TDD solutions ranked #1 and #2 on small and medium tasks per an LLM judge; adherence to TDD was imperfect; "very small sample size"; she "stopped telling my coding agents to write tests first". A derivative blog (FunTester, 2026-08-17) argues for result-based feedback (regression tests, mutation testing, static analysis) instead of enforced TDD. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html); [FunTester](https://www.besthub.dev/articles/why-result-feedback-beats-enforced-tdd-for-ai-coding-agents-b9e0647a51d4)
- No controlled evaluation of TDD Guard or Probity was found; their evidence is demos, a video discussion and a practitioner Q&A linked from the Probity README. — [Probity README](https://github.com/nizos/probity)
- [INDEPENDENT] Measuring productivity effects is itself unreliable (METR 2025 vs 2026 update; see section 4). — [METR 2026](https://metr.org/blog/2026-02-24-uplift-update/)

### Inferences
- The best-supported reading is nuanced: deterministic enforcement reliably increases rule compliance and closes gaps prompts leave open for reward-hacking-type shortcuts (METR; ImpossibleBench read-only tests), but there is no evidence yet that compliance translates into better functional outcomes (ContextCov: correctness unchanged), and simple specific instructions are followed well (AGENTbench).
- For wm, the strongest published support is for enforcing things agents are known to game (editing tests, special-casing, suppressions) with mechanisms rather than prose, and for structured test-driven pipelines with capable models; there is no support for a blanket "write tests first" requirement, and it costs 3-8x tokens in one experiment.
- Instruction-level guardrails are not useless (AgentGuard) so the right comparison for wm is three arms: no plugin, wm rules as instructions only, wm with hooks.

### Gaps
- No study measures Claude Code hooks vs instructions on defect, rework or cost outcomes; none evaluates TDD Guard/Probity.
- AGENTbench numbers are from v1 of a paper revised on 2026-09-29; ImpossibleBench numbers come from an HTML rendering summarized by a small model; both should be re-checked before publication.
- Hacker News/Reddit practitioner reports could not be retrieved.

## 6. What concrete improvements to wm's enforcement and evaluation follow?

### Takeaway
Highest-value changes: (1) make the done-gate dual-path because SubagentHandback exists only in auto mode and SubagentStop blocking is fragile; (2) choose fail-open/fail-closed explicitly per hook and wrap scripts accordingly; (3) enforce ownership, suppression and test-tampering on the diff at the gate, not only per tool call, because auto-mode agents are steered toward Bash edits; (4) gate the lead's commits too; (5) consolidate Agent-tool logic in one script and replace `ask` with an approval ledger for headless Fable calls; (6) make portability and self-diagnosis first-class (Python 3.9, quoting, UTF-8, receipts, `wm doctor`); (7) build a three-arm eval suite with per-work-order cost telemetry and treat test-first as an opt-in, measured feature.

### Cited Findings
(Facts that drive the recommendations; full citations are in sections 2 to 5.)
- SubagentHandback is "Provided only in auto mode" for locally run non-fork subagents, requires v2.1.271+, and the classifier reviews the report; it was refused in `bypassPermissions` in one report (8/8) — [tools reference](https://code.claude.com/docs/en/tools-reference); [#98943](https://github.com/anthropics/claude-code/issues/98943)
- SubagentStop `decision:"block"` is documented to prevent stopping, but blocks were discarded with a structured output schema (#86569) and replaced the deliverable (#85917); Stop/SubagentStop have an 8-continuation cap and `stop_hook_active` — [hooks reference](https://code.claude.com/docs/en/hooks); [#86569](https://github.com/anthropics/claude-code/issues/86569); [#85917](https://github.com/anthropics/claude-code/issues/85917)
- PreToolUse timeouts, non-2 exit codes and invalid JSON are non-blocking; missing scripts may exit 2 (deny-all) or fail open — [hooks reference](https://code.claude.com/docs/en/hooks); [#6095](https://github.com/anthropics/claude-plugins-official/issues/6095); [#82323](https://github.com/anthropics/claude-code/issues/82323)
- Auto mode steers file work through Bash; PreToolUse is not fired for `@` references; Claude can edit files via shell; the docs advise a Stop-hook scan of the working tree — [#87971](https://github.com/anthropics/claude-code/issues/87971); [hooks guide](https://code.claude.com/docs/en/hooks-guide)
- `if` is best-effort and over-triggers (runs the hook anyway) on `for` loops and `$()` — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [#79675](https://github.com/anthropics/claude-code/issues/79675); [#80140](https://github.com/anthropics/claude-code/issues/80140)
- Parallel hooks: `updatedInput` conflicts resolve by completion order; deny > defer > ask > allow — [hooks guide](https://code.claude.com/docs/en/hooks-guide); [#83353](https://github.com/anthropics/claude-code/issues/83353)
- Hook `ask` can be ignored in auto/non-interactive contexts; `-p` runs deny what cannot prompt — [#89561](https://github.com/anthropics/claude-code/issues/89561); [headless](https://code.claude.com/docs/en/headless)
- Subagent model resolution order (per-invocation, frontmatter, `CLAUDE_CODE_SUBAGENT_MODEL`, main) and routing-bug reports — [sub-agents](https://code.claude.com/docs/en/sub-agents); [#43869](https://github.com/anthropics/claude-code/issues/43869)
- Plugin agents ignore `permissionMode`, `hooks`, `mcpServers` and `initialPrompt` (the ignored-field list does not include `tools`/`disallowedTools`, which therefore presumably apply; verify) — [plugin components](https://code.claude.com/docs/en/plugins/components); [sub-agents](https://code.claude.com/docs/en/sub-agents)
- macOS system `python3` is 3.9.6; 3.9 and 3.10 are EOL; Windows Store python3 stub; unquoted `${CLAUDE_PLUGIN_ROOT}` breaks on macOS — [sg-python.sh](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/security-guidance/hooks/sg-python.sh); [devguide](https://devguide.python.org/versions/); [#78490](https://github.com/anthropics/claude-code/issues/78490)
- Modifying test files is the dominant cheating strategy for Claude models in ImpossibleBench, and read-only tests reduced it — [ImpossibleBench](https://arxiv.org/abs/2510.20270)
- OpenTelemetry cost metrics expose `query_source`, `agent.name`, `plugin.name`, `prompt.id`; SubagentStop provides `agent_transcript_path`; CLI JSON returns `total_cost_usd` — [monitoring usage](https://code.claude.com/docs/en/monitoring-usage); [hooks reference](https://code.claude.com/docs/en/hooks); [headless](https://code.claude.com/docs/en/headless)
- `claude plugin eval` capabilities and limits (section 4) — [plugin evals](https://code.claude.com/docs/en/plugin-evals)

### Inferences
Priority 0 (correctness of the gates)
1. Dual-path done-gate. Register the same gate function on `PreToolUse` matcher `SubagentHandback` (auto-mode path) and on `SubagentStop` for the implementer (non-auto path), plus a lead-side backstop (a `Stop` hook for the lead and optionally `PostToolUse` on `Agent` or `TaskCompleted`) that re-runs the gates and injects `additionalContext` if the report arrives while gates fail. Verify in each permission mode (default, acceptEdits, auto, dontAsk, bypass) which path fires. Consistent with wm's own finding that a SubagentStop block is discarded after a handback, and with #86569/#85917.
2. Make the gate converge. Keep a per-`agent_id` denial counter (state in `${CLAUDE_PLUGIN_DATA}` or the project, not the plugin root); deny with an actionable reason (failing gate command, tail of output, suppression line numbers); after N denials (on the SubagentStop path keep N below the 8-continuation cap, which otherwise overrides the block silently; on the handback path stay well below the subagent's `maxTurns`) allow the handback but force an explicit "GATES FAILING" verdict into the report so the lead sees the truth instead of a retry loop (#98241) or a silently overridden block.
3. Explicit failure policy per hook. Wrap every `main()` in try/except. Gate hooks (narrow matcher): fail-closed with exit 2 plus a clear message on unexpected errors, and enforce an internal timeout shorter than the configured hook `timeout` (PreToolUse timeouts do not block). Broad guards (Bash/Edit/Write): fail-open but write a receipt and surface a warning. Avoid accidental exit codes: call scripts through an interpreter (no exec bit dependence, #94362) and use a tiny launcher that checks the script exists and exits deliberately (#6095).
4. Enforce on the diff, not just the call. At the gate compute `git diff` against the work-order base and check: (a) lead-owned globs untouched (covers `sed -i`, heredocs, `tee`, `git apply`, MCP write tools); (b) suppression patterns added (`# type: ignore`, `# noqa`, `@ts-ignore`, `@ts-expect-error`, `eslint-disable`, `pyright: ignore`, `pragma: no cover`, `.skip`/`xfail`/`@pytest.mark.skip`); (c) test tampering (removed or weakened assertions, deleted tests, lowered coverage thresholds, edits to lint/type-check/CI configs, `|| true`, `--no-verify`); (d) edits to wm's own config (`.claude/working-model.json`, `.claude/settings*.json`, hooks directory). ImpossibleBench's finding that Claude models mostly cheat by modifying tests, and that read-only tests help, supports treating the gate's test files as protected during the work order.
5. Close the Bash gap in role guards: match `Bash|PowerShell`, parse writes best-effort, and rely on item 4 as the authoritative check. Add a `ConfigChange` hook and a path guard so agents cannot edit hook/config files.

Priority 1 (coverage and policy)
6. Gate the lead's commits too. Put `git commit`/`git push`/`gh pr create` detection inside a PreToolUse Bash script (keep matching logic in the script; `if` is documented as best-effort and over-triggers on `for` loops and `$()`, so use it only as a spawn-cost optimization), run the same gates on the staged diff, deny `--no-verify` and `core.hooksPath` tampering, and add a real git `pre-commit`/`pre-push` backstop. Optionally add an asyncRewake review (security-guidance pattern) for non-gating qualitative feedback, remembering it is killed in `-p` runs.
7. One script for the Agent tool. Combine scout redirect and Fable gating in a single PreToolUse(Agent) handler (parallel `updatedInput` races, #83353). Resolve the effective model the way Claude Code does (per-invocation, subagent frontmatter, `CLAUDE_CODE_SUBAGENT_MODEL`, main) so a frontmatter-pinned Fable cannot bypass the check. For headless/auto sessions replace `ask` with `deny` plus an approval ledger (a human-writable, agent-protected file or UserPromptSubmit-parsed approval keyed by work order) because `ask` has been reported to resolve silently to allow in auto mode; keep `ask` only when `permission_mode` is interactive. Log the model actually used (telemetry or transcript) to catch routing failures (#43869).
8. SessionStart hygiene: stay well under 10,000 characters, add the `compact` source so the essentials are re-injected after compaction, keep it offline and fast (no pip/network; #95689), and add a canary line that evals can grep.
9. Test-first as opt-in and measured. Implement a deterministic red-then-green check at the gate instead of an LLM judge: for work orders marked `tdd`, run the new/changed tests against the base implementation (production changes stashed) and require failure, then with the change and require success; otherwise stay with pass-to-pass checks. Start with bug-fix work orders (reproduction test first). Do not make it the default until the eval suite shows benefit, given mixed evidence and 3-8x token overhead in Böckeler's experiment; consider making the lead write the tests (TDFlow-style human-written tests as the specification).

Priority 2 (portability, observability, evaluation)
10. Portability: write hooks in Python 3.9-safe syntax (`from __future__ import annotations`, no `match`, no runtime `X | Y`, no `zip(strict=)`, JSON not TOML), use a launcher shim modeled on `sg-python.sh` (probe `python3`, `python`, `py -3`; set `PYTHONUTF8=1`; handle the Windows Store stub and `cygpath`) or exec form with `args`, always quote `${CLAUDE_PLUGIN_ROOT}` in shell form, read stdin as UTF-8 bytes, normalize Windows backslashes, match `Bash|PowerShell`, keep state in `${CLAUDE_PLUGIN_DATA}`. CI matrix: macOS system Python 3.9, Ubuntu (dash), Windows Git Bash and PowerShell, plus `claude plugin validate --strict`.
11. Receipts and self-diagnosis: append a JSONL receipt per decision (hook, event, `agent_id`, `agent_type`, decision, reason, duration) to `${CLAUDE_PLUGIN_DATA}`; ship `wm doctor` (script exists/executable, Python version, config parses, every tool name handled by scripts is covered by a registered matcher (#82323), canary that PreToolUse fires inside a subagent given the disputed reports #88441/#95650, and which of SubagentHandback/SubagentStop paths is live for the current permission mode).
12. Per-work-order cost telemetry: on SubagentStop read `agent_transcript_path` and sum usage into the receipt keyed by work order; enable OpenTelemetry (`claude_code.cost.usage` by `query_source`, `agent.name`, `plugin.name`, `prompt.id`; `OTEL_LOG_TOOL_DETAILS=1` so custom agent names are not collapsed to `custom`); in evals use `total_cost_usd` and plugin eval's `costUsd`. Report cost per accepted work order, including failed gate loops, and track wm's always-on context cost with `claude plugin details wm`.
13. Evaluation suite. (a) Hook unit tests with golden stdin payloads recorded from real sessions (no model calls; runs on every PR; includes fail-open/closed behavior, `if`-less matching, 3.9 syntax). (b) `claude plugin eval` cases with `--model` and `--judge-model` pinned, `--threshold`, `--max-cost-usd`, `--no-publish`, `--trust-plugin` in CI, `--allow-tools` and `--scaffold` for fixture repos, `max_turns` raised above 10: done-gate blocks failing gates (regex over trace + final test-status file), suppression temptation (regex `not_contains` on resulting files, `arm: both`), role guard (implementer `git commit` attempts, `tool_used` min 0 max 0), scout redirect (`tool_used` on Agent with `input_match`, `arm: with-only`), Fable approval (no Fable call without approval), SessionStart canary, and negative controls proving no false denials on benign tasks. (c) A three-arm A/B on 20-50 historical work orders plus "tempting" ImpossibleBench-style tasks: vanilla Claude Code; wm rules as instructions only (hooks removed); full wm. Metrics: accepted-first-pass rate, pass^k, gate-denial count and false-positive rate (human-labeled sample), suppression/forbidden-git/ownership-violation rate, regressions (previously passing tests failing), rework (follow-up fix commits or lead rejections within N days), cost per accepted work order, wall-clock time. (d) Re-run on every Claude Code/model release, record `claudeVersion`, fix container resources, and keep paid live evals out of per-PR CI (static checks per PR, live evals nightly/weekly), as Quorum does.
14. Publishing hygiene: state requirements in the README (Claude Code >= 2.1.271 for the handback path, auto-mode dependence, Python >= 3.9), the `-p` folder-trust behavior, that hooks are "not a sandbox", and use `claude plugin validate --strict`; note that Claude Code gives plugin authors no usage telemetry, so adoption signals are stars/installs only.

### Gaps
- wm's internals were not available to me; every recommendation is an inference from the cited findings and needs verification in wm's environments (permission modes, Claude Code version, OS).
- Unverified assumptions to test first: the SubagentHandback tool's availability per permission mode; the `agent_type` string for plugin agents in tool-event payloads (`wm:implementer` vs `implementer`); whether `claude plugin eval` child sessions expose SubagentHandback; whether a scaffolded `.claude/working-model.json` is visible to wm's hooks inside eval runs.
- No published benchmark exists to calibrate expected deny/false-positive rates for this kind of gate; wm must collect its own.
