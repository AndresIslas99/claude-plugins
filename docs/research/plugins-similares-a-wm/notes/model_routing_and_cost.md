# Model routing and cost practices inside Claude Code (state as of 6 October 2026)

> Evidence tags used below. [OFFICIAL] = Anthropic documentation, blog or announcement. [VENDOR-MEASURED] = a measurement Anthropic ran itself (directional, Anthropic says "not guarantees"). [INDEPENDENT] = measured by a third party. [OPINION] = practitioner opinion or anecdote. [UNVERIFIED] = asserted without method. [SECONDARY] = reported by an outlet quoting someone else. Dates are publication dates or Claude Code version dates. Everything was fetched on 2026-10-06 (the changelog's newest entry is v2.1.292, dated 2026-10-06). Claude Code and platform docs pages were read as raw markdown or verbatim page text, and blog, announcement and system-card quotes were checked against the raw page or PDF text; sources that could only be read through a summarizing fetch are flagged in the bullet. Model names, prices and Claude Code behavior in this area changed several times between July and October 2026; anything dated before September 2026 may be outdated.

## Q1. What model-routing mechanisms does Claude Code offer today (opusplan, aliases, frontmatter model and effort, CLAUDE_CODE_SUBAGENT_MODEL, modelSettings, fast mode, /model mid-session and caching, effort and its cost)?

### Takeaway
`opusplan` still exists and now resolves to Opus 5.5 for planning and Sonnet 5.5 for execution. Claude Code also offers per-subagent `model`, `effort`, `maxTurns`, `omitClaudeMd` and `experimental.cacheTtl` frontmatter (supported for plugin agents), a per-spawn `model` parameter and, since v2.1.292 (2026-10-06), a per-spawn `effort` parameter, `CLAUDE_CODE_SUBAGENT_MODEL` (a default only since v2.1.251, with a `_FORCE` switch since v2.1.257), per-model `modelSettings`, a native advisor tool, fast mode (Opus only) and fallback chains. Prompt caches are per model, so any model switch is a cold-cache event, while effort changes on the 5.5 models keep the cache.

**Aliases and defaults**
- [OFFICIAL] Aliases: `default` clears any override and resolves to the account default, which is Opus 5.5 on Pro, Max, Team, Enterprise and the Anthropic API; `best` uses the `fable` alias where available, otherwise `opus`; `fable` resolves to Fable 5.1 (Fable 5 in the Claude apps gateway); `sonnet` and `opus` resolve to the latest versions; `haiku`; `sonnet[1m]`, `opus[1m]`; and `opusplan`. "Aliases point to the recommended version for your provider and update over time. To pin to a specific version, use the full model name." — [Model configuration](https://code.claude.com/docs/en/model-config)
- [OFFICIAL] Alias resolution differs by provider. Anthropic API: opus = Opus 5.5, sonnet = Sonnet 5.5. Claude Platform on AWS: Opus 5.5, Sonnet 4.6. Amazon Bedrock and Google Cloud Agent Platform: Opus 5.5, Sonnet 4.5. Microsoft Foundry: Opus 4.6, Sonnet 4.5. — [Model configuration](https://code.claude.com/docs/en/model-config)
- [OFFICIAL] Version floors: Opus 5.5 needs v2.1.280, Sonnet 5.5 needs v2.1.284, Fable 5.1 needs v2.1.257, per-model `modelSettings` needs v2.1.288, `ANTHROPIC_DEFAULT_MODEL` needs v2.1.236. Before v2.1.280 `default` resolved to Sonnet 5 on Pro and Team Standard and to Opus 5 on Max and others. — [Model configuration](https://code.claude.com/docs/en/model-config)
- [OFFICIAL] Fable is never the account default; select it explicitly. Depending on plan and seat tier, Fable usage can bill to usage credits, with a consent prompt in interactive sessions (non-interactive `-p` bills without asking). — [Model configuration](https://code.claude.com/docs/en/model-config)

**opusplan**
- [OFFICIAL] "`opusplan` ... In plan mode: uses `opus` for complex reasoning and architecture decisions. In execution mode: automatically switches to `sonnet` for code generation and implementation." `opusplan[1m]` needs v2.1.265. A changelog entry for v2.1.287 (2026-10-01) fixes "switching between Opus 5.5 and Sonnet 5.5 (`/model`, `opusplan`)", which confirms it works with the 5.5 pair. — [Model configuration](https://code.claude.com/docs/en/model-config), [Changelog](https://code.claude.com/docs/en/changelog)
- [OFFICIAL] "The `opusplan` model setting resolves to Opus during plan mode and Sonnet during execution, so each plan-mode toggle is a model switch and starts a fresh cache." Anthropic's own table compares four mechanisms: the advisor tool (stronger model "at decision points mid-task", started by Claude), `opusplan` (stronger model during plan mode), subagents with `model` set (stronger model "for the entire delegated subtask"), and `/model` (from the next request onward). — [Prompt caching](https://code.claude.com/docs/en/prompt-caching), [Advisor](https://code.claude.com/docs/en/advisor)

**Subagent model resolution**
- [OFFICIAL] Order: (1) the per-invocation `model` parameter, (2) the subagent definition's `model` frontmatter (`inherit` = main model), (3) `CLAUDE_CODE_SUBAGENT_MODEL`, (4) the main conversation's model. A family alias (for example `opus`) in (1) or (2) resolves to the main conversation's exact model, including `[1m]`, when the main model is in that family; an alias in `CLAUDE_CODE_SUBAGENT_MODEL` always resolves to the version the alias points to. — [Sub-agents](https://code.claude.com/docs/en/sub-agents)
- [OFFICIAL] History: before v2.1.251 (2026-08-28) the variable "came first in this order and overrode both the per-invocation parameter and the frontmatter"; v2.1.251 "Changed `CLAUDE_CODE_SUBAGENT_MODEL` to set the default subagent model rather than override everything". `CLAUDE_CODE_SUBAGENT_MODEL_FORCE=1` (v2.1.257, 2026-09-01) restores override-everything: the `model` field in agent definitions is ignored and Claude "can't pass a model when it starts a subagent"; forks and skills with `model: inherit` still run on the main model. — [Sub-agents](https://code.claude.com/docs/en/sub-agents), [Changelog](https://code.claude.com/docs/en/changelog)
- [OFFICIAL] "Setting `CLAUDE_CODE_SUBAGENT_MODEL` by itself doesn't change the model the built-in Explore and Plan subagents run on." Plan "inherits from the main conversation". `general-purpose` uses the variable if set and nothing else assigns a model, otherwise the main model. `/tasks` shows the model (and effort, when set by frontmatter) on each subagent row (v2.1.242+). — [Sub-agents](https://code.claude.com/docs/en/sub-agents)
- [OFFICIAL] Explore history: v2.0.17 (2025-10-15) "Introducing the Explore subagent. Powered by Haiku"; v2.1.198 (2026-07-01) "The built-in Explore agent now inherits the main session's model (capped at opus) instead of running on haiku". Current docs: Explore runs on the main model, or on the `opus` alias if the main model is Fable (subscription, Console or `ANTHROPIC_BASE_URL` gateway). "A user or project subagent named `Explore` overrides the built-in and keeps its own `model` field, so define one with `model: haiku`." — [Changelog](https://code.claude.com/docs/en/changelog), [Sub-agents](https://code.claude.com/docs/en/sub-agents)
- [OFFICIAL] Built-ins can be blocked with `permissions.deny: ["Agent(Explore)"]` (or `--disallowedTools "Agent(Explore)"`); `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1` (v2.1.198+) removes Explore and Plan so Claude explores directly. Other built-ins: `claude-code-guide` runs on Haiku, `statusline-setup` on Sonnet. — [Sub-agents](https://code.claude.com/docs/en/sub-agents)
- [OFFICIAL] Subagents inherit the main conversation's extended-thinking setting (v2.1.198) and there is "no per-subagent thinking setting". Subagents inherit the configured advisor and the pairing check runs against the subagent's own model. — [Sub-agents](https://code.claude.com/docs/en/sub-agents), [Advisor](https://code.claude.com/docs/en/advisor)

**Subagent frontmatter (including for plugin agents)**
- [OFFICIAL] Fields: `name`, `description`, `model` (alias, full ID or `inherit`), `tools`, `disallowedTools`, `permissionMode`, `maxTurns` (output marked partial at the limit, resumable), `skills`, `mcpServers`, `hooks`, `memory`, `background`, `omitClaudeMd` (v2.1.271), `effort` (low, medium, high, xhigh, max), `isolation: worktree`, `initialPrompt`, `experimental.cacheTtl` ("5m" or "1h", v2.1.248). For plugin subagents, `hooks`, `mcpServers`, `permissionMode` (and `initialPrompt`) are ignored; plugin agents are named `<plugin>:<name>`. `effort`, `maxTurns` and `disallowedTools` were added for plugin-shipped agents in v2.1.78 (2026-03-17). — [Sub-agents](https://code.claude.com/docs/en/sub-agents), [Changelog](https://code.claude.com/docs/en/changelog)
- [OFFICIAL] What a non-fork subagent loads at start: its own system prompt plus environment details, the delegation message, all CLAUDE.md levels (skipped by Explore and Plan, or by `omitClaudeMd: true`), a git-status snapshot (skipped only by Explore and Plan), preloaded skills, and a sibling roster. No conversation history. Combined descriptions of non-built-in subagents over 15,000 tokens trigger a startup warning. — [Sub-agents](https://code.claude.com/docs/en/sub-agents)
- [OFFICIAL] Frontmatter `effort` "Overrides the session effort level, but not the `CLAUDE_CODE_EFFORT_LEVEL` environment variable"; `maxEffortLevel` or an organization cap still limits it. v2.1.292 (2026-10-06): "Added an `effort` parameter to the Agent tool, so Claude runs a sub-agent at the effort level you ask for". The sub-agents page as fetched did not yet describe this parameter. — [Model configuration](https://code.claude.com/docs/en/model-config), [Changelog](https://code.claude.com/docs/en/changelog)
- [OPINION/FEATURE REQUEST] A user-filed request for a subagent-scoped effort environment variable (`CLAUDE_CODE_SUBAGENT_EFFORT`) was opened 2026-07-19 (v2.1.215) and was still open on 2026-10-06; the reporter states that frontmatter `effort` is the only per-subagent control and that the file-less built-in subagents inherit the session effort. — [GitHub issue 79135](https://github.com/anthropics/claude-code/issues/79135)

**Effort levels and defaults**
- [OFFICIAL] Levels low, medium, high, xhigh, max exist on Fable 5.1, Opus 5.5, Sonnet 5.5, Opus 5, Sonnet 5, Opus 4.8, Opus 4.7. Haiku has none. Defaults in Claude Code: Opus 5.5 and Sonnet 5.5 `medium`; Fable 5.1 `high`; Opus 4.7 `xhigh`; others `high`. On the raw API Sonnet 5.5 defaults to `high`. "The effort scale is calibrated per model, so the same level name does not represent the same underlying value across models." — [Model configuration](https://code.claude.com/docs/en/model-config), [Models overview](https://platform.claude.com/docs/en/models/overview), [Sonnet 5.5 guide, 2026-09-28](https://claude.dev/blog/building-with-claude-sonnet-5-5/)
- [OFFICIAL] Resolution order: explicit choice (`CLAUDE_CODE_EFFORT_LEVEL`, `--effort`, `/effort`), then settings (a per-model level in `modelSettings` or `effortLevel`), then the model default. `modelSettings` (v2.1.288+) keeps a saved effort level or auto-compact window per model, or caps one model's effort. A top-level `effortLevel` in user settings "doesn't count for Opus 5.5". `max` applies to the current session only unless set by environment variable. — [Model configuration](https://code.claude.com/docs/en/model-config), [Settings reference](https://code.claude.com/docs/en/settings-reference)
- [OFFICIAL] Per-level guidance: low "Quick exchanges where you review each result"; medium "default on Opus 5.5 and Sonnet 5.5 ... day-to-day engineering work with a clear scope, such as implementing a new feature"; high "Work where verification matters or edge cases are likely, such as fixing a bug in an existing codebase"; max "may show diminishing returns and is prone to overthinking, so test before adopting it broadly". "Opus 5.5 at `medium` matches or exceeds Opus 5 at `high` on coding and knowledge-work evaluations." — [Model configuration](https://code.claude.com/docs/en/model-config)

**Effort and cost (measured)**
- [VENDOR-MEASURED] Opus 5.5 on Anthropic's 478-problem SWE-bench Pro subset (runs 2026-09-19/20, not comparable to the public leaderboard): measured against `high`, `medium` scored about 2.5 points lower for about 70% of the cost, `low` about 8 points lower for about one third of the cost, `xhigh` about 1.4 points higher for 2.5 times the cost. "Long-horizon coding is where effort genuinely buys accuracy." On research and knowledge-work benchmarks (Fable 5) `low` gave up 1 to 3 points for a third to a half off cost and the default bought nothing over `medium`. — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)
- [VENDOR-MEASURED] Escalate-on-failure policy on Opus 5.5 (SWE-bench Pro subset): run all tasks at `low` (13% fail), re-run the failures at `high`: about 97% solved for about $0.17 per task, versus 95.3% for $0.29 with everything at `high`; starting at `medium` gave about 97% for about $0.24. Conditions: a failure signal such as tests, and double wall-clock time on failures. — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)
- [INDEPENDENT] Artificial Analysis Intelligence Index (a composite of 10 evals, not coding-only; values extracted from the page data on 2026-10-06, models run with "Default Fallback"): Opus 5.5 medium 51.2 at $1,627 to run the index (205 s per task); high 53.6 at $2,172 (282 s); xhigh 56.0 at $4,057 (509 s); max 57.6 at $8,708 (782 s). Fable 5.1 high 51.2 at $5,242; xhigh 53.2 at $9,063; max 53.4 at $13,129. Sonnet 5.5 xhigh 51.9 at $2,748; max 56.0 at $9,074 (942 s per task). Output tokens for the max runs: Sonnet 5.5 416M vs Opus 5.5 260M. — [AA: Opus 5.5 vs Sonnet 5.5](https://artificialanalysis.ai/models/comparisons/claude-opus-5-5-vs-claude-sonnet-5-5), [AA: Fable 5.1 vs Opus 5.5](https://artificialanalysis.ai/models/comparisons/claude-fable-5-1-vs-claude-opus-5-5)
- [OFFICIAL] Thinking is billed as output. A Claude Code blog post puts a rough price on effort: "say high adds 20K thinking tokens across a task. On Opus 5.5 that's $0.40. A retry loop of ten turns at 100K of cached context, with 10K output tokens in total, costs about the same. So high pays for itself on a task where it saves one retry." (2026-09-25) — [What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)
- [OFFICIAL] Sonnet 5.5 "at low effort ... sometimes skips a check that exercises the change"; Anthropic supplies a system-prompt paragraph that requires a real test, type-check or build before reporting done. (2026-09-28) — [Building with Claude Sonnet 5.5](https://claude.dev/blog/building-with-claude-sonnet-5-5/)

**Fast mode**
- [OFFICIAL] Fast mode is "not a different model": the same Opus with a different API configuration, "up to 2.5x faster at a higher cost per token". Supported on Opus 5.5, Opus 5 and Opus 4.8 only ("not available on Sonnet, Haiku, or other models"; Sonnet 5.5 "has no fast mode"). On subscription plans it is billed to usage credits only. "The first time you enable fast mode in a conversation, you pay the full fast mode uncached input token price for the entire conversation context", once per conversation; the speed header is part of the cache key. Opus 5.5 is the fast-mode default since v2.1.280. — [Fast mode](https://code.claude.com/docs/en/fast-mode), [Prompt caching](https://code.claude.com/docs/en/prompt-caching), [Building with Claude Sonnet 5.5](https://claude.dev/blog/building-with-claude-sonnet-5-5/)

**/model mid-session and caching**
- [OFFICIAL] "Each model has its own cache. Switching with `/model` means the next request reads the entire conversation history with no cache hits, even though the content is identical." Claude Code asks for confirmation only while the cache is warm (v2.1.238+); a `PreModelSwitch` hook (v2.1.251) can block, confirm or annotate a switch. Other events that count as a model switch: a skill or command whose frontmatter names a different `model` (for that turn), `opusplan` plan-mode toggles, and automatic safety-classifier fallback. — [Prompt caching](https://code.claude.com/docs/en/prompt-caching), [Changelog](https://code.claude.com/docs/en/changelog)
- [OFFICIAL] "On Opus 5.5, Sonnet 5.5, and Fable 5.1 with an API key or a Claude subscription, changing effort keeps the cache" (not on Bedrock, Google Cloud Agent Platform, a Claude apps gateway, or with `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS`; before v2.1.260 Fable 5.1 did not keep it). On other models an effort change invalidates the cache. — [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- [OFFICIAL] Size of a broken cache on a 100,000-token prefix: Fable 5.1 "$1.25 USD instead of $0.03 USD" (50 times), Opus 5.5 "$0.50 USD instead of $0.02 USD" (25 times), "the other current models 12.5 times". At 120K context an Opus 5.5 five-minute write is about $0.60 and a read about $0.02. — [Optimizing for cost and intelligence](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence), [What a task costs on Opus 5.5](https://claude.dev/blog/what-a-task-costs-on-opus-5-5/)
- [OFFICIAL] Official advice (2026-08-14): "Set your model and effort level before you start. Changing either one mid-conversation can bust your prompt cache, which can increase token cost." On `/model`: "every model has its own cache, so on the next turn the entire conversation gets prefilled again at full price. (This includes opusplan, which switches models every time you go in or out of plan mode.)" On fast mode: "if you're going to turn it on, turn it on at the start. (Turning it off again is free, cache-wise.)" The same post says `/effort` also breaks the cache; that statement predates the September prompt-caching page, which says effort changes keep the cache on Opus 5.5, Sonnet 5.5 and Fable 5.1. — [Maximizing the value of your Claude Code sessions](https://claude.com/blog/maximizing-the-value-of-your-claude-code-sessions), [Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- [OFFICIAL] Subagents and the cache: a subagent's first request "doesn't read the parent's cache, because the two prefixes differ"; subagents get the 5-minute TTL "even on a subscription" unless you set `subagentPromptCacheTtl` / `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL` (v2.1.242+) or `experimental.cacheTtl` in frontmatter (v2.1.248). A fork "inherits the parent's system prompt, tools, and conversation history exactly, so its first request reads the parent's cache", but a fork runs on the main conversation's model. In a workflow fan-out, agents with the same model, effort, agent type, tools, output schema and working directory share a prefix and Claude Code holds all but the first for up to 5 seconds so they can read the first agent's cache. The main conversation gets a 1-hour TTL on a subscription within plan usage (5 minutes on API key or usage credits). — [Prompt caching](https://code.claude.com/docs/en/prompt-caching), [Workflows](https://code.claude.com/docs/en/workflows), [Sub-agents](https://code.claude.com/docs/en/sub-agents)

**Native advisor tool**
- [OFFICIAL] `/advisor <model>`, the `advisorModel` setting, or `--advisor` pair the main model with a stronger advisor that "receives the full conversation, including every tool call and result". An advisor must rank at or above the main model. Accepted pairings: Sonnet 5.5 main: Fable, Opus 5 or later, Sonnet 5.5; Opus 5 or 5.5 main: Fable, Opus 5 or later; Fable 5.1 main: Fable 5.1 only; Haiku 4.5 can call an advisor but cannot be one. "There is no setting to cap or force advisor calls." Advisor tokens bill at advisor rates (usage credits for Fable on plans where Fable bills that way). Toggling the advisor does not invalidate the main cache, but "The advisor model's own read of the conversation is not cached. Each advisor call processes the full transcript anew." API only (not Bedrock, Foundry, Google Cloud). Experimental. — [Advisor](https://code.claude.com/docs/en/advisor)
- [OFFICIAL] The API-level advisor tool (beta header `advisor-tool-2026-03-01`, type `advisor_20260301`) bills the advisor sub-inference at the advisor's rates, has an optional `max_uses`, a `max_tokens` cap on advice and optional advisor-side caching ("breaks even at roughly three advisor calls"). Advice is typically "400 to 700 text tokens, or 1,400 to 1,800 tokens total including thinking". With a Sonnet 5.5 executor, advice comes back encrypted (`advisor_redacted_result`). — [Advisor tool (API)](https://platform.claude.com/docs/en/agents-and-tools/tool-use/advisor-tool), [Building with Claude Sonnet 5.5](https://claude.dev/blog/building-with-claude-sonnet-5-5/)

**Fallback and other**
- [OFFICIAL] `fallbackModel` / `--fallback-model sonnet,haiku` (chain capped at 3, applies to subagents too, lasts one turn). Content-based fallback: Fable 5.1, Fable 5 and Opus 5.5 re-run cyber-flagged requests on Opus 4.8 and biology-flagged ones on Opus 5; Sonnet 5.5 re-runs cyber-flagged requests on Sonnet 5 and ends biology-flagged requests with a refusal. Disable with `switchModelsOnFlag: false`. — [Model configuration](https://code.claude.com/docs/en/model-config)
- [OFFICIAL] Organization controls that affect routing: `availableModels` (allowlist), `deniedModels` and `availableModelsMatch: "exact"` (v2.1.283), `enforceAvailableModels`, `maxEffortLevel` and organization effort limits. A blocked family alias in a subagent's `model` is replaced by the newest permitted version of that family, or by the inherited model, with a warning in interactive sessions; `availableModels` also applies to subagent model overrides and to the advisor model (v2.1.172). — [Model configuration](https://code.claude.com/docs/en/model-config), [Sub-agents](https://code.claude.com/docs/en/sub-agents), [Changelog](https://code.claude.com/docs/en/changelog)
- [OFFICIAL] The Claude Code docs point to an Anthropic post, "Lessons from building Claude Code: Prompt caching is everything", as the design rationale for plan mode, deferred tool loading and compaction (page not fetched in this research). — [Prompt caching, related resources](https://code.claude.com/docs/en/prompt-caching), [post](https://claude.com/blog/lessons-from-building-claude-code-prompt-caching-is-everything)
- [OFFICIAL] Dynamic workflows pick each agent's model "in the same order it uses for subagents"; a model named in the script counts as the per-invocation model; the docs suggest "Ask Claude to use a smaller model for stages that don't need the strongest one". More than 25 agents or a projected 1.5M tokens shows a "Large workflow" warning; up to 16 concurrent agents and 1,000 agents per run. — [Workflows](https://code.claude.com/docs/en/workflows)

### Inferences
- Because Opus 5.5 and Sonnet 5.5 have identical cache-read prices ($0.20), moving a long-context loop from Opus to Sonnet only saves on cache writes (50%) and output (50%), not on reads. Illustration at list prices, assuming a subagent work order with a 20K-token cold start, 30 turns averaging 50K cached context, 60K freshly written tokens and 25K output tokens: Opus 5.5 about $1.20 (reads $0.30, writes $0.40, output $0.50), Sonnet 5.5 about $0.75, Haiku 4.5 about $0.38, Fable 5.1 about $2.63. At equal token use Sonnet is therefore 0.625 of Opus and breaks even if it uses 1.6 times Opus's tokens, which is exactly the output-token ratio Artificial Analysis measured at max effort (416M vs 260M) and is consistent with the nearly equal index costs ($9,074 vs $8,708). These are calculations from list prices with stated assumptions, not measurements.
- The same arithmetic prices a model switch at 120K context at about $0.60 (Opus 5.5), $0.30 (Sonnet 5.5), $1.50 (Fable 5.1) versus roughly $0.02 to $0.03 warm. Subagents do not trigger this on the parent, since they start separate contexts, but each fresh subagent pays its own cold start (the brief measured about 20K tokens; at list price roughly $0.05 for Sonnet 5.5, $0.10 for Opus 5.5, $0.25 for Fable 5.1 on a cold five-minute write, about $0.004 to $0.005 if a same-prefix sibling warmed it within five minutes).
- All wm roles can be expressed in plugin-agent frontmatter (`model`, `effort`, `maxTurns`, `omitClaudeMd`, `disallowedTools`, `experimental.cacheTtl`), but not hooks, MCP servers or permission modes. Pinning `model` per agent is more robust than relying on inheritance or `CLAUDE_CODE_SUBAGENT_MODEL`.
- `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` (the brief's setup) now only affects subagents that have no `model` of their own, and not the built-in Explore or Plan, which is consistent with the brief's measurement that Explore runs on the session model. `_FORCE=1` would route Explore to the forced model but would also override wm's per-role frontmatter, so it is unsuitable for wm.
- The `haiku`, `sonnet` and `opus` aliases float. Using aliases lets wm:scout move to Haiku 5.5 automatically when the alias changes, but on Bedrock and Google Cloud the `sonnet` alias is Sonnet 4.5 (retiring on Anthropic-operated platforms on 2026-11-30), so a published plugin should document pinning variables for those providers.
- Per-role effort is cheap to vary on Opus 5.5, Sonnet 5.5 and Fable 5.1 (cache preserved), expensive on other models and on Bedrock or gateways.

### Gaps

- The new Agent-tool `effort` parameter (v2.1.292, shipped the same day) is documented only by a changelog line; its exact semantics against frontmatter `effort` are unverified.

## Q2. What does Anthropic officially recommend for subagent models, planning versus execution and cost control (docs, engineering blog, advisor/executor pattern)?

### Takeaway
Official guidance is not uniform and moved during 2026. Older and generic pages say Sonnet for most coding, Opus for hard problems, Haiku for lookups, and plan with Opus then execute with Sonnet. Anthropic's own measurements show multi-model setups pay only in narrow cases.

### Inferences
- The newest Anthropic material (late September 2026) supports two things for wm: (a) Opus 5.5 at default effort as the lead and daily driver, and (b) Fable only as an escalation after Opus 5.5 at higher effort has failed twice. It is lukewarm on delegating code writing to a smaller model: the 2026-09-25 post says keep code edits on Opus 5.5 and measure opusplan before adopting it, while the 2026-09-28 post (written after Sonnet 5.5 existed) endorses Sonnet 5.5 for well-scoped tasks with a clear spec and a way to check the result. wm's "Sonnet 5.5 from precise work orders" matches the second and the 2026-07-07 "edits you can describe precisely" guidance, but no Anthropic measurement compares Opus-plans-Sonnet-implements against Opus 5.5 alone on coding.
- Anthropic's measured evidence says delegation pays for context isolation, cost-tail insurance and work beyond one context window, not for dependent chains that fit in one context. A wm rule of "delegate only if the output would flood the main context, the work is independent, or the work order is precise and verifiable; otherwise do it in the lead at low or medium effort" follows from that.
- The documented consult-rate fragility (executors stop asking at low effort) argues against letting a cheaper agent decide whether to escalate by itself; wm's design where the lead decides and the user approves each Fable call sidesteps that failure mode.

## Q3. What do practitioners report about tiered routing (Haiku explore, Sonnet implement, Opus plan and review): savings, quality loss, failure modes?

### Takeaway
Independent measurement of the tiered pattern in Claude Code is thin; most "60-80% savings" claims are unmeasured. The solid evidence is (a) Anthropic's own narrow-case results (Q2), (b) independent and vendor measurements that per-token price is a poor predictor of cost per task, and (c) a steady stream of user-reported failure modes: silent inheritance of the expensive model, frontmatter models not honored in some code paths, cheaper models skipping verification or stubbing work, handoff context loss, and subagent start-up overhead.

### Inferences
- The strongest measured argument for tiering is not per-token price but context isolation and tail-cost insurance, and the strongest argument against is that cheaper models can use more tokens or skip checks, which turns savings into retries. A routing design needs its own cost-per-accepted-work-order measurement instead of relying on published ratios.
- Silent model inheritance is the most documented cost trap. wm should pin models, verify the served model from subagent transcripts, and treat any setup that depends on `CLAUDE_CODE_SUBAGENT_MODEL` read from `settings.json` `env` as unverified on current versions.
- The Cognition findings (single-threaded writes, clean-context reviewer, escalation by a stronger model) match wm's role split; the risk they flag for wm:implementer is context loss in the work order, so a work order should carry the decisions and constraints, not just the task.

### Gaps
- No controlled public study of Haiku-explore / Sonnet-implement / Opus-review in Claude Code was found; "60-80%" figures come from unmeasured blogs.
- Reddit and GitHub reports concern Opus 4.5 to 5, Sonnet 4.5 to 5 and Haiku 4.5 and may not transfer to Sonnet 5.5 and Opus 5.5.
- Reddit snapshots are third-party mirrors; vote counts and comments could not be verified against reddit.com.
- Hacker News discussions were searched for but none with substantive routing data was found.

## Q4. What about proxies and routers (for example musistudio/claude-code-router): routes and risks?

### Takeaway
claude-code-router (CCR) is a popular local gateway that sends Claude Code traffic to other providers and models by scenario (default, background, think, long context, web search, image, subagent tag, or arbitrary header and body conditions) with fallbacks. Anthropic states it does not support routing Claude Code to non-Claude models through any gateway, does not endorse or audit such products, and prohibits routing requests through consumer subscription credentials on behalf of users. Technical risks are mostly cache, thinking-block and tool-compatibility behavior that depends on the gateway.

### Cited Findings

- [INDEPENDENT] Current README (v3.x): "a local model gateway and control plane for coding agents" for Claude Code, Codex, Grok CLI, Kimi CLI, OpenCode and others; routes to OpenAI Chat/Responses, Anthropic Messages, Gemini, OpenRouter, DeepSeek, Moonshot, Kimi Code, Mistral, Z.AI and custom providers; features include retries, credential pools, "ordered fallback models", request logs with "resolved routes, latency, token usage, cost estimates". The README opens with a sponsor banner (Kimi) and lists commercial API resellers as sponsors. — [README](https://github.com/musistudio/claude-code-router)
- [INDEPENDENT] Routing documentation (v3.x): conditions on request headers and body (`request.header.x-client-name`, `request.body.model`, `request.body.messages` with a "contains deep" operator for task-type routing such as images), rewrites that set `request.body.model`, Node.js script rules that receive `input.tokenCount` and a request summary and can return a model plus a fallback chain, retry and fallback modes triggered by 408/409/429/5xx (retry) or any 4xx/5xx (fallback targets), and response headers `x-ccr-fallback-attempts` and `x-ccr-fallback-model`. ### Inferences
- A router that sends only Claude models to different Claude deployments is within supported behavior; a router that sends scenarios (background, think, long context) to non-Claude models is explicitly unsupported and changes the quality, tool-call and thinking-block semantics Claude Code was tested on. For wm, whose routing is by role inside Claude Code, an external router adds risk (cache loss, unsupported paths, credential policy) without a clear benefit.
- A router cannot reproduce wm's role-based routing: CCR conditions see request bodies, not wm roles, unless the subagent tag trick is used, which needs a custom prompt convention.
- CCR's own quality or cost impact was not measured in any source found; the 1,170 open issues and sponsor-driven provider presets are signals about maintenance load and incentives, not evidence of defects.

### Gaps
- No measured quality or cost comparison of CCR routes (for example DeepSeek as `background`) was found.
- CCR-specific incident evidence (cache-miss costs, tool-call or thinking errors) was not retrieved; the search returned generic API guidance rather than CCR issue threads.
- The January to April 2026 enforcement chronology is from news aggregators, not an Anthropic announcement; the primary source found is the current legal page.

## Q5. How do people measure Claude Code usage and cost per model and per subagent (/usage, ccusage, statusline, OpenTelemetry), and how do Pro and Max plans weigh models against usage limits?

## Q6. What benchmark evidence shows the coding-quality gap between Opus 5.5, Sonnet 5.5, Haiku 4.5 and Fable 5.1 (or predecessors)?

## Q7. What concrete improvements to wm's routing does the evidence suggest (effort per role, escalation and de-escalation, cost per work order, caching-aware delegation, budgets)?

### Takeaway
The wm role split is consistent with Anthropic's guidance and with the Cognition pattern, with three evidence-based caveats: Anthropic has not shown that an Opus-plans, Sonnet-implements split saves money on coding and tells users to measure it; cheaper-model savings depend on token use, not price; and silent model inheritance and per-role effort are the main places wm can lose money. The improvements below are inferences from the cited evidence in Q1 to Q6.

**Improvements (each tied to the evidence above)**
1. Pin every wm agent completely: `model` as an alias, `effort`, `maxTurns`, `omitClaudeMd: true` (for agents whose work order is self-contained) and a minimal `tools` or `disallowedTools` list. This avoids the silent-inheritance bug class (issues 43869, 80902) and shrinks the roughly 20K-token start-up. Suggested starting efforts, from Anthropic's effort guidance and data: scout none (Haiku has no effort setting); implementer `medium` (Anthropic's feature-work default; do not exceed `high` because of scope-creep penalties); reviewer `high` (verification and edge cases); fable-advisor `medium`, or `low` for open judgment questions and `xhigh` only for verification-heavy ones (Fable at `low` already beat Sonnet 5 per solved task, and its research score was flat across effort); researcher `low` or `medium`.
2. Do not use `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`. To keep the built-in Explore (Opus 5.5) from doing searches, deny `Agent(Explore)` in project settings and give wm:scout a description that wins delegation; alternatively define a user or project agent named `Explore` with `model: haiku`. Add a defensive `PreToolUse` hook on the Agent tool that rewrites or rejects spawns whose `model` does not match the wm role (community-reported to work, because `updatedInput` is honored).
3. Verify routing every run: a `SubagentStop` hook (or a script) that reads `agent_transcript_path`, records the served `model`, token usage and elapsed time, and flags mismatches. `/tasks` also shows model and effort per subagent row.
4. Cost per work order: log, per work order id, cost from the implementer transcript, review transcript(s), rework passes and any advisor consult, priced from list prices (cache reads, 5-minute and 1-hour writes, output). Report "cost per accepted work order", not per token. Run the A/B that Anthropic recommends: the same 10 to 20 real work orders through (A) Opus 5.5 `medium` directly, (B) Opus 5.5 `low` directly, (C) Sonnet 5.5 implementer plus Opus reviewer. The list-price arithmetic in Q1 implies Sonnet loses its saving if it uses more than about 1.6x Opus's tokens at the illustrated mix (this is a calculation, not an Anthropic statement).
5. Delegate by rule, not by habit: delegate when output would flood the lead's context (search results, logs, test output), when pieces are independent, or when the work order is precise and verifiable; otherwise implement in the lead at `low` or `medium`. This follows the measured result that delegation pays on cost tails and work beyond one context, and loses on dependent chains.
6. Escalation ladder with a failure signal: (a) implementer fails the gate (tests, type-check, review blocker) then one retry with a sharper work order that names the failed check; (b) re-run at higher effort on the same model (Anthropic's low-then-high policy) or hand to the lead at `medium`; (c) the lead raises its own effort to `high` then `xhigh` before changing model; (d) propose a Fable consult to the user only after the lead at `xhigh` fails twice on the same problem, or for unsupervised long runs. De-escalate by lowering effort first (cheap, cache-preserving), not by switching model mid-session. Add the "ask for real checks" paragraph from the Sonnet 5.5 guide and an explicit "no edits outside the work order's scope" line to the implementer prompt.
7. Caching-aware delegation: keep model and effort fixed within a session; avoid `opusplan` in the same session as wm (each plan toggle is a cold-cache model switch); batch work orders for the same agent type back-to-back within five minutes so siblings share the cached system-prompt and tool prefix, or set `experimental.cacheTtl: 1h` or `subagentPromptCacheTtl` for the implementer if gaps are typically 5 to 60 minutes; keep CLAUDE.md small (every non-Explore subagent loads it unless `omitClaudeMd`); use `/compact` at natural breaks while the cache is warm.
8. Fable consult packaging: compare the dossier approach with the native `/advisor fable` pairing on cost. Native consult cost is roughly transcript tokens times $10 per million plus about $0.08 of output (about $1.1 at a 100K transcript; Anthropic's measured $1.55 per attempt over 1.39 requests works out to about $1.12 per consult); a dossier consult costs the dossier tokens at $10 per million, a cold subagent start (about $0.25 at 20K tokens) and the memo plus thinking at $50 per million. A dossier of 15K tokens and a 3K-token memo costs roughly $0.15 + $0.25 + $0.15 plus thinking, so it wins when the lead's transcript is long and the dossier is short. Show the user an estimated cost range in the approval prompt, cap memo length ("under 80 words" style instruction worked best for the native advisor), and target one to three consults per task.
9. Budgets: pass `maxTurns` per agent; add a work-order budget line (turn limit plus an "elapsed against budget" line, which Anthropic measured on one research benchmark (DRACO, single agent) as cutting typical cost 60% for a 4.1-point lower score, and with much smaller effects on two other sets); set `--max-budget-usd` for headless runs; warn when a work order's running cost exceeds a multiple of the lead's own estimate; use the `Large workflow` warning thresholds (25 agents or 1.5M tokens) as a sanity bound for any fan-out.
10. Make the scout verifiable: require file paths with line numbers and short quotes so the lead can spot-check cheaply, because a small model that misreads a result "sends the main model after the wrong file". Move `model: haiku` to follow the alias to Haiku 5.5 when released, and add a smoke test before swapping.
11. Document provider caveats for a public plugin: on Bedrock and Google Cloud the `sonnet` alias is Sonnet 4.5, on Foundry `opus` is Opus 4.6, effort changes there are not cache-preserving, and the advisor tool is unavailable; recommend `ANTHROPIC_DEFAULT_SONNET_MODEL` / `ANTHROPIC_DEFAULT_OPUS_MODEL` pins.

### Gaps
- None of the numeric thresholds above (effort per role, retry counts, break-even multiples) has been tested on wm work orders; they are starting points derived from Anthropic benchmarks that use different tasks.
- It is not known whether the per-spawn `effort` parameter (v2.1.292) interacts with frontmatter `effort` the way `model` does; test before relying on it.
- Whether `experimental.cacheTtl: 1h` pays depends on wm's real inter-spawn gaps; Anthropic's rule of thumb for the main loop is to use the 1-hour TTL when about 1 turn in 20 follows a 5-minute to 1-hour pause, but subagent request patterns differ.
- Interactions between wm hooks (PreToolUse on Agent) and plugin-hook restrictions were not tested in this research.
