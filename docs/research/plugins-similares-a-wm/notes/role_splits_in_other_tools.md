## Key Question 1: How do the main tools define roles, bind models to roles, hand context from planner to executor, verify results, and how widely are they used?

### Takeaway
Every major tool now has named agents or modes with per-agent tool limits and a way to give each role its own model: an explicit `model` field that can inherit or pin (Cursor, Kilo, Codex, Factory, OpenCode, VS Code custom agents) or per-mode settings (Aider's editor-model flag, Cline's Plan/Act setting, Roo's sticky per-mode model memory); handoff is either same-session continuity (Cline, Windsurf) or a parent-written prompt to an isolated child that returns only a summary (Roo/Kilo, Cursor, Codex, Factory, Amp, OpenCode, Devin). Verification is built in only for the autonomy-oriented products (Devin, Factory, Copilot/Cursor/Codex cloud agents); interactive tools lean on the human. In 2026 the trend is orchestration as a capability of the main agent with single-threaded writes, not a separate orchestrator persona (Roo archived, Kilo deprecating its Orchestrator mode).

### Inferences
- Shared primitives across tools: per-agent `model` with `inherit` as default (Cursor, Factory, Codex, OpenCode, Kilo, VS Code), per-agent tool or permission scopes (`readonly`, `sandbox_mode`, glob allow/deny, read-only tool categories), context isolation with a single summary returned, and a persisted human-editable plan before building (Windsurf, Cursor, Kilo plan files, VS Code handoffs). wm already has the first three; the plan-edit gate is implicit in its work orders.
- Two handoff architectures exist. Same-session continuity (Cline, Windsurf) has no handoff loss but also no context isolation. Isolated child with prompt-in, summary-out (everything else) gives isolation but makes the parent's prompt quality and the child's summary fidelity the failure points (see Key Question 3 and 5). wm is the second type, so it inherits those risks and should compensate with artifacts and gates.
- Only Factory (Missions), Cursor (research blog), Cognition (Smart Friend) and Anthropic (advisor tool) publish reasoning for which model fills which role; the rest leave it to the user. Cline's telemetry shows users overwhelmingly choose Opus-plans/Sonnet-acts when they split, which is adoption evidence, not quality evidence.
- wm's lineup (Opus main, Sonnet implementer, Opus reviewer, Haiku search, stronger consult) is closest to Factory Missions plus Cognition's "writes single-threaded, fresh-context review, Smart Friend". Differences: Factory's validators use another vendor's model, and Factory writes a validation contract before implementation.
- Persona-style orchestrator modes are being retired (Roo archived, Kilo deprecating Orchestrator in favour of subagent tools), supporting wm's choice that the main session orchestrates itself rather than a separate orchestrator role.
- Adoption figures describe products, not role splits; none of them measures the value of the split. Several figures (Cursor, Cognition, Factory, Copilot users) come from low-reliability secondary sources and should be quoted with that caveat.

### Gaps
- No controlled planner/executor vs single-model results from Cursor, Codex, Copilot, Devin, Augment or Amp; only anecdotal or telemetry data. Cursor's Plan Mode docs say nothing about per-phase models; Devin and Augment do not publish per-role models.
- OpenAI's harness-engineering post could not be fetched (403); only a secondary summary was read.
- Adoption figures for Cursor, Cognition, Factory and Copilot are from aggregators; I did not find primary filings or press releases for the exact numbers quoted.
- Amp's Oracle model identity and Kilo's deprecation date were not confirmed from primary pages in this session (the Amp news post failed to fetch). No adoption figures were found for Amp or Augment Intent (Intent is in public beta since Feb 2026).

## Key Question 2: What did Aider measure for architect/editor pairs (pairings, pass rates, costs vs single models, dates), and what changed later?

### Takeaway
Aider's architect/editor split (v0.58.0, 2024-09-26) raised scores for nearly every pair tested in 2024-25 and gave a cost-or-time advantage at the frontier (R1+Sonnet 64.0% at $13.29 vs o1 61.7% at $186.50), but the latest architect entry (o3-high + gpt-4.1, 2025-06-27) scored below o3-high alone (78.2% vs 81.3%, though 17% cheaper and 38% faster), no architect result exists for any 2026-generation model, and the benchmark is saturated. Aider has been in maintenance mode since mid-2025.

## Key Question 3: How do Roo Code's and Kilo Code's Orchestrator decompose and delegate, and what do users report about quality, cost and context loss?

### Takeaway
Roo's Orchestrator ("Boomerang") hands a self-contained instruction to an isolated subtask in a chosen mode and gets back only an `attempt_completion` summary; the Orchestrator itself deliberately has no file-read, edit or command tools. Public user evidence is thin and negative-leaning (truncated instructions, useless or unverifiable subtask results, duplicate re-execution costing tokens); no quantitative quality or cost studies exist. Roo was archived on 2026-05-15 and Kilo has deprecated its Orchestrator in favour of subagents inside ordinary agents.

### Cited Findings
- **[Official]** Decomposition: "Roo analyzes a complex task and suggests breaking it down into a subtask"; down-flow is the `new_task` `message` parameter, which must include "all necessary context from the parent task or previous subtasks" and "a clearly defined scope"; up-flow is only the `attempt_completion` `result` summary ("only this summary returns to the parent"); each subtask has "its own isolated context with a separate conversation history" in a mode picked by the Orchestrator — [Roo boomerang docs](https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks)
- **[Official]** The Orchestrator intentionally lacks file read/write and command execution; docs warn of "context poisoning" if it reads files itself; docs do not say whether different modes use different models (only the sticky-model feature exists) — [Roo boomerang docs](https://roocodeinc.github.io/Roo-Code/features/boomerang-tasks); [Roo custom modes docs](https://roocodeinc.github.io/Roo-Code/features/custom-modes)
- **[Official]** Kilo: the old Orchestrator was "the only way to break complex tasks into subtasks" and required explicit switching; now agents with full tool access launch subagents through a `task` tool (analysis of complexity, subagent launch, isolated history on a shared directory, result delivered before the parent continues, concurrent sessions allowed); the deprecated page says to stop switching to orchestrator mode — [Kilo Orchestrator (deprecated)](https://kilo.ai/docs/code-with-ai/agents/orchestrator-mode)
- **[Vendor claim / Opinion]** Kilo staff blog (2025-05-05, Brendan O'Leary): "ONLY that summary went back to the parent task", no cost numbers, no model assignment per mode, a "Pro Tip" to use strong models for planning and cheaper ones for implementation, and the author's impression of "probably the most bug-free code I've written in a while" — [Kilo blog](https://blog.kilo.ai/p/how-kilo-codes-orchestrator-mode)
- **[Opinion]** Roo issue #3751 (2025-05-20, v3.17.2, Gemini 2.5 Flash Thinking): orchestrator-written instructions for custom-role subtasks were "very obviously truncated"; closed "not planned" — [GitHub issue](https://github.com/RooCodeInc/Roo-Code/issues/3751)
- **[Opinion]** Roo issue #4881 (2025-06-19, v3.21.1, Sonnet 4 via OpenRouter): after a subtask completes, navigating away loses the completion button and "Resume Task" re-runs finished work with duplicate token charges; closed as duplicate — [GitHub issue](https://github.com/RooCodeInc/Roo-Code/issues/4881)
- **[Opinion]** Roo issue #6970 (2025-08-12): "subtasks currently often don't return useful results, and require additional prompting"; the orchestrator lacks visibility into what a subtask did, causing "misunderstanding of what the subtask did" and "inability to identify errors or understand possible places where errors were introduced"; proposes a separate validator chat with yes/no grading and automatic reversion; closed "not planned" — [GitHub issue](https://github.com/RooCodeInc/Roo-Code/issues/6970)
- **[Opinion]** The same handoff failure appears in Cursor: the parent over-injects stale context into sub-agent prompts (May 2026) — [Cursor forum](https://forum.cursor.com/t/orchestrator-agent-pollutes-and-overrides-prompt-context-passed-to-sub-agents/161339)
- **[Secondary]** Roo reached about 3M installs and 24.2k stars before shutdown (announced 2026-04-21, archived 2026-05-15); Kilo is the actively maintained fork — [rywalker.com](https://rywalker.com/research/roo-code); [Kilo comparison page](https://kilo.ai/compare/roo-code-shutdown-roomote)

### Inferences
- The failures cluster at the interface, not in the models: an instruction channel that can truncate or over-condense, a summary-only return the parent cannot verify, and non-idempotent subtask resume. The summary-only return prevents context bloat but removes the evidence the parent needs; wm's work-order-in, report-with-evidence-out design plus deterministic gates addresses exactly these.
- Roo's choice to strip the Orchestrator of read/edit/command tools is a deterministic role limit similar to wm's hooks, with a stated reason (avoid context pollution); Kilo's later move to subagent tools inside normal agents suggests persona-based orchestrator modes were a transitional design.
- Practical lesson: the parent's task message is the only contract, so it needs completeness checks (nothing truncated, all referenced files and criteria present) before dispatch.

### Gaps
- No quantitative user or independent study of Roo/Kilo Orchestrator quality or cost. A search snippet mentioned a Reddit comment with 5-hour session costs (about $20 split between Gemini 2.5 Pro for the Orchestrator and Sonnet 3.7 for code), but the thread could not be retrieved, so it is not reported as a finding.
- Reddit and Hacker News threads could not be fetched directly; user evidence is limited to GitHub issues and a Cursor forum parallel. The date and rationale for Kilo's Orchestrator deprecation were not found beyond the docs page.

## Key Question 4: What do academic and industry studies find about multi-agent or role-split coding vs a single agent (gains, losses, costs, handoff errors)?

### Takeaway
Controlled studies that match models and tokens find no reliable gain, and often losses and large token overheads, from multi-agent topologies on coding benchmarks (SWE-bench Verified and Terminal-Bench relative changes of -2% to -19%; at most 1 of 6 multi-agent systems beating a matched single agent). Positive results come from decomposable or read-heavy tasks, long-horizon builds with isolated workspaces and test-based merging, heterogeneous strong-planner or advisor setups, and independent review roles; the best industry evidence (Cognition, Cursor, Factory, Anthropic) says to keep writes single-threaded. Most studies use pre-2026 models.

### Cited Findings

#### Critical and negative results
- **[Independent]** MAST, "Why Do Multi-Agent LLM Systems Fail?" (submitted 2025-03-17, v3 2025-10-26): 1,600+ annotated traces, 7 frameworks (ChatDev, MetaGPT, HyperAgent, AppWorld, AG2, Magentic-One, OpenManus), failure rates of 41% to 86.7%; 14 failure modes in three groups. Most common: step repetition 15.7%, reasoning-action mismatch 13.2%, unaware of stopping conditions 12.4%, disobey task specification 11.8%, incorrect verification 9.1%, no or incomplete verification 8.2%, task derailment 7.4%, fail to ask for clarification 6.8%, premature termination 6.2%, conversation reset 2.2%, ignored other agent's input 1.9%, disobey role specification 1.5%, information withholding 0.85%. Interventions on ChatDev: improved role specification +9.4% task success and high-level task-objective verification +15.6% on ProgramDev (GPT-4o); "not all failure modes are resolved"; "many existing verifiers perform only superficial checks" such as compilation; calls for multi-level verification — [arXiv 2503.13657](https://arxiv.org/abs/2503.13657); [full text](https://arxiv.org/html/2503.13657) **[Outdated?]** (GPT-4/Claude 3-era systems)
- **[Independent]** "Towards a Science of Scaling Agent Systems" (v1 2025-12-09, v3 2026-04-08): 260 configurations, six benchmarks including SWE-bench Verified and Terminal-Bench, GPT-5, Gemini 2.5 and Claude Sonnet 3.7/4/4.5 families, matched reasoning-token budgets (mean 4,800 per trial). Relative to a single agent: SWE-bench Verified hybrid -2.1%, centralized -3.1%, decentralized -5.4%; Terminal-Bench centralized -19.2%, independent +1.7%; Finance-Agent centralized +80.8%; PlanCraft -39% to -50%; overall range +80.8% to -70.0%. Capability saturation: tasks where a single agent already exceeds 45% accuracy "experience negative returns from additional agents"; independent agents amplify errors 17.2x vs 4.4x under centralized coordination; token overhead independent 58%, centralized 285%, decentralized 263%, hybrid 515%; success per 1,000 tokens 67.7 single agent vs 21.5 centralized — [arXiv 2512.08296](https://arxiv.org/abs/2512.08296); [HTML v3](https://arxiv.org/html/2512.08296v3) (same-family agents, not strong-planner/weak-executor mixes)
- **[Independent]** "Rethinking the Value of Multi-Agent Workflow" (2026-01-18): a single agent running multi-turn conversations "can reach the performance of homogeneous workflows with an efficiency advantage from KV cache reuse" across seven benchmarks including coding; limitation: heterogeneous multi-model workflows cannot share a KV cache and were not matched — [arXiv 2601.12307](https://arxiv.org/abs/2601.12307)
- **[Independent]** BenchAgent, "Do More Agents Help?" (2026-06-04): GPT-4.1, ten reasoning, coding and tool-use benchmarks under one protocol; "at most one of six tested MAS exceeds the matched single-agent anchor", five trail by 2.56-11.29 points at higher cost; a Claude-Code-style single-runtime workflow reached 66.72% on GAIA, more than 20 points above the best fixed multi-agent system — [arXiv 2606.05670](https://arxiv.org/abs/2606.05670)
- **[Official]** Cognition (2025-06-12): parallel subagents making implicit conflicting decisions (Flappy Bird example) produce inconsistent work — [Cognition](https://cognition.com/blog/dont-build-multi-agents). Anthropic (2025-06-13): "Most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time" — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[Independent]** Benchmark validity: of 254 SWE-bench submissions, the top entries are statistically indistinguishable (no adjacent top-30 pair separated on Verified; McNemar tests), and within-model scaffold ranges reach 29.8 points vs an 8.8-point spread across the top 30 (2026-09-15) — [arXiv 2609.17394](https://arxiv.org/abs/2609.17394); an earlier leaderboard dissection found "dominance of proprietary LLMs (especially Claude 3.5)" without establishing an architecture winner (2025-06, v3 2026-02) — [arXiv 2506.17208](https://arxiv.org/abs/2506.17208)

#### Positive results
- **[Independent, authors' own]** MetaGPT (2023-08, GPT-4 era): roles Product Manager, Architect, Project Manager, Engineer, QA Engineer with structured artifacts (PRD, then design with file lists, data structures and interface definitions, then task distribution); 85.9% HumanEval and 87.7% MBPP Pass@1; executable feedback +4.2% and +5.4% Pass@1; vs ChatDev on SoftwareDev: executability 3.75 vs 2.25, human revision cost 0.83 vs 2.5, but tokens 31,255 vs 19,292 — [arXiv 2308.00352](https://arxiv.org/abs/2308.00352); [numbers via ar5iv](https://ar5iv.labs.arxiv.org/html/2308.00352) **[Outdated?]**
- **[Independent]** ChatDev (2023-07, ACL 2024): chat chain and "communicative dehallucination"; the abstract gives no benchmark numbers — [arXiv 2307.07924](https://arxiv.org/abs/2307.07924)
- **[Independent]** Agentless (2024-07-01): fixed localisation, repair and patch-validation pipeline without agent loop solved 32.00% of SWE-bench Lite at $0.70 per issue, beating contemporary agents — [arXiv 2407.01489](https://arxiv.org/abs/2407.01489) **[Outdated?]**
- **[Independent]** CAID (Geng and Neubig, 2026-03-23, v2 2026-07-08): centralized delegation, isolated git-worktree workspaces and test-based integration gave +25.6 points on PaperBench and +14.7 on Commit0 vs a single agent (long-horizon, interdependent subtasks) — [arXiv 2603.21489](https://arxiv.org/abs/2603.21489)
- **[Independent, authors' own]** Agyn (2026-02-01): coordination, research, implementation and review roles in isolated sandboxes resolved 72.2% of SWE-bench 500 (v2 abstract), "outperforming single-agent baselines using comparable language models"; per-role models and cost not given — [arXiv 2602.01465](https://arxiv.org/abs/2602.01465)
- **[Official]** Anthropic research system (2025-06-13): Opus 4 lead plus Sonnet 4 subagents "outperformed single-agent Claude Opus 4 by 90.2%" on an internal research eval; agents use about 4x and multi-agent about 15x the tokens of chat; token usage alone "explains 80% of the variance" on BrowseComp; early failures included 50 subagents for simple queries and duplicated work from vague task descriptions — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **[Official]** Anthropic parallel Claudes C compiler (2026-02-05, Nicholas Carlini): 16 agents, nearly 2,000 sessions, 2B input and 140M output tokens, just under $20,000, a 100,000-line Rust compiler that builds Linux 6.9; task locking through files, progress files; failure modes: breaking existing functionality (needs CI) and noisy test output polluting context; "the task verifier is nearly perfect, otherwise Claude will solve the wrong problem" — [Anthropic](https://www.anthropic.com/engineering/building-c-compiler)
- **[Official]** Cursor browser/long-run study (2026-01-14): hierarchical planners/workers/judge ran hundreds of agents for weeks, 1M+ lines, trillions of tokens, 25x video-rendering speed-up in one project; noted as "nowhere near optimal" — [Cursor blog](https://cursor.com/blog/scaling-agents)

#### Planner/executor, advisor and role-specific model evidence
- **[Independent]** PEAR planner-executor benchmark (2025-10-08, v4 2026-01-08): "A weak planner degrades overall clean task performance more severely than a weak executor"; planner memory matters, executor memory does not; planner-targeted attacks are most effective (domains not specified in the abstract) — [arXiv 2510.07505](https://arxiv.org/abs/2510.07505)
- **[Independent]** Plan-and-Act (ICML 2025): separate planner and executor models, 57.58% on WebArena-Lite (web tasks, not coding) — [arXiv 2503.09572](https://arxiv.org/pdf/2503.09572)
- **[Vendor claim]** Anthropic advisor strategy (2026-04-09): Sonnet 4.6 with an Opus advisor gained 2.7 points on SWE-bench Multilingual while cutting cost per agentic task by 11.9%; Haiku 4.5 with an Opus advisor scored 41.2% on BrowseComp vs 19.7% solo, trailing Sonnet solo by 29% at 85% lower cost — [Anthropic](https://claude.com/blog/the-advisor-strategy)
- **[Official]** Role-specific model choice reported by practitioners: Cursor found GPT-5.2 a better planner than a coding-specialised model ([Cursor blog](https://cursor.com/blog/scaling-agents)); Cognition found Smart Friend works across frontier models but not with a weaker (SWE-1.5) primary ([Cognition](https://cognition.com/blog/multi-agents-working)); Factory assigns different vendors' models to orchestrator, worker, validator and research seats ([Factory Missions](https://factory.com/news/missions))
- **[Official data]** Aider's results (Key Question 2) are the only large public pair-vs-solo series I found, run by the tool's maintainer with open raw data — [Aider leaderboard data](https://raw.githubusercontent.com/Aider-AI/aider/main/aider/website/_data/polyglot_leaderboard.yml)

#### Underspecification and escalation
- **[Independent]** Ambig-SWE (2025-02-18, v3 2026-02-21): interaction on underspecified SWE-bench Verified tasks improves performance by up to 74%, and "current state-of-the-art models struggle to differentiate between well-specified and underspecified instructions" — [arXiv 2502.13069](https://arxiv.org/abs/2502.13069)
- **[Independent]** "Ask or Assume?" (2026-03-27, v3 2026-09-07): an uncertainty-aware multi-agent scaffold that "decouples underspecification detection from code execution" reaches 69.40% resolve rate on underspecified SWE-bench Verified, "significantly outperforming" a single-agent baseline and nearly closing the gap to fully specified issues — [arXiv 2603.26233](https://arxiv.org/abs/2603.26233) (baseline figures not in the abstract)

#### Reviewer reliability
- **[Independent]** CriticGPT (OpenAI, 2024-06-28): model critiques preferred over human critiques in 63% of cases on naturally occurring LLM code errors; human-plus-critic teams produced fewer hallucinated errors — [arXiv 2407.00215](https://arxiv.org/abs/2407.00215)
- **[Independent]** LLM reviewers overcorrect (2026-02-28): they "frequently misclassify correct code implementation as non-compliant or defective", and "more detailed prompt design, particularly with those requiring explanations and proposed corrections, leads to higher misjudgment rates" — [arXiv 2603.00539](https://arxiv.org/abs/2603.00539)
- **[Independent]** Self-preference bias (2026-04-24, v4 2026-06-02): 20 LLMs favour their own outputs; stronger capability does not reduce the bias; a structured multi-dimensional evaluation cut it by 31.5% on average — [arXiv 2604.22891](https://arxiv.org/abs/2604.22891)

#### Context and instruction degradation
- **[Independent]** "Context Rot" (2025-07-14, 18 LLMs): performance degrades non-uniformly as input grows; distractors compound — [Chroma research](https://www.trychroma.com/research/context-rot)
- **[Independent]** IFScale (2025-07-15): best frontier models reach only 68% accuracy at 500 simultaneous instructions, with primacy bias (a keyword-inclusion report task, not coding) — [arXiv 2507.11538](https://arxiv.org/abs/2507.11538)
- **[Independent]** "Evaluating AGENTS.md" (2026-02-12, v3 2026-09-29): context files "do not generally improve task success rates" while "increasing inference cost by over 20% on average"; repository overviews were ineffective; agents follow the instructions well — [arXiv 2602.11988](https://arxiv.org/abs/2602.11988)

### Inferences
- Evidence quality ranking: controlled protocol studies (MAST, the scaling paper, BenchAgent, Rethinking) are the most rigorous but use older or same-family models and do not test a strong-planner plus cheaper-implementer mix; industry reports (Cognition, Cursor, Factory, Anthropic) are real-world but uncontrolled and vendor-authored; vendor guides with multipliers (Augment) are the weakest.
- Reconciling the results: multi-agent helps when subtasks are decomposable and read-heavy, when workspaces are isolated and merges are test-gated, or when a much stronger model supplies only the thinking; it hurts on sequential, tightly coupled, tool-heavy tasks and when a single model already succeeds more than about 45% of the time. The same-model scaling results mean wm should not expect an accuracy gain from role splitting by itself.
- wm's configuration (sequential single writer, heterogeneous models, independent reviewer, gated escalation) matches the part of the design space where industry evidence is most positive and controlled studies are silent; so the evidence neither confirms nor refutes it, and measuring it on wm's own tasks is warranted.
- Reviewer evidence cuts both ways: fresh-context review finds real bugs (Cognition's production figures, CriticGPT) but LLM reviewers also over-flag correct code and prefer their own style, so reviews should be evidence-based and verified by execution.

### Gaps
- No controlled study of an Opus-5-class planner plus Sonnet-5-class implementer against single-model Opus; no study using work-order-style specs.
- No independent replication of Cognition's "2 bugs per PR, 58% severe" (no control group, no definition of "severe" in the post).
- Most results predate the 5.x model generation; SWE-bench saturation limits what any leaderboard can show.
- The cross-family self-preference claim in a 2025 study (GPT-4o and Claude 3.5 Sonnet favouring same-family outputs) appeared only in a search summary and was not verified.
- The "4-220x" multi-agent token multiplier seen in one search summary has no traceable source and is not used.

## Key Question 5: Which practices reduce handoff loss (shared context documents, precise specs, executing tests, fresh-context reviewers)?

### Takeaway
The converging practices are: persisted plan/spec/progress artifacts that humans can edit; specs with an exact contract plus machine-checkable acceptance criteria agreed before coding; execution-based verification at each handoff instead of model self-reports; reviewers with fresh context reading only the diff and spec; capability-limited roles; and an explicit ask-or-block path for underspecification. Counter-evidence warns that more context is not better (AGENTS.md study, spec overhead for small tasks).

### Cited Findings

#### Shared context documents and artifacts

### Inferences
- Handoff loss shows up in three places: what the planner writes (incomplete, truncated, over-synthesised or over-prescriptive), what the executor returns (summary without evidence, premature "done"), and what the reviewer sees (executor's transcript biases it). Each has a documented countermeasure: completeness-checked work orders, evidence-bearing reports checked by commands, and reviewers limited to spec plus diff.
- "Share context" and "keep context small" are both supported; the reconciliation is pointers plus decisions: pass non-discoverable decisions and the contract, let the receiver re-discover the rest (the AGENTS.md result, Cognition's reviewer design, the Cursor forum bug).
- Tests are the strongest contract carrier (Anthropic C compiler, Factory validation contract, VeriMAP, MAST), but only if the tests are trusted; test quality needs its own check.
- Self-reported completion is unreliable (premature victory, marking features complete untested), so completion should be gated by something other than the executor's word.

### Gaps
- No ablation isolating one practice (plan file, spec precision, test execution, fresh reviewer) on coding accuracy; evidence is a mix of engineering blogs, issue reports and indirect benchmarks.
- No study of how many numbered rules a coding work order can carry before compliance drops (IFScale is a non-coding keyword task).
- VeriMAP's quantitative results and defaults (reported as 3 attempts per subtask and 5 replanning iterations in Augment's guide) were not verified in the paper.

## Key Question 6: Does the evidence support wm's split, and what concrete improvements follow (when not to split, what the spec must contain, how to verify, when to escalate)?

### Takeaway
The evidence supports wm's structure (single-writer implementation in an isolated context, independent fresh-context review, contract-first work orders with executable acceptance tests, deterministic role limits, a gated escalation path) but does not support an accuracy gain from "Opus plans, Sonnet implements" by itself with the 5.5-generation models, nor a guaranteed cost saving, nor Fable as the default coding escalation. wm should justify the split by role isolation, review independence and context hygiene, and measure cost and quality against single-model Opus on its own tasks.

### Inferences

#### Verdict
- Supported by evidence: one writer at a time with an isolated context; independent fresh-context review; tests and contracts as the handoff; deterministic role and scope limits; a human- or Opus-gated escalation to a stronger model; read-only cheap roles for search.
- Not supported or unproven: accuracy gain from Opus-plans/Sonnet-implements at the 5.5 generation (Anthropic's own table has Opus ahead on 7 of 8 benchmarks by at most 3.2 points and Sonnet ahead on Terminal-Bench 4.0); a cost saving (price ratio is only 2:1, cache-read prices are equal at $0.20, and Artificial Analysis measured Sonnet 5.5 as more expensive per task at max effort; if agentic coding sessions are dominated by cache-read input, which I did not measure here, the effective gap is smaller than the 2:1 headline); Fable as a general coding escalation (Opus 5.5 beats Fable 5.1 on all three coding rows Anthropic published, and Fable costs 2.5x Opus per token on input and output, though cache-read prices are close at $0.25 vs $0.20, so its premium sits in output and cache-write tokens).
- Frame the split as role isolation, review independence and context hygiene, and say so in the README; make any cost claim conditional on a measured benchmark.

#### When not to split
- Do the work inline in the main session when the change is small or confined to one or two files and the main session already holds the context (Böckeler's "sledgehammer to crack a nut"; Augment's own "when not to use": single-file changes), when the target is unknown or exploratory, when the steps are tightly coupled and sequential (scaling paper: sequential tasks degrade 39-70% with multi-agent variants), when the contract cannot be expressed as runnable checks, or when the planner lacks codebase knowledge to specify precisely (Cognition: over-prescriptive managers backfire).
- Split when the change is well specified and test-verifiable, when implementation output would pollute the main session's context (context rot), when an independent review is wanted, and for parallel read-only work (search, research, review). Never run parallel writers without isolated worktrees, disjoint file ownership and test-gated merging (Cognition, Cursor, Codex docs, CAID).
- Add a written triage rule with a cost check: work-order authoring plus implementation plus review must plausibly cost less than doing it inline (the thresholds are heuristics; none are evidence-based).

#### What the work order must contain
- Goal and non-goals; the exact contract (signatures, schemas, file paths, error behaviour), because MetaGPT-style interface definitions and Factory's contracts are the artifacts that carried work between roles.
- A short, prioritised list of numbered rules, most important first (instruction-density and primacy effects; AGENTS.md study: only minimal requirements). Do not paste repository overviews or discoverable facts; give pointers instead.
- The implicit decisions the implementer must honour (conventions, edge cases, error handling), since "actions carry implicit decisions" is the main cause of conflicting output.
- Executable acceptance tests or verification functions with exact commands and expected exit codes, authored and approved before implementation, ideally failing first for the right reason (VeriMAP verification functions, Factory validation contract, "verifier nearly perfect").
- Scope: allowed and forbidden files, enforced by hooks rather than by prose (Kilo globs, Roo `fileRegex`), plus a rule that tests and the spec itself are read-only for the implementer.
- Enumerated BLOCKED triggers (ambiguity, contract-test conflict, need to touch out-of-scope files, repeated failing attempts) and a required BLOCKED payload (what was tried, evidence, the exact question), because models cannot reliably self-detect underspecification (Ambig-SWE).
- A report format with files changed, commands run with exit codes, deviations from the order, unresolved risks (Factory handoff reports), written to a file rather than only returned as a chat summary.
- A completeness lint by the main session before dispatch (all fields present, referenced files exist, tests run and fail as expected, nothing truncated), which operationalises "decouple underspecification detection from execution" (Ask or Assume) and prevents the truncation and stale-context failures seen in Roo and Cursor.

#### How to verify
- Deterministic ladder first: hooks, then lint, type-check and the work order's tests run by the harness (not by the implementer's claim), then a check that spec and tests were untouched, then UI or end-to-end runs where applicable (Factory validators, Anthropic harness browser testing).
- Then the Opus reviewer in fresh context given only the spec and the diff (not the implementer transcript), asked to judge conformance to the contract and to attach evidence (a failing test or reproduction) to every finding, to limit overcorrection.
- To reduce shared blind spots, vary the reviewer (different effort level and system prompt at minimum; a different model family if the plugin can call one, as Factory does with GPT-5.3-Codex validators); this is a hypothesis supported by self-preference research, not by a coding-specific measurement.
- Make "done" a machine-checked state in a status file the implementer cannot mark complete itself (Anthropic harness feature list).

#### When to escalate
- BLOCKED goes to the main session, which decides: fix the spec, take over, or retry; cap retries per work order (a cap of 2-3 is a heuristic; Augment's guide attributes 3 attempts and 5 replans to VeriMAP, unverified) and log reasons.
- Consult the strongest model only when Opus has failed after a bounded effort at higher effort settings or the job is long-horizon and asynchronous (Anthropic's stated Fable use case), since Opus 5.5 beats Fable 5.1 on the coding rows published and costs 2.5x less per token; keep user approval and add a per-session consult cap analogous to the advisor tool's `max_uses`.
- Package the consult as a dossier containing the failing evidence, what was tried and the exact question, since the advisor pattern works because the advisor sees the shared context and returns a plan, correction or stop in roughly 400-700 tokens.

#### What to borrow
- Factory: complexity-to-model routing tiers, validation contract first, structured handoff reports, an "agent readiness" precondition (runnable tests and lint before enabling the implementer), milestone-level validation.
- Cognition: writes stay single-threaded; fresh-context review; Smart Friend consult pattern; "map-reduce-and-manage" only for read-heavy fan-out.
- Anthropic: JSON status file with test-gated pass flags, progress log, git as checkpoint; advisor `max_uses` cap.
- Cursor/VS Code/Codex/OpenCode: `inherit` default with explicit pin and effort per role; VS Code's prioritised model list as fallback; read-only flags per role.
- Windsurf/Cursor/Kilo: a user-editable plan artifact before building; Copilot: a cheap self-review pass before reporting (as a pre-filter, not a substitute for independent review); Cline: usage telemetry to see which role mappings people actually run.

#### What to avoid
- Orchestrators that rewrite or re-synthesise the user's precise instructions (Cursor forum), summary-only returns with no verifiable evidence (Roo issue #6970), non-idempotent resume (Roo #4881), giant specs for small tasks (Böckeler), repository-overview context files (AGENTS.md study), assuming a model fits a role without testing (Cursor: GPT-5.2 beat a coding-specialised model as planner), parallel writers, and trusting the executor's "done" (Anthropic's premature victory).

#### Measure it
- Ship a small eval harness: the same set of real tasks run (a) end to end with Opus alone and (b) through wm, recording pass rate, tokens and dollars per task by role, wall-clock time, BLOCKED rate and reasons, review-finding precision, and rework loops; log per-role effort settings because Sonnet 5.5's verbosity depends heavily on effort.

### Gaps
- No head-to-head data for Opus 5.5 vs Sonnet 5.5 as implementers under a work-order protocol; no coding-specific cost-per-task data by model; the Artificial Analysis figures are secondary and general-purpose.
- Fable 5.1's advantage on very long or hard tasks is claimed but I found no published evidence for coding where it beats Opus 5.5; Anthropic's table shows the reverse on three coding evals.
- Thresholds (retry caps, size limits, rule counts) are heuristics without evidence; the cache-read dominance of agentic cost is an inference from price structure, not a measured breakdown.
