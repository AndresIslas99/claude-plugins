### Takeaway

### Inferences
- Adoption ranking by live signals (downloads and release cadence) is: OpenSpec (2.45M npm/month) far ahead, then BMAD, Taskmaster, GSD and Spec Kit (PyPI undercount) in the 40k to 85k per month range, then cc-sdd (24k). Stars alone would rank Superpowers and Spec Kit first, which reflects marketing reach and plugin-marketplace exposure more than process adoption.
- Abandonment risk is real in this space: three of the named frameworks have effectively stopped (claude-code-spec-workflow, Taskmaster feature work, Agent OS workflow phases) and one was forked (GSD). For a plugin to be published, the lesson is to keep the surface small and self-contained so a pause in maintenance does not strand users.
- Frameworks that shipped many breaking releases (OpenSpec 1.0 removed commands; BMAD v6.11 retired about half of its core skills with shims; Spec Kit says it will "keep breaking it when breaking it makes it better") show that migration shims and `update` commands are part of the product, not an afterthought.

### Gaps
- Kiro: no current (2026) official user count and no "specs created" figure was found; the GitHub repo is only an issue tracker, so its star counts do not measure product adoption. Kiro's changelog is a rolling page, so version numbers may be stale within days.
- No source found for how many of Superpowers' 296k stars correspond to active installs; the plugin is distributed through marketplaces, so npm numbers do not apply.
- I did not verify the date GSD's original repository was archived beyond the API flag (`archived: true`, last push 2026-05-31); one search-result summary claimed 2026-06-26 but I could not trace it to a primary page. I also did not establish why the original maintainer stopped (the continuation's docs refer to an earlier community fork named "get-shit-done-redux").

## 2. What are each framework's phases and artifacts, how does it hand off from planning to implementation, and how does it keep spec and code in sync (spec drift)?

### Takeaway
Every framework converges on the same skeleton (intent, spec, plan/design, tasks, implement, verify), but they differ in three decisions that matter for wm: (1) whether the spec is per-change and discarded/archived (Spec Kit, Kiro, cc-sdd, BMAD plans) or merged into a living source of truth (OpenSpec delta merge on archive); (2) whether process size is fixed (Spec Kit core, early Kiro) or routed by an up-front size/risk decision (BMAD Build, Superpowers three paths, cc-sdd discovery, OpenSpec lite/full, GSD fast/quick/full); (3) whether anything checks drift mechanically (almost nothing in the core of any framework; Spec Kit's `/speckit.converge`, OpenSpec's `/opsx:verify` and BMAD's retrospective are all LLM judgments, and the deterministic drift checks live in community extensions or in GSD Core's codebase-map gate). The 2026 trend is toward fewer phases and smaller artifacts, with maintainers themselves cutting scaffolding (Agent OS v3, BMAD v6.11/6.12, Superpowers 6.4.2 "leaner plans").

### Cited Findings

#### GitHub Spec Kit (as of v1.1.1, 2026-10-06)
- Core sequence: "Constitution once per project; specify, plan, tasks, implement, converge per feature"; clarify, checklist and analyze are optional "quality gates" ([README](https://github.com/github/spec-kit/blob/main/README.md), [agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)). Only `/speckit.specify` is strictly required before `/speckit.plan` ([agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)).
- Artifacts: `.specify/memory/constitution.md` (principles plus governance, with version/ratified/amended fields), per-feature `spec.md`, `plan.md`, `tasks.md`, `checklists/requirements.md`, plus `research.md`, `data-model.md`, `contracts/`, `quickstart.md` that `implement` reads if present ([constitution-template.md](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md), [implement.md](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)).
- Clarification: `/speckit.clarify` asks "up to five targeted questions" and writes the answers back into `spec.md`; spec templates carry inline `[NEEDS CLARIFICATION: ...]` markers ([agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md), [spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)).
- Plan gate: the plan template has a "Constitution Check" marked "GATE: Must pass before Phase 0 research. Re-check after Phase 1 design." ([plan-template.md](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)).
- Tasks: dependency-ordered phases (Setup, Foundational, one phase per user story, Polish) with `[P]` parallel markers and per-story "Checkpoint" lines ([tasks-template.md](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md), [agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)).
- Consistency check: `/speckit.analyze` is "STRICTLY READ-ONLY", treats constitution conflicts as CRITICAL ("non-negotiable"), caps output at 50 findings and promises deterministic IDs on re-runs ([analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)). It is an LLM prompt, so "deterministic" is a request to the model, not a guarantee.
- Handoff to implementation: `/speckit.implement` reads `tasks.md` and `plan.md` (plus optional design docs and the constitution), treats unchecked checklist items as a gate it must ask the user about, executes phases in order, and marks tasks `[X]` ([implement.md](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)). For large features the docs advise scoping each run ("Implement only the Setup and Foundational phases...") "to avoid overwhelming the agent's context" ([agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)).
- `/speckit.converge` (added 2026-06-18 in v0.11.2) assesses the code against spec, plan and tasks, is "append-only" (its only write is a new Convergence phase in `tasks.md`), and loops with `implement` until it reports "Converged" ([CHANGELOG](https://github.com/github/spec-kit/blob/main/CHANGELOG.md), [converge.md](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md), [agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md)).
- Two more first-party processes shipped as opt-in bundled extensions: `bug` (assess, fix, test; reports in `.specify/bugs/<slug>/`; verdict `verified | partial | failed`, "Missing verification is not a successful fix") in v0.9.5 on 2026-06-05, and `assess` (intake, research, define, shape, decide; ends in go / needs-clarification / kill) in v0.13.0 on 2026-07-17 ([README](https://github.com/github/spec-kit/blob/main/README.md), [history.md](https://github.com/github/spec-kit/blob/main/docs/history.md)).
- Official philosophy versus tooling: the methodology doc says "Specifications as the Lingua Franca. The specification becomes the primary artifact. Code becomes its expression... Maintaining software means evolving specifications" and that "pivots become systematic regenerations rather than manual rewrites", with nine constitutional articles (Library-First, CLI Interface, Test-First "NON-NEGOTIABLE", Simplicity, Anti-Abstraction, Integration-First) and "Phase -1" plan gates ("Using <=3 projects?", "No future-proofing?") that make the model "explicitly justify any complexity" ([spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)). The current persistence docs, by contrast, leave the update strategy to the team (next bullet), so the spec-as-source rhetoric is not what the tooling enforces.
- Spec drift: the project "does not force one artifact maintenance strategy" and names three conventions: flow-back (edit any artifact, reconcile manually; risk "silent divergence"), flow-forward (each feature directory immutable, new directory for new requirements; risk duplication) and living spec (edit `spec.md`, regenerate `plan.md`/`tasks.md`; risk "lost rationale") ([spec-persistence.md](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md), [evolving-specs.md](https://github.com/github/spec-kit/blob/main/docs/guides/evolving-specs.md)). The docs cite Birgitta Boeckeler's spec-first / spec-anchored / spec-as-source taxonomy ([Fowler site](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), 2025-10-15).
- Community drift tooling (not core, "maintainers only verify that catalog entries are complete and correctly formatted"): Spec Sync, Reconcile Extension, Architecture Governance ("read-only, fail-closed validator"), CI Guard ("block merges on gaps"), Canon, DocGuard, Retrospective Extension ("spec adherence scoring"), Verify Tasks Extension ("Detect phantom completions: tasks marked [X] in tasks.md with no real implementation") ([community/extensions.md](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)).
- Maintainer's own limits (2026-08-21): the brownfield on-ramp "could be smoother" and trust boundaries remain "guidance rather than enforcement" ([manorrock.com](https://www.manorrock.com/blog/2026/08/21/spec_kit_turns_one.html), secondhand via a fetch summary).

#### OpenSpec (v1.14.1)
- Model: `openspec/specs/` is "the source of truth" for current behaviour; `openspec/changes/<name>/` holds proposal.md, delta specs under `specs/`, design.md and tasks.md; archiving "merges its delta specs into the main specs and preserv[es] the change for history" in a dated archive folder ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)).
- Delta format: `## ADDED Requirements`, `## MODIFIED Requirements`, `## REMOVED Requirements` ("Why deltas": review efficiency, conflict avoidance, brownfield fit) ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)).
- Commands: core profile `/opsx:propose`, `explore`, `apply`, `update`, `sync`, `archive`; expanded profile adds `new`, `continue`, `ff`, `verify`, `bulk-archive`, `onboard` ([opsx.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md), [release v1.0.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.0.0)).
- "Actions, not phases": "Dependencies are enablers - they show what's possible, not what's required next"; the README's philosophy is "fluid not rigid / iterative not waterfall" ([opsx.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md), [README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md)).
- Progressive rigor: "Lite spec (default)" with "a few concrete acceptance checks" versus "Full spec (for higher risk)" for cross-team, API, migration or security changes; a spec "is a behavior contract, not an implementation plan" ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)).
- Handoff: `/opsx:apply` implements `tasks.md` checkboxes; since v1.14.1 `openspec instructions apply` says "the tracked tasks are complete" and asks the user to review or verify before archiving rather than declaring the change ready ([release v1.14.1](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.14.1)).
- Drift handling: "artifacts are the live plan, not a signed contract"; manual code edits are reconciled by editing the delta spec or fixing the code, and `/opsx:verify` "reads your artifacts and your code and tells you where they diverge" (completeness, correctness, coherence) without blocking anything; "at archive time, your specs become the truth of record" ([editing-changes.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/editing-changes.md)).
- Project context: `openspec/config.yaml` injects `context` (prepended to every artifact's instructions, 50 KB limit) and per-artifact `rules` ([opsx.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md)).

### Inferences
- Right-sizing is now the dominant design move: BMAD (intent gaps, irreversible actions, footprint), Superpowers (spike, bounded, architectural with a one-way ratchet), cc-sdd ("no spec needed, implement directly"), OpenSpec (lite vs full), GSD (fast, quick, full) and Spec Kit (independent bug and assess entry points) all add a fast lane after earlier versions were criticised as heavy. wm's T0 to T4 triage matches this direction; the one-way ratchet ("nothing downgrades mid-task") and BMAD's "route after investigating, not before" are concrete refinements to consider.
- Only OpenSpec treats the spec as a merged, living artifact with a mechanical merge step; everyone else treats specs as per-change records. A wm work order (spec for one change) is closer to Spec Kit/Kiro/cc-sdd feature specs, so wm needs its own answer to "what survives after the work order": its ADRs and path-scoped rules play the role of OpenSpec's merged specs, and the learning loop is the merge step.
- Drift is handled almost entirely by LLM re-reading (`converge`, `verify`, retrospective) and by convention (persistence models); the only mechanical checks are format validation (OpenSpec `validate`), state scripts (BMAD `tickets.py`, GSD `gsd-tools`) and counting heuristics (GSD drift gate). A deterministic "does the diff touch files outside the work order's declared scope" check would be stricter than anything listed here.

| GSD Core (1.16.0) | Discuss, plan, execute, verify, ship; fast and quick lanes | `PLAN.md` in parallel waves, fresh context per agent | Post-execute codebase drift gate; decision-coverage gates | Profiles per agent, per-phase models, dynamic routing, cross-AI review | Many hooks and `gsd-tools` gates, TDD red-evidence check, parity tests | Installer, plugin manifest, commands, skills, agents, hooks |

### Gaps
- Kiro: the `tasks.md` checkbox grammar and the `.config.kiro` metadata fields are not documented in what I could read (the latter comes from one user issue).
- No framework publishes data on how often specs actually drift from code or how often drift checks catch real problems.
- Spec Kit's `analyze` "deterministic IDs" claim is a prompt requirement; I found no test showing that re-runs are stable.

## 3. Does each framework assign different models or agents to different phases, and does it run subagents, parallel tasks or git worktrees?

### Takeaway
Only a minority assign models by role. The ones that do (GSD Core profiles, Superpowers' written model-selection rules, Taskmaster's Claude Code plugin agents, moai-adk, Spec Kit workflow steps) all converge on "strongest model plans and judges, a cheaper tier executes, escalate one tier on repeated failure", which is wm's split. Subagent-per-task execution with an independent reviewer is now common (cc-sdd, Superpowers, BMAD Build, GSD), but it is specified in prose that the host model may skip; worktree isolation is mostly an opt-in extension, except GSD Core and moai-adk where hooks enforce it. Spec Kit, OpenSpec and Agent OS core run a single agent and leave model choice to the user.

### Cited Findings

#### Frameworks with explicit model routing
- Superpowers (v6.4.x) `subagent-driven-development` has a "Model Selection" section: "Use the least powerful model that can handle each role to conserve cost and increase speed"; mechanical 1-2 file tasks with a complete spec get a "fast, cheap model", integration and debugging get a "standard model", architecture/design and the final whole-branch review get "the most capable available model"; "Fix-loop escalation (rounds 4-5): use a model at least one tier above the implementer that got stuck"; "Always specify the model explicitly when dispatching a subagent. Use a mid-tier model as the floor for reviewers and for implementers working from prose descriptions. - Taskmaster: three model roles in config, "the main model, the research model, and the fallback model (in case either the main or research fail)", used for Taskmaster's own LLM calls ([README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md)). A community extension, SpecJudge (57 stars), reads the spec artifacts and recommends the cheapest "right-sized" model per project, labelling Claude Fable 5 as "overkill" for a small CRUD example ([README](https://github.com/JoaquinRuiz/SpecJudge/blob/main/README.md), [catalog entry](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)).
- OpenSpec has no routing; its README only says it "works best with high-reasoning models" and recommends "Codex 5.5 and Opus 4.7 for both planning and implementation" ([README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md)).
- BMAD ships five named personas (Analyst Mary, PM John, Architect Winston, Developer Amelia, UX Designer Sally) that are prompts, not separate models; review lenses can be run "on another model" via `bmad-customize` ([skills-and-agents.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/reference/skills-and-agents.md), [review-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md)).
- cc-sdd's Claude Code skills carry no per-role model setting (only `disable-model-invocation: true` on entry skills); my grep of the repository tarball found no `model:` frontmatter and no hook definitions ([kiro-impl SKILL.md](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/claude-code-skills/skills/kiro-impl/SKILL.md)).

#### Subagents, independent review and parallelism
- cc-sdd `/kiro-impl` (autonomous mode): "one task per iteration; fresh implementer, reviewer, and debugger contexts when native subagents are available"; implementer must end with an exact `## Status Report` block whose `STATUS` is `READY_FOR_REVIEW | BLOCKED | NEEDS_CONTEXT` (a missing or prose status triggers one re-dispatch); reviewer returns `APPROVED | REJECTED`; two rejection rounds go back to the implementer, the third triggers a debugger subagent (max 2 debug rounds), after which the task is marked `_Blocked:_`; the controller alone commits with explicit file staging ("NEVER use `git add -A`"); `(P)` tasks are "informational" and still run sequentially "to avoid git conflicts" ([kiro-impl SKILL.md](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/claude-code-skills/skills/kiro-impl/SKILL.md), [skill-reference.md](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/skill-reference.md)). `/kiro-spec-batch` creates multiple specs "in parallel when native subagents are available"; for independent writers it advises: "Separate chats do not by themselves isolate file edits: choose separate worktrees" ([skill-reference.md](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/skill-reference.md)).
- Superpowers: fresh subagent per task, "a task review (spec compliance + code quality) after each, and a broad whole-branch review at the end"; a recovery "ledger"; `scripts/task-brief PLAN_FILE N` extracts a task to a file so the dispatch prompt stays small; `review-package` "rejects empty or non-descendant BASE..HEAD ranges (exit 3)"; inline `executing-plans` is the "cheapest" alternative with "one fresh review of the whole branch at the end"; `using-git-worktrees` creates an isolated worktree and "verifies clean test baseline" ([README](https://github.com/obra/superpowers/blob/main/README.md), [SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)).
- BMAD Build: reviews "its own work with independent reviewers", which "works best on a platform that can spawn subagents, or at least call another model from the command line"; review layers "review the same diff independently and in parallel", then triage verifies, dismisses (with a recorded reason, "never silently") or routes each finding to patch / defer / decision-needed; `bmad-build-auto` "halts `blocked` with `no subagents`" if subagents are unavailable; default depth `quick` (one reviewer) versus `thorough` (several lenses) ([build-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/build-a-change.md), [review-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md), [autonomous-development-loops.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/autonomous-development-loops.md)). Docs candidly list platform risk: "Vendors, including Anthropic and OpenAI, sometimes ship changes that alter how subagents run... the lenses execute one after another instead of in parallel - or they fall back to the main session, which is far worse for review quality than it sounds" ([review-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md)).
- GSD Core: thin orchestrators spawn 33 specialised agents, "each executor starts with a clean 200k-token context", plans run "in parallel waves" ([README](https://github.com/open-gsd/gsd-core/blob/HEAD/README.md), [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/ARCHITECTURE.md)). Worktree isolation is enforced by a hard-blocking PreToolUse hook: the agent-isolation guard exists because dispatch isolation was "a prose instruction" and "Nothing verifies the model actually copied it. When it is omitted, the executor runs and commits directly in the user's PRIMARY checkout" ([gsd-agent-isolation-guard.js](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-agent-isolation-guard.js)).
- moai-adk: a leader session plus numbered "lanes", each lane a session plus its own git worktree; "A lane runs at most 10 `Agent()` subagents at once, and write-capable spawns are isolated in their own worktrees" ([README](https://github.com/modu-ai/moai-adk/blob/main/README.md)).
- Taskmaster `loop` runs Claude Code sequentially per task (optionally `--sandbox` in Docker); the plugin's `task-orchestrator` coordinates "parallel execution opportunities" ([loop docs](https://tryhamster.com/docs/taskmaster/automation/loop), [agents/](https://github.com/eyaltoledano/claude-task-master/tree/main/packages/claude-code-plugin/agents)).
- Spec Kit core `implement` runs in the agent's own session and marks `[P]` tasks as parallelizable only in the task file; parallelism, worktrees and multi-agent coordination come from community extensions: Worktree Isolation, Worktrees ("Default-on worktree isolation for parallel agents"), Spec Kit Schedule ("parallel subagent rounds... critical-path aware, file-conflict safe"), MAQA ("coordinator, feature, QA workflow... parallel or sequential dispatch"), Red Team ("parallel lens agents") ([community/extensions.md](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)). Feature branches are optional and handled by the `git` extension ([existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/guides/existing-projects.md)).
- OpenSpec "never commits, branches, pushes, or pulls"; parallel work is parallel change folders, with `bulk-archive` "conflict detection" ([team-workflow.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/team-workflow.md), [release v1.0.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.0.0)).

#### Kiro (AWS)
- Classic spec flow: no phase-to-model mapping found; the model is per session (an "Auto" router picks per request) (reported) ([models docs](https://kiro.dev/docs/models/)). Per-agent `model:` exists in CLI custom agents (`.kiro/agents/*`), and a request for a model per hook or subagent (#4180) was open (reported) ([agent config](https://kiro.dev/docs/cli/v3/agent-config/)). Docs advise Sonnet 5.5 for "bug fixes, review, agent and subagent work" and Haiku for sub-agents (reported) ([models docs](https://kiro.dev/docs/models/)). Credit multipliers versus Auto: Haiku 4.5 0.4x, Sonnet 5.5 1.3x, Opus 5.5 2.0x, Fable 5.1 6x (Fable 5.1 in Enterprise preview since 2026-09-16) (Sonnet and Opus confirmed on the changelog; Haiku and Fable reported) ([changelog](https://kiro.dev/changelog/), [models docs](https://kiro.dev/docs/models/)).
- Subagents (2025-12-18) run in their own context windows; pipelines support DAGs ("planned upfront and cannot be modified") and review loops with `max_iterations` 1-10 (reported) ([subagents docs](https://kiro.dev/docs/custom-agents/subagents/)). The "frontier"/autonomous agent became Kiro Web autonomous mode (GA 2026-09-01): sandboxed, research/code/verification sub-agents, up to 10 concurrent tasks, and "you cannot choose the model" in that mode (reported) ([autonomous agent post](https://kiro.dev/blog/introducing-kiro-autonomous-agent/), [autonomous-mode docs](https://kiro.dev/docs/web/autonomous-mode/)).
- Workflows (opt-in since 2026-09-30, confirmed on the changelog and docs): "a graph: agent steps, sequences, loops, and parallel branches" stored as JSON or YAML; each step "runs in its own session with fresh context, so a reviewer... evaluates the work without inheriting the coder's reasoning"; "custom agents, preferred models, and thinking effort per step"; "A workflow coordinates several agents and repeats reviews, so it uses more tokens than a single session" ([workflows docs](https://kiro.dev/docs/workflows/)). The bundled `feature-pipeline` (confirmed): setup creates "an isolated worktree" and a run directory, then requirements, a design loop ("at most three design/review attempts; stop only when `design-review.json` says `APPROVED`; abort if unmet"), plan, a code loop of at most three attempts in which "the two code reviewers deliberately use different models (`claude-fable-5` and `gpt-5.6-sol`)" and an aggregate `code-review.json` gates exit, then validate; it "launches from Opus 5 at High effort" with design and review agents at "Extra high effort"; caveats quoted verbatim: "iteration caps limit time and usage; they do not prove quality" and "A workflow does not make an agent read-only by itself; the selected agent tools and permissions still govern side effects" ([patterns docs](https://kiro.dev/docs/workflows/patterns/)).
- Kiro's own agent-triage team runs its lead on the strongest model, fan-out workers on cheap models and a cross-provider "council" for judgement calls (reported) ([blog, 2026-08-21](https://kiro.dev/blog/trust-agent-triage/)).
- Checkpoints: the IDE snapshots files and conversation per prompt but "does not track MCP or bash changes"; CLI "Rewind" forks the conversation only (reported) ([checkpoints docs](https://kiro.dev/docs/checkpoints/)).

### Inferences
- Kiro's Workflows (2026-09-30) is the closest commercial analogue to wm's architecture: fresh-context author and reviewers on different model families, a JSON verdict file as the loop gate, capped iterations, an isolated worktree. It arrived a year after Kiro's classic spec flow had no model routing at all, which suggests the author-then-independent-review loop is where vendors are converging.
- Three independent projects (Superpowers, GSD Core, Taskmaster plugin) landed on the same routing as wm: top model plans/judges/reviews, mid-tier executes, with escalation on repeated failure. wm's choice of Sonnet for the implementer is therefore mainstream; the independent DeepSWE row for the older Sonnet 5 (slower and costlier per task at max effort) is a reminder that routing should be validated per task type and per model generation, since vendor figures put Sonnet 5.5 within about 3 points of Opus 5.5 on DeepSWE v1.1. DeepSWE tasks are long-horizon, whereas a precise work order is closer to Superpowers' "plan contains the complete code, so cheapest tier" case. The deeper routing and cost evidence lives in the sibling note `model_routing_and_cost.md`. The Superpowers rule "mid-tier floor for implementers working from prose descriptions" implies work-order precision is what lets a cheaper model succeed.
- wm's fixed-format implementer report with BLOCKED mirrors cc-sdd's `STATUS: READY_FOR_REVIEW | BLOCKED | NEEDS_CONTEXT` and BMAD's `blocked` plan status with enumerated blocking conditions; neither enforces the format in code (cc-sdd re-dispatches once when the block is unparseable). A deterministic parser in a SubagentStop hook would be a step beyond both.
- "Omitted model inherits the session's most expensive model" (Superpowers) is a concrete cost leak for any plugin that spawns subagents: wm agents should pin `model:` in their frontmatter rather than rely on the caller.
- Worktree isolation that depends on the model passing the right parameter failed in practice (GSD incident #3045) and was fixed with a hook; if wm ever allows parallel implementers it should enforce isolation in a PreToolUse hook, not in prompt text.

### Gaps
- No framework publishes measured per-role model comparisons (for example Sonnet vs Opus as implementer on precise specs); the only numbers are DeepSWE (generic long-horizon tasks) and Superpowers' unquantified guidance.
- I did not verify whether DeepSWE has Sonnet 5.5 or Opus 5.5 entries beyond the summarised extract.
- Kiro: whether parent hooks fire on sub-agent tool calls is unverified (the docs list hook triggers among items isolated per sub-agent), and I did not test any Kiro behaviour myself.

## 4. How does each framework verify quality (instructions, checklists, tests, hooks, CI), and is anything deterministic?

### Takeaway
In every framework the core verification is prose that the model is asked to follow (checklists, analyze/verify/converge passes, review subagents, "verification before completion" skills). Deterministic enforcement exists in three places only: structural validators and state scripts (OpenSpec `validate`, BMAD `tickets.py`, GSD `gsd-tools check`), a minority of real Claude Code hooks (GSD Core guards, Superpowers' SessionStart bootstrap, Spec Kit's new runtime-events layer and community Quality Gates), and independent CI. Three first-party sources independently report that agents skip or reinterpret instruction-level steps: Microsoft's Spec Kit extension study (on-demand commands invoked in 0 of 30 autonomous runs), GSD's incident reports (an agent "reasoned past" an advisory and a planner overwrote a roadmap), and BMAD's own context-file research (an unaided skill "never invoked in 56% of cases"). GSD's maintenance log also shows that deterministic gates are costly to keep correct (fail-open bugs, per-framework test-report adapters).

### Cited Findings

#### Context: what Claude Code itself guarantees (official docs, fetched 2026-10-06)
- "Claude treats [CLAUDE.md and auto memory] as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)).
- Command hooks: "Exit 2 means a blocking error"; "Any other exit code doesn't block on its own for most hook events"; a timed-out `PreToolUse` command hook "doesn't block; the call continues through normal permission flow"; default command-hook timeout 600 s; `SubagentStop` and `Stop` hooks can block with `decision: "block"` and a `reason`; plugin hooks (`hooks/hooks.json`) run inside subagents too, with `agent_id` and `agent_type` in the input; all matching hooks run in parallel ([Claude Code hooks reference](https://code.claude.com/docs/en/hooks)).
- Stop-hook limits (confirmed 2026-10-06): "Claude Code applies an 8-consecutive-continuation cap: after stop hooks have continued the turn eight times in a row, Claude Code overrides the next block and ends the turn"; the cap can be raised with `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`; Stop and SubagentStop hooks receive `stop_hook_active` ("true when Claude Code is already continuing as a result of a stop hook"), and SubagentStop receives `agent_id`, `agent_type`, `agent_transcript_path` and `last_assistant_message` ("the text content of the subagent's final response, so hooks can access it without parsing the transcript file") ([hooks reference, Stop input](https://code.claude.com/docs/en/hooks)). The page text I read describes the cap for stop hooks generally; I could not confirm from it whether SubagentStop shares the same counter, so that needs a test before wm relies on it.
- Skill descriptions are loaded into context every turn and the combined `description` + `when_to_use` is truncated at 1,536 characters; full skill bodies load only when invoked ([Claude Code skills docs](https://code.claude.com/docs/en/skills)). A GSD triage memo (2026-05-12) reports a default listing budget of 1% of the context window (~2,000 tokens at 200k) beyond which "the harness silently truncates the tail", and that GSD's 66 skills alone consumed about 60% of it; this is a third-party claim about Claude Code and I did not find it in Anthropic's docs ([GSD memo](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/research/2026-05-12-skill-surface-budget.md)).

#### Spec Kit
- Core quality steps are prompts: `clarify`, `checklist` ("unit tests for your requirements"), `analyze` (read-only, "Constitution Authority"), `converge` (append-only), and `implement`'s own step 9 "Validate that tests pass and coverage meets requirements" ([agentic-sdd.md](https://github.com/github/spec-kit/blob/main/docs/reference/agentic-sdd.md), [implement.md](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)).
- Extension "hooks" in `.specify/extensions.yml` are prompt-level: the command template tells the model to read the YAML, print an `EXECUTE_COMMAND:` block for mandatory hooks and then "actually invoke the hook... Emitting the block alone does not run the hook" ([implement.md](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)); `auto_execute_hooks` "is currently reserved and is not consulted" ([extensions.md](https://github.com/github/spec-kit/blob/main/docs/reference/extensions.md)).
- Deterministic pieces: the workflow engine's `gate` (human approval), `shell` steps and JSON run state ([workflows.md](https://github.com/github/spec-kit/blob/main/docs/reference/workflows.md)); and, since v0.15.0 (July 2026), an "agent-native runtime events layer" in which an event dispatcher (`.specify/events.py`) plus per-agent adapters write native hook configuration (for Claude Code `.claude/settings.json`, events `session_start`, `pre_tool_use`, `post_tool_use`, `user_prompt_submit`, `stop`, `session_end`) from `events:` declared in `extension.yml` ([July 2026 newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-July.md), [claude integration](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/claude/__init__.py)).
- Community enforcement: "Quality Gates (Enforcement Layer)" (spec-gates, 3 stars, MIT) builds "one policy file and one verify entrypoint for identical results" at the agent boundary (Claude Code `PreToolUse` block, `PostToolUse` auto-format, `Stop` "refuse to end with failing checks"), git boundary (pre-commit) and CI boundary, with attestations (policy SHA-256, resolved tool versions, candidate versus checked file counts), 15 "canaries" that plant known violations and require the gate to reject each, a "no-op signature" check for "a gate that passed while checking zero of its candidate files", and executable acceptance criteria as fenced `accept` shell blocks in `tasks.md` ([README](https://github.com/schwichtgit/spec-gates/blob/main/README.md)). Others: Verify Tasks Extension ("phantom completions: tasks marked [X] with no real implementation"), TDD Extension ("recorded red and green evidence, and mutation-checked test strength"), CI Guard ("block merges on gaps"), Architecture Governance ("read-only, fail-closed validator") ([community/extensions.md](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)).
- Maintainer statement: trust boundaries "remain guidance rather than enforcement" ([manorrock.com](https://www.manorrock.com/blog/2026/08/21/spec_kit_turns_one.html), secondhand); a `shell` workflow step "runs a local command with your privileges. There is no capability sandbox" ([workflows.md](https://github.com/github/spec-kit/blob/main/docs/reference/workflows.md)); a catalog listing "did not mean its code had been audited or endorsed" ([history.md](https://github.com/github/spec-kit/blob/main/docs/history.md)).

#### OpenSpec
- `openspec validate [--strict]` is a deterministic structural check (a requirement "must contain SHALL or MUST keyword", required "## Purpose" and "## Requirements" sections, scenarios; a requirement over 500 characters is a warning that fails `--strict`), and `status`, `instructions`, `list`, `validate` emit JSON for agents ([constants.ts](https://github.com/Fission-AI/OpenSpec/blob/main/src/core/validation/constants.ts), [agent-contract.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/agent-contract.md), [release v1.14.1](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.14.1)). `/opsx:verify` is an LLM pass that "reports completeness, correctness, and coherence without blocking anything" ([editing-changes.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/editing-changes.md)). No hooks: my search of the tarball found no use of Claude Code hook events ([repo](https://github.com/Fission-AI/OpenSpec)).
- A telling fix in v1.0.0: "JSON instruction output now separates context/rules from template (AI was copying constraint blocks into artifact files)" ([release v1.0.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.0.0)).

#### BMAD
- Review is a multi-lens LLM pass followed by a triage that must "Verify the claimed consequence at the named location", "Assign severity", "Dismiss noise, refuted claims, and unsubstantiated claims, with a recorded reason - never silently" and route survivors to patch / defer / decision needed ([review-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md)); a "verification-gap" lens asks "if this behavior broke, would any test fail?" and was "blind validat[ed] against seven real commits from a production HIPAA platform" ([CHANGELOG v6.11.0](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md); vendor claim, n=7).
- Typed halt conditions for the unattended worker: `unclear intent`, `intent gap`, `no subagents`, `implementation verification failed`, `plan failed ready-for-development standard`, `review repair loop exceeded 5 iterations (non-convergence)`; on an intent gap the attempted change "is first saved as a patch file beside the plan" as evidence ([autonomous-development-loops.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/autonomous-development-loops.md)).
- Stop rule: "Non-trivial findings on a third pass of agentic review usually mean something is wrong upstream of this change: weak internal design, a contradiction, or ambiguity in the rules. Fix that instead of running another pass" ([review-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md)).
- Deterministic parts: ticket and sprint state in Python scripts (`tickets.py`, sprint planning "moved into a tested Python script"); no Claude Code hooks in the repository ([CHANGELOG v6.11.0](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)).
- Official docs argue that instruction files rarely help: "Measured present versus absent, repository instruction files show no improvement in success rate and +20% inference cost", but "a compressed documentation index in AGENTS.md" scored 100% versus 53% with no documentation, and "The unaided skill was never invoked in 56% of cases... Agents often skip retrieval they have to choose" ([theory-of-project-context.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/existing-codebases/theory-of-project-context.md)). These cite external studies without links; verify against the evidence section below before relying on them.

#### cc-sdd
- Skill-level gates: `kiro-review` (spec compliance, boundary fit, "mechanical verification", RED-phase evidence), `kiro-verify-completion` ("Fresh-evidence gate before success claims", returns VERIFIED / NOT_VERIFIED / MANUAL_VERIFY_REQUIRED), `kiro-validate-impl` (GO / NO-GO). The Feature Flag Protocol forces RED with the flag OFF ("If tests pass with flag OFF, the tests are not testing the right thing. Rewrite") ([kiro-impl SKILL.md](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/claude-code-skills/skills/kiro-impl/SKILL.md), [skill-reference.md](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/skill-reference.md)). All are prose; the docs concede "A skill installation alone does not prove independent review" ([skill-reference.md](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/skill-reference.md)). The controller discovers validation commands from project scripts, task runners and CI files ("Prefer commands already used by repo automation") ([kiro-impl SKILL.md](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/claude-code-skills/skills/kiro-impl/SKILL.md)).

#### Superpowers
- Behaviour is steered by a `SessionStart` hook that injects the `using-superpowers` bootstrap ("If you think there is even a 1% chance a skill might apply... you ABSOLUTELY MUST invoke the skill") on `startup|clear|compact`; everything after that is instruction ([hooks.json](https://github.com/obra/superpowers/blob/main/hooks/hooks.json), [using-superpowers SKILL.md](https://github.com/obra/superpowers/blob/main/skills/using-superpowers/SKILL.md)). Deterministic helpers: `task-brief`, `review-package` (rejects empty ranges), ledger scripts.
- Self-testing: the repo ships headless Claude Code tests (`claude -p`) and a token analysis script (`analyze-token-usage.py`); skills were "pressure tested" with scenarios such as a "$5k per minute" outage to see whether agents still consult skills ([tests/claude-code/README.md](https://github.com/obra/superpowers/blob/main/tests/claude-code/README.md), [blog](https://blog.fsck.com/2025/10/09/superpowers/)).
- Release notes (v6.4.1, 2026-09-18) report probe findings: "When a task named one test file, sessions ran only that file in 11 of 12 probe runs, so a broken test next door went unseen. The skill now says to run the project's test command and report every failure by name"; "In evals, every implementer shipped the same crash on an input the spec implied but never named" ([RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)); maintainer-run, small n, no raw data.

#### GSD Core (the most hook-heavy framework)
- Hooks directory contains blocking and advisory guards: agent-isolation guard, worktree-path guard, write guard, read guard, secret-read guard, prompt guard, commit-format validator (opt-in), phase-boundary hook, context monitor ([hooks/](https://github.com/open-gsd/gsd-core/tree/HEAD/hooks)). Even here most are advisory or opt-in: the workflow guard "is a SOFT guard for edits - it advises, not blocks" with "ONE hard block" that "fails CLOSED on internal error (#3504)... a thrown error exits 2 (block), not 0" ([gsd-workflow-guard.js](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-workflow-guard.js)).
- Why hooks: "A prose backstop cannot fix a prose defect - it is the same class of artifact the model may equally skip" ([gsd-agent-isolation-guard.js](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-agent-isolation-guard.js), issue #3045); the write guard exists because "a planner read a ~16-line window of ROADMAP.md and Write-overwrote the whole 292-line file with it - three milestones of committed history destroyed" and "an agent [read] the advisory, classif[ied] it as non-binding, and reason[ed] past it" (#973); its stated bound: it "stops accidental and single-shot collapse, not a determined agent" ([gsd-write-guard.js](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-write-guard.js)). A guard "that cannot verify must not answer 'safe'" (#3050 lesson) ([gsd-agent-isolation-guard.js](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-agent-isolation-guard.js)).
- Measured hook-failure data in a 2026-10-02 research memo (issue #5180): "117 `hook_cancelled` in ~25 days, durationMs min 5.4 s, median 15.4 s, p90 54 s, max 84.3 s; 23 hit blocking gates, 8 of them worktree-path-guard"; "a hook killed by the host and a hook that fails open on its own internal probe timeout have the SAME effect (tool call proceeds)"; fix: blocking guards registered with a 120 s host timeout and a 5 s per-git-probe budget, plus a test that runs each guard as a real subprocess and asserts the budgets ([memo](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/research/2026-10-02-git-probe-timeout-blocking-guards.md), [CHANGELOG 1.16.0](https://github.com/open-gsd/gsd-core/blob/HEAD/CHANGELOG.md)). The numbers come from one maintainer's machine ("#3981 dev machine") and a Windows CI run, so they show failure modes, not rates.
- Deterministic gates in `gsd-tools check/verify`: decision coverage, UI safety, TDD review checkpoint, `tdd-red-evidence` (requires "a complete supported report and a matching target failure" and parses TAP, JUnit XML, swift-testing and Python unittest text), verify artifacts/plan-structure/key-links, post-execute drift ([ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/ARCHITECTURE.md), [FEATURES.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/FEATURES.md)). In TDD mode the executor requires a RED commit before the GREEN commit and "fails fast if tests pass unexpectedly during RED" ([FEATURES.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/FEATURES.md)).
- Maintenance cost of gates, from the v1.16.0 changelog (2026-10-05): "A gate verb that failed no longer exits 0, and a gate that could not read its evidence no longer passes"; a real red from `python -m unittest` or `swift test` or Vitest "was misreported as zero tests discovered, permanently blocking GREEN"; "Blocking PreToolUse guards no longer silently allow a denied edit on a slow host"; and a validator bug where exported environment variables "silently accept[ed] a non-conforming commit" ([CHANGELOG](https://github.com/open-gsd/gsd-core/blob/HEAD/CHANGELOG.md), [gsd-validate-commit.sh](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-validate-commit.sh)).
- Prose-defined formats drift even inside one run: "Two independently-invented, mutually incompatible disposition formats were observed across two consecutive rounds of the same phase, each written by a different planner subagent instance improvising from prose alone"; fix: one canonical shape plus a parity test "that fails if the three drift apart" ([FEATURES.md #3806](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/FEATURES.md)). Logic restated as prose in several workflows "had already drifted between two backends", so GSD moves it into "one code-owned computation" (`phase.tdd-applicable`) ([FEATURES.md #4273](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/FEATURES.md)).

#### Kiro (AWS)
- Hooks come in two action types (confirmed): an "Agent Prompt" action sends a prompt to the agent and "trigger[s] a new agent loop", consuming credits, while a "Shell Command" action runs locally, is deterministic and consumes no credits, with a configurable timeout (default 60 seconds, 0 disables it); the docs advise shell commands "when you want to run a specific command or perform a deterministic set of actions". Triggers (confirmed): Prompt Submit, Agent Stop, Session Start and End, Pre Tool Use and Post Tool Use (tool categories read, write, shell, web, spec or `*`, prefixes `@mcp`, `@powers`, `@builtin`, regex patterns), File Create/Save/Delete ("File triggers respond only to changes made by the agent"), Pre/Post Task Execution and Manual; config is `.kiro/hooks/*.json` v1 (reported) ([actions](https://kiro.dev/docs/hooks/actions/), [types](https://kiro.dev/docs/hooks/types/), [hooks docs](https://kiro.dev/docs/hooks/)). Exit-code semantics are inconsistent in Kiro's own pages: the actions page says a non-zero exit "blocks tool invocation for Pre Tool Use hooks and blocks prompt submission for Prompt Submit hooks", the types page says other exit values "display warnings", the CLI 2.x reference says exit 2 blocks preToolUse only, and the docs disagree on whether a Stop hook can block (partly reported) ([2.x reference](https://kiro.dev/docs/cli/2x-reference/), [hooks migration](https://kiro.dev/docs/cli/v3/hooks-migration/)). The Kiro changelog confirms a `SessionEnd` hook trigger added in CLI 2.25.0 (2026-09-28) ([changelog](https://kiro.dev/changelog/)).
- Permission model (reported): deny beats ask beats allow across scopes; compound shell commands are split before matching; workspace rules are stored outside the repository ("A cloned repo cannot inject permission rules") ([permissions docs](https://kiro.dev/docs/permissions/)). Since IDE 1.2.4 (2026-09-30, confirmed) the agent "asks before modifying agent/Hook/Power files or `.kiro/workflows/` recipes" even when broader file permissions allow the write ([changelog](https://kiro.dev/changelog/)); the backstory is a July 2025 prompt-injection code-execution flaw via agent-edited trusted-command and MCP configuration, fixed in 0.1.42 (reported) ([Embrace The Red](https://embracethered.com/blog/posts/2025/aws-kiro-aribtrary-command-execution-with-indirect-prompt-injection/)).
- Open user-reported defects in the enforcement layer, all unresolved on 2026-10-06 (issue titles confirmed; bodies read only for #11786): #11050 "UserPromptSubmit hook exiting non-zero does not block the prompt (docs say it does)"; #10649 "inclusion: always in steering front-matter does not reliably load files into model context"; #11786 a Spec "Run all tasks" sub-agent "ran unattended for about 7 hours, burned an estimated 1,000+ credits, and then was silently killed by the 300-iteration limit", after which "Kiro then reported the execution as succeeded" and "the task checkbox in `tasks.md` was changed to `[x]`"; #11804 "design loop spent credits, never wrote design.md" ([#11050](https://github.com/kirodotdev/Kiro/issues/11050), [#10649](https://github.com/kirodotdev/Kiro/issues/10649), [#11786](https://github.com/kirodotdev/Kiro/issues/11786), [#11804](https://github.com/kirodotdev/Kiro/issues/11804)). These are single-reporter bug reports (practitioner evidence), not confirmed by AWS.
- Workflows add deterministic loop control (JSON verdict file, iteration cap, abort on cap) but the docs themselves say the caps "do not prove quality" ([patterns docs](https://kiro.dev/docs/workflows/patterns/)).

#### Taskmaster and Conductor
- Taskmaster: dependency validation and next-task selection are code (`validate-dependencies`, `fix-dependencies`, `next`); the `review` status plus `task-checker` agent (Sonnet) is an LLM pass that "run[s] compilation and build commands" and tests before a task may be `done` ([README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md), [task-checker.md](https://github.com/eyaltoledano/claude-task-master/blob/main/packages/claude-code-plugin/agents/task-checker.md)); its MCP server of 36 tools costs ~21,000 tokens of context in the default `all` mode (7 tools / ~5,000 tokens in `core`) ([README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md)).
- Conductor: plan.md checkboxes and a configurable `workflow.md` (TDD, commit strategy) with no enforcement layer ([README](https://github.com/gemini-cli-extensions/conductor/blob/main/README.md)).

### Inferences
- The strongest convergent evidence for wm's design is negative: instruction-only steps are skipped (Microsoft 0/30 on-demand command invocations; GSD advisory reasoned past; BMAD skill never invoked 56%). Only enforcement outside the model (hooks, scripts, CI) or always-on context changed outcomes in those reports.
- A done-gate that "denies the handback while gates fail" is the same pattern as spec-gates' `Stop` boundary and GSD's fail-closed legs, so it is well precedented; the lessons to copy are: fail closed on internal errors (exit code 2 or JSON `decision: block`, never a plain non-zero exit), register generous hook timeouts for blocking hooks because a timed-out PreToolUse hook silently allows the call, add a "no-op" check (the gate ran and examined at least one file or test), keep a canary suite that proves the gate still rejects known violations, and test hooks as real subprocesses on Windows.
- A done-gate that blocks the implementer's handback must be designed around Claude Code's own limits: after eight consecutive stop-hook continuations the next block is overridden (unless the cap is raised), so wm should convert "gate still failing after N attempts" into an explicit BLOCKED handback with the gate output attached, and have the lead (or a PostToolUse/lead-side step) re-run the gates after any handback rather than trust that the hook always held. SubagentStop's `last_assistant_message` makes the fixed-format report machine-checkable without transcript parsing.
- Independent studies of overclaiming (OverclaimBench: 80.4% of incomplete runs misleading; second-party confirmation cutting false success from 45-48% to 3%) and of grader-versus-maintainer gaps (METR: about 24 points) say the same thing as the framework incident reports: completion must be established by a party other than the implementer, using evidence the implementer cannot edit.
- Parsing the implementer's fixed-format report in a hook would remove a failure class that cc-sdd handles by re-dispatching and GSD handles by parity tests; a machine-checkable report is cheaper than a prose convention.
- Expect gate maintenance to be a real cost: GSD needed per-format test-report adapters and several fail-open fixes. For wm, delegating to "the project's gates" (the commands the repo already runs) avoids owning those adapters, which is also what cc-sdd and Superpowers 6.4.1 converged on ("the project's suite defines green").

### Gaps
- No framework reports a measured false-negative rate for its own gates; GSD's `canary`-style positive-control ratchet and spec-gates canaries are the closest.
- BMAD's docs cite their studies without links; they correspond to the ETH Zurich AGENTS.md paper (arXiv 2602.11988, "over 20%" extra cost and no general success gain, confirmed) and Vercel's AGENTS.md evals (100% versus 53%, skills uninvoked in 56% of cases, vendor claim, reported); see the measured-outcomes section.
- Whether Claude Code's 8-continuation cap also applies to SubagentStop hooks, and whether the cap counter resets between subagents, is untested here.
- Kiro: the Stop-hook blocking contradiction in its own docs is unresolved, and the hook-failure issues are unverified single reports.

## 5. How does each framework store decisions, history and learnings, and how does it handle brownfield (existing) versus greenfield projects?

### Takeaway
Decision and learning storage is the weakest part of most frameworks: Spec Kit, Kiro-style specs and cc-sdd keep per-feature folders as history and one global "constitution/steering" file as memory; OpenSpec has the only merge-into-source-of-truth plus dated-archive design; BMAD (2026) and GSD Core have the most developed learning mechanisms (BMAD's admission-tested `record`/`audit` of agent mistakes, GSD's `LEARNINGS.md`, debugger knowledge base and review-dispositions ledger). For brownfield, the field has converged on "do not document the whole codebase; spec only the change, let the agent read code, and keep a small verified context file", and BMAD's docs now argue that generated documentation "makes agents worse".

### Cited Findings

#### Decisions, history and learnings
- Spec Kit: `.specify/memory/constitution.md` is versioned (version, ratified, last-amended fields) and governs later phases; feature folders under `specs/` are the history (flow-forward model keeps each folder "intact for audit, comparison, or explaining how the project reached its current state"); `research.md` holds technical decisions read by `implement`; there is no built-in ADR or learning loop ([constitution-template.md](https://github.com/github/spec-kit/blob/main/templates/constitution-template.md), [spec-persistence.md](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md), [implement.md](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)). Community fills the gap: adrkit ("Pulls the decisions governing this work into agent context, checks produced plans against them, and drafts an ADR from a plan artifact"), Memory MD ("durable decisions, bugs, and project context"), Archive Extension ("Archive merged features into main project memory, resolving gaps and conflicts"), Retrospective Extension ("spec adherence scoring, drift analysis, and human-gated spec updates") ([community/extensions.md](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)). The constitution guidance warns "Do not invent standards merely to fill the constitution template. The constitution governs later planning and analysis, so unrealistic rules create noise" ([existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/guides/existing-projects.md)).
- OpenSpec: archived changes in `openspec/changes/archive/<date>-<name>/` keep "the full context of every change - not just what changed, but the proposal explaining why, the design explaining how, and the tasks showing the work done", and `specs/` accumulates "organically as changes are archived"; design.md templates include "Architecture Decisions" entries; `config.yaml` rules inject standing constraints per artifact ([concepts.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md), [opsx.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md)). No learning loop.
- BMAD: `bmad-project-context` writes "one small verified block" into `AGENTS.md` between `<!-- bmad:context -->` markers, never commits, and has intents `setup`, `refresh`, `record` and `audit`: "Record the moment an agent gets something wrong. A pitfall goes in only when someone has seen the mistake. A scan finding that looks like a trap becomes a question, not a line"; "Audit... re-checks and cuts; the block ends smaller or equal, never larger"; "A rule stays until what it is about is gone, or you retire it. 'Nothing broke lately' is never a reason to delete one"; admission test: "what is expensive to rediscover, or that the agent learns only after it has already gone wrong" ([set-and-maintain-project-context.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/existing-codebases/set-and-maintain-project-context.md), [CHANGELOG v6.11.0](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)). Plan files keep a triage log (verdict plus evidence for every review finding), `deferred` findings with severity, `baseline_revision` and `risk`; `bmad-retrospective` closes epics against their own artifacts ([autonomous-development-loops.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/autonomous-development-loops.md), [CHANGELOG v6.12.0](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)).
- Agent OS: standards are the memory ("Standards... unchanged" in v3): short markdown files under `agent-os/standards/<area>/` with an `index.yml`, produced by `/discover-standards` from the codebase and injected on demand with `/inject-standards` into conversations, plans or skills; a sync script pushes project standards back to base profiles ([discussion #310](https://github.com/buildermethods/agent-os/discussions/310), [inject-standards.md](https://github.com/buildermethods/agent-os/blob/main/commands/agent-os/inject-standards.md)).
- cc-sdd: steering files (`product.md`, `tech.md`, `structure.md` plus custom) are project memory; "When a task reveals cross-cutting insights... the finding is recorded under `## Implementation Notes` in `tasks.md` and injected into subsequent implementer prompts"; debug findings are recorded there too ([skill-reference.md](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/skill-reference.md)).
- Superpowers: a run "ledger" records every conflict ruling as `Ruling: <what you decided> - <why> - <what it costs if wrong>`; "The ledger is your recovery map... After compaction, trust the ledger and `git log` over your own recollection"; the author's own 2025-10-09 post says the cross-session memory system has "all the pieces" written but "haven't had time to wire them together" ([SKILL.md](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md), [blog](https://blog.fsck.com/2025/10/09/superpowers/)).
- GSD Core: `.planning/` holds PROJECT, REQUIREMENTS, ROADMAP, STATE and per-phase CONTEXT (decisions captured in Discuss), plans, summaries and verification files; `/gsd-extract-learnings N` writes `{phase}-LEARNINGS.md`; `gsd-debugger` appends every resolved session to `.planning/debug/knowledge-base.md`; the "Review Dispositions Ledger" is append-only ("a later round adds a new row naming what it supersedes rather than editing or deleting"); a blocking "Decision coverage gate" requires every decision in CONTEXT.md `<decisions>` to appear in a plan, and a non-blocking one checks decisions against shipped artifacts ([COMMANDS.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/COMMANDS.md), [FEATURES.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/FEATURES.md), [ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/ARCHITECTURE.md), [CHANGELOG 1.16.0](https://github.com/open-gsd/gsd-core/blob/HEAD/CHANGELOG.md)). The plan phase also runs a "Package Legitimacy Gate: registry-API verdict on every package; [SLOP] removed, [SUS]/[ASSUMED] flagged" ([ARCHITECTURE.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/ARCHITECTURE.md)); the Spec Kit community has a similar "Version Guard" ("Verify tech stack versions against live npm registries") ([community/extensions.md](https://github.com/github/spec-kit/blob/main/docs/community/extensions.md)).
- Taskmaster: `update-subtask` "appends new information to the existing subtask details, marking it with a timestamp"; `update --from=N` rewrites future tasks; tags isolate workstreams ([command-reference.md](https://github.com/eyaltoledano/claude-task-master/blob/main/docs/command-reference.md), [tutorial.md](https://github.com/eyaltoledano/claude-task-master/blob/main/docs/tutorial.md)).
- Adjacent decision tools: Haft (1.4k stars) stores typed decision records ("which options were compared, which decisions the human made, what evidence supports them, and what has gone stale") behind MCP gates ([README](https://github.com/m0n0x41d/haft/blob/main/README.md)); moai-adk records "Decision memory + lessons" after each run and says it turns "observation into rules" ([README](https://github.com/modu-ai/moai-adk/blob/main/README.md)).

#### Brownfield versus greenfield
- Spec Kit: adopt in place with `specify init --here --force --integration <key>` on a branch; the constitution should come from evidence ("README, architecture decisions, contribution guide, and CI configuration"); start with "a bounded first change"; the spec "defines the change you intend to make, not a retroactive specification of every existing behavior" ([existing-projects.md](https://github.com/github/spec-kit/blob/main/docs/guides/existing-projects.md)). Maintainer: the brownfield on-ramp "could be smoother" ([manorrock.com](https://www.manorrock.com/blog/2026/08/21/spec_kit_turns_one.html)). Independent: Boeckeler found the agent "frequently ignored existing code descriptions, generating duplicates instead" ([Fowler site](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), 2025-10-15, via fetch summary).
- OpenSpec: "brownfield-first"; "You do not document your whole codebase to start. You write specs only for what you're about to change"; specs "start nearly empty and accumulate"; `/opsx:explore` maps the area first and `/opsx:onboard` guides a first change ([existing-projects.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/existing-projects.md)).
- BMAD: "Modern agents are trained very well to get knowledge from code. Feeding them textual descriptions of things they can already read there creates contradiction, ambiguity, and context-window bloat. That, oddly enough, includes the original greenfield context (PRD etc). Keep it archived... out of reach of an ordinary change"; `bmad-document-project` is deprecated in favour of `bmad-project-context`; "Build Follows What It Finds" and a pattern you dislike but do not plan to change should not be mentioned because "Hoping it modernizes on its own continues the pattern" ([start-in-an-existing-codebase.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/existing-codebases/start-in-an-existing-codebase.md)).
- Agent OS: `/discover-standards` "surface[s], suggest[s], and create[s] standards from your codebase" ([discussion #310](https://github.com/buildermethods/agent-os/discussions/310)).
- cc-sdd: "Extend an existing system": `kiro-steering`, then discovery or spec init, optional `kiro-validate-gap`, design, tasks, impl ([README](https://github.com/gotalab/cc-sdd/blob/main/README.md)). Superpowers' "Bounded" path requires that "the flow you are changing is already here to read" ([brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)).
- GSD Core: `/gsd-onboard` for existing repos, codebase mapping by a `gsd-codebase-mapper` agent and the drift gate that re-maps when structure changes ([README](https://github.com/open-gsd/gsd-core/blob/HEAD/README.md), [FEATURES.md](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/FEATURES.md)). Conductor: "Intelligent initialization for both new (Greenfield) and existing (Brownfield) projects" ([README](https://github.com/gemini-cli-extensions/conductor/blob/main/README.md)).
- Practitioner field report on spec accumulation (opinion, self-measured): 94 spec folders with 238 markdown files and 15,225 lines, "I haven't reopened a single one since it was marked complete"; "Four are superseded. None of them says which"; Claude "ignored the existing specs entirely, instead reconstructing intent from the codebase"; his "living spec" rewrite cut 238 files to 14 and 15,225 lines to 3,112, claiming "approximately 60 to 68% leaner" with identical correctness scores ([dev.to, 2026-09-11](https://dev.to/alfredoperez/i-wrote-238-specs-and-never-read-one-again-5705), via fetch summary). A Korean field report cited in Spec Kit's own newsletter describes 13 features growing `specs/` to 12,931 lines, 73% of the 17,590-line `src/`, and a move to a self-built harness ([August 2026 newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-August.md), original not read).

#### Kiro (AWS)
- Memory is steering: `.kiro/steering/*.md` with "Generate Steering Docs" writing `product.md`, `tech.md`, `structure.md`; inclusion modes `always`, `fileMatch` (glob), `manual` and `auto` (matched on description); global `~/.kiro/steering` with workspace precedence; AGENTS.md supported (2025-10-31, nested since August 2026); live references `#[[file:path:10-25]]` (reported; the live-reference syntax also appears in the CLI 2.27.0 changelog entry, confirmed) ([steering docs](https://kiro.dev/docs/steering/), [changelog](https://kiro.dev/changelog/)). A user reports `inclusion: always` is not reliably applied during spec creation and that rules work when duplicated into AGENTS.md (issue open, title confirmed) ([#10649](https://github.com/kirodotdev/Kiro/issues/10649)).
- Decisions and history: no ADR concept; an independent write-up recommends adding ADRs manually and warns auto-generated ones are "technically correct and completely useless" (reported) ([DoiT](https://www.doit.com/blog/spec-driven-development-with-kiro-ai-code-ownership)). Kiro Web "Memory" learns from the task creator's PR comments and is account-level, not stored in the repository (reported) ([memory docs](https://kiro.dev/docs/web/memory/)).
- Learning-pipeline hygiene, from Kiro's own agent-triage team (reported): their lesson store once ingested raw ticket text and was fixed with "schema validation before writing, plus a nightly prune"; "Unless curated... a learning pipeline compounds garbage as efficiently as knowledge" ([blog, 2026-08-21](https://kiro.dev/blog/trust-agent-triage/)); the Crew product caps lessons at 50 with deduplication and a confidence threshold of 0.8 ([Crew memory docs](https://kiro.dev/docs/crew/features/memory/)).
- Brownfield: "Set up steering for this project" analyses the repository and writes the three foundation files (2025-07-15 post); design-first was added because "especially when working on existing, brownfield apps, some developers came in with the technical architecture already mapped out" (2026-02-18); bugfix specs read the codebase for root cause (reported) ([deep-dive post](https://kiro.dev/blog/from-chat-to-specs-deep-dive/), [specs/bugfix/design-first post](https://kiro.dev/blog/specs-bugfix-and-design-first/)). Docs steer greenfield work to requirements-first and existing code to bugfix or design-first (reported) ([specs docs](https://kiro.dev/docs/specs/)).

### Inferences
- wm's ADR plus path-scoped rules plus learning loop is more complete than what any framework ships by default; the closest analogues are BMAD's `record`/`audit` (rule admission requires an observed mistake; audits can only shrink the file) and GSD's decision-coverage gate (decisions must be traced into plans and, non-blocking, into shipped files). Two ideas worth stealing: an explicit admission test for every learned rule (evidence of an observed failure, not a scan finding) and a shrink-only audit pass so rules do not accumulate.
- Accumulation is the shared failure mode of per-feature artifacts (238 files, 73% spec-to-source ratio); a work order that is archived or deleted after merge, with only its durable decisions promoted to ADRs or rules, avoids it. OpenSpec's archive and Spec Kit's "Archive Extension" are both attempts to do that promotion, and neither is automatic.
- Brownfield guidance is consistent: let the agent read code, record only what is expensive to rediscover, and scope specs to the change. wm's `/wm:adopt` should therefore generate a small verified context block and path-scoped rules rather than documentation of the whole repository.

### Gaps
- No framework reports retention data (how many recorded rules stay useful) or measures whether the learning/record mechanisms reduce repeated mistakes.
- I did not read the Korean and Japanese field reports directly; figures come from Spec Kit's newsletter summary.
- No independent brownfield measurement of Kiro exists in what I found.

## 6. How does each framework integrate with Claude Code (slash commands, skills, agents, plugins, hooks, MCP)?

### Takeaway
By October 2026 almost every framework installs as Agent Skills (`.claude/skills/<name>/SKILL.md`) rather than as `.claude/commands` files, and several publish as Claude Code plugins. Real Claude Code hooks are rare: GSD Core ships many, Superpowers ships one SessionStart hook, Spec Kit added an adapter layer in July 2026, and OpenSpec, BMAD, Agent OS, cc-sdd and Taskmaster ship none. Subagent definitions with pinned models appear only in Taskmaster's plugin (three agents) and GSD (33 agents); cc-sdd and Superpowers dispatch subagents dynamically with prompt templates and no static agent files. The platform constraint most likely to bite a plugin author is the shared skill-listing budget.

### Cited Findings

#### Per framework
- Spec Kit: `claude` integration is "Skills-based integration; installs skills in `.claude/skills`" (invoked as `/speckit-*` skills; older releases installed slash commands); the CLI (`uv tool install specify-cli`, `specify init`) is outside the agent; from v0.15.0 an event adapter writes Claude hooks into `.claude/settings.json` ([integrations.md](https://github.com/github/spec-kit/blob/main/docs/reference/integrations.md), [claude integration code](https://github.com/github/spec-kit/blob/main/src/specify_cli/integrations/claude/__init__.py), [July 2026 newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-July.md)). I found no Claude Code plugin manifest in the repository (no `.claude-plugin/` directory in the tarball).
- OpenSpec: `openspec init` "creates skills in `.claude/skills/` (or equivalent)", with `/opsx:*` slash names; v1.0.0 consolidated "8+ scattered config files" into a single `.claude/skills/` directory and stopped generating `CLAUDE.md`, `.cursorrules`, `AGENTS.md`, `project.md`; supports 30+ tools; no hooks and no plugin manifest ([opsx.md](https://github.com/Fission-AI/OpenSpec/blob/main/docs/opsx.md), [release v1.0.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.0.0), [README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md)).
- BMAD: install with `npx skills add bmad-code-org/BMAD-METHOD` or as a Claude Code plugin (`/plugin marketplace add bmad-code-org/bmad-plugins`, then install `bmad-method` and `bmad-core-tools`); a `bmad` hub skill runs `bmad setup` and `bmad status`; requires `uv` (Python 3.11+) for rendered skills; no hooks ([README](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/README.md), [CHANGELOG v6.11.0](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)). A skills-first rewrite shrank core from fourteen to eight skills in v6.11.0, with forwarding shims kept "until the v7 cut" ([CHANGELOG](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/CHANGELOG.md)).
- Agent OS: shell installer copies commands (`discover-standards`, `inject-standards`, `index-standards`, `plan-product`, `shape-spec`) to `.claude/commands/agent-os/`; v2.1 offered `standards_as_claude_code_skills` and an `improve-skills` helper; v3 relies on Claude Code's Plan Mode and AskUserQuestion ([CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md), [commands/agent-os/](https://github.com/buildermethods/agent-os/tree/main/commands/agent-os)). No hooks, no plugin.
- Taskmaster: MCP server (`claude mcp add taskmaster-ai -- npx -y task-master-ai`; 36 tools, ~21k tokens in `all` mode) plus a Claude Code plugin marketplace (`/plugin marketplace add eyaltoledano/claude-task-master`, `/plugin install taskmaster@taskmaster`) containing 46 slash-command files (`/tm:*`, counted in the repository's `packages/claude-code-plugin/commands/`) and three agents with pinned models (orchestrator opus, executor sonnet, checker sonnet); model provider `claude-code/sonnet` needs no API key ([README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md), [CLAUDE_CODE_PLUGIN.md](https://github.com/eyaltoledano/claude-task-master/blob/main/CLAUDE_CODE_PLUGIN.md), [agents/](https://github.com/eyaltoledano/claude-task-master/tree/main/packages/claude-code-plugin/agents)).
- cc-sdd: `npx cc-sdd@latest` installs 17 Agent Skills into `.claude/skills/` (legacy `/kiro:*` commands and `--claude-agent` static subagent files are deprecated); entry skills use `disable-model-invocation: true`; subagents are dispatched dynamically through Claude Code's Agent tool, with prompt templates stored inside the skill (no `.claude/agents/` files); no hooks ([README](https://github.com/gotalab/cc-sdd/blob/main/README.md), [skill-reference.md](https://github.com/gotalab/cc-sdd/blob/main/docs/guides/skill-reference.md), [kiro-impl SKILL.md](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/claude-code-skills/skills/kiro-impl/SKILL.md)).
- Superpowers: official marketplace plugin (`/plugin install superpowers@claude-plugins-official`) and its own marketplace; `plugin.json` plus a `hooks.json` with one `SessionStart` hook (matcher `startup|clear|compact`) that injects the bootstrap; 15 skills; works on 16+ agent harnesses; commercial support offered by Prime Radiant ([README](https://github.com/obra/superpowers/blob/main/README.md), [plugin.json](https://github.com/obra/superpowers/blob/main/.claude-plugin/plugin.json), [hooks.json](https://github.com/obra/superpowers/blob/main/hooks/hooks.json)). Release 6.4.2 removed `CLAUDE.md` because "Claude Code now reads `AGENTS.md` directly, but only when no `CLAUDE.md` exists" ([RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)).
- GSD Core: installer (`npx @opengsd/gsd-core@latest`) writes commands, skills, 33 agents and hook registrations into `.claude/` and `settings.json`; also ships `.claude-plugin/plugin.json`; adds a statusline and context-monitor hook; "The installer is required for cross-runtime compatibility - do not copy files from `agents/` or `commands/` directly" ([README](https://github.com/open-gsd/gsd-core/blob/HEAD/README.md), [plugin.json](https://github.com/open-gsd/gsd-core/blob/HEAD/.claude-plugin/plugin.json), [hooks/](https://github.com/open-gsd/gsd-core/tree/HEAD/hooks)).
- Conductor: `/plugin marketplace add gemini-cli-extensions/conductor` then `/plugin install conductor`; "View Layer UX Adapter" falls back to text menus in Claude Code ([README](https://github.com/gemini-cli-extensions/conductor/blob/main/README.md)).
- claude-code-spec-workflow: 10 slash commands and 4 agents written into `.claude/`; superseded by an MCP server ([README](https://github.com/Pimzino/claude-code-spec-workflow/blob/main/README.md)).
- Kiro is its own IDE (a Code OSS fork) and CLI, not a Claude Code plugin; it runs Claude models through Amazon Bedrock, with Claude Opus 5.5 (2026-09-28) and Sonnet 5.5 (2026-10-02) on the changelog and Fable 5.1 in Enterprise preview at 6x credits (reported for Bedrock and Fable) ([changelog](https://kiro.dev/changelog/), [how Kiro works](https://kiro.dev/docs/how-kiro-works/), [models](https://kiro.dev/docs/models/)). Neither has Anthropic or AWS involvement that I could find beyond model supply.

#### Anthropic's own first-party baseline (same distribution channel wm will join)
- The official plugin directory `anthropics/claude-plugins-official` had 37,470 stars and 4,220 forks on 2026-10-06 and lists, among others, `feature-dev`, `hookify`, `code-review`, `ralph-loop`, `pr-review-toolkit`, `security-guidance` and `claude-md-management` ([API](https://api.github.com/repos/anthropics/claude-plugins-official), [plugins/](https://github.com/anthropics/claude-plugins-official/tree/main/plugins)).
- `feature-dev` is a "systematic 7-phase approach" (discovery, codebase exploration with "2-3 `code-explorer` agents in parallel", clarifying questions, architecture design, implementation, quality review, summary) with three agents that all pin `model: sonnet` and carry read-only tool lists (`code-explorer`, `code-architect`, `code-reviewer`; the reviewer uses "confidence-based filtering to report only high-priority issues") ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/feature-dev/README.md), [code-reviewer.md](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/feature-dev/agents/code-reviewer.md)).
- `hookify` turns "conversation patterns or... explicit instructions" into markdown rule files (`.claude/hookify.<name>.local.md`) with `event`, regex `pattern` and `action: warn | block` ("`warn`... (default)"), taking effect "on the very next tool use" without restart; `/hookify` with no argument "analyzes recent conversation to find behaviors you've corrected or been frustrated by" ([README](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/hookify/README.md)). This is a first-party precedent for converting repeated corrections into deterministic rules.

#### Platform constraints that affect all of them
- Skill descriptions are always in context (truncated at 1,536 characters each) while bodies load on demand ([Claude Code skills docs](https://code.claude.com/docs/en/skills)); GSD's research memo found its own 66 skills used about 60% of a (claimed) default listing budget and responded with a 100-character description cap enforced in CI, a `--minimal` install (6 skills, "~12k tokens of cold-start overhead to ~700") and a plan to emit fewer skills ([GSD memo](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/research/2026-05-12-skill-surface-budget.md)). Claude Code has a `/skill-doctor` command that shows what each skill costs ([skills docs](https://code.claude.com/docs/en/skills)).
- Path-scoped loading exists natively: skills accept a `paths` frontmatter field so they "load automatically only when working with files matching the patterns" ([skills docs](https://code.claude.com/docs/en/skills)), and `.claude/rules/` supports path-specific rules ([memory docs](https://code.claude.com/docs/en/memory)).
- Plugin hooks "merge with your user and project hooks", run in parallel, and fire for subagents' tool calls with `agent_id` and `agent_type` in the payload; hooks can also be declared in skill and subagent frontmatter, where a subagent's `Stop` hook is converted to `SubagentStop` ([hooks reference](https://code.claude.com/docs/en/hooks)).
- Token cost of the integration surface itself is a recurring complaint source: Conductor's README warns of "increased token consumption" ([README](https://github.com/gemini-cli-extensions/conductor/blob/main/README.md)); Taskmaster documents ~21k tokens for its tool schema ([README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md)); a Spec Kit field report counted 18,799 tokens in the standard slash-command templates versus 863 with the bundled `lean` preset ([Spec Kit September 2026 newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-September.md), citing a Medium post that returned HTTP 403 to me, so unverified).

### Inferences
- As a Claude Code plugin wm sits in the same distribution channel as Superpowers (official marketplace), Taskmaster and GSD Core; its differentiator is that it ships subagent definitions with pinned models plus blocking hooks, a combination that only GSD Core and Taskmaster partially have.
- wm should budget its always-loaded surface: few skills with short descriptions, path-scoped rules for repository-specific guidance, and heavy procedures inside skill bodies that load on demand. GSD's experience (66 skills consuming most of a listing budget) shows that plugin sprawl can crowd out other plugins.
- Since Claude Code exposes `agent_type` to hooks, role guards can key on the subagent name; this makes wm's design (guards per role) native rather than a workaround, and no other framework surveyed uses that field in its hooks (GSD guards key on `subagent_type` in the Agent call instead).

### Gaps
- I did not verify the exact default of the skill listing budget in Anthropic documentation; the 1% figure comes from a GSD memo and a third-party blog.
- I did not inspect the BMAD `bmad-skills` repository that, per `bmad-plugins`' description, ships the Claude plugin.

## 7. What are the documented strengths of each framework, and what do users and independent analysts criticise (overhead, token cost, waterfall rigidity, spec bloat, fit for small changes, maintenance burden), with sources?

### Takeaway
Criticism is remarkably consistent across tools and sources. The ten recurring themes are: ceremony out of proportion to the change; token and context cost; slow, waterfall-like flow; review burden and spec accumulation; no way to update or reconcile specs; agents skipping or reinterpreting instructions and falsely reporting completion; review loops that never converge; upgrade churn and maintainer abandonment; telemetry/security hygiene; and shared state under parallel runs. Maintainers have responded in 2026 by adding fast lanes (Spec Kit bug extension and TinySpec, BMAD Build, OpenSpec lite specs, GSD fast/quick, Superpowers bounded path), shrinking scaffolding (Agent OS v3, BMAD v6.11) and adding after-the-fact checks (Spec Kit converge). Praise concentrates on forced up-front thinking, predictability, and (for Superpowers/BMAD review) catching defects, and mostly comes from practitioners rather than measurements. Labels: [V] vendor/maintainer, [I] independent evidence with numbers or verifiable repo facts, [P] practitioner opinion or complaint; issue and reaction counts as of 2026-10-06/07.

### Cited Findings
(Community complaint evidence below was gathered by a delegated researcher from GitHub issues, discussions, Hacker News and blogs; I re-checked 24 of the cited issues and discussions through the GitHub API, confirmed titles, dates, comment/reaction counts and the key numbers in the bodies of #1401, #2943, #1492, #1865, #2017, #1235, #188, #2033, #895 and #743, and marked blog quotes that came through summarisers with a dagger.)

#### 1. Ceremony out of proportion to the change (fit for small changes)
- Spec Kit [P]: issue "Proposal: speckit.tinySpec: a lightweight workflow for small tasks" (2025-11-13, 22 reactions) describes adding one button producing "30 files changed, < 20 actual LOC" ([#1174](https://github.com/github/spec-kit/issues/1174)); another reporter says the tool tries "to create new files and generates hundreds of unnecessary tests" instead of adding a test to the existing structure (2025-09-08, 24 reactions) ([#75](https://github.com/github/spec-kit/issues/75)); a Hacker News commenter likened its output to "Tony Stark building a robot from scratch in a cave when 'just screw this bolt on' would have sufficed" ([HN, 2025-10-17](https://news.ycombinator.com/item?id=45610996)). A community TinySpec extension was merged into the catalog on 2026-04-10 (opt-in, not core) and the README now calls its three processes "independent entry points, not three mandatory phases" ([PR #2147](https://github.com/github/spec-kit/pull/2147), [README](https://github.com/github/spec-kit/blob/main/README.md)) [V].
- Kiro [I]: Boeckeler's hands-on found Kiro turned a small bug into "4 user stories with a total of 16 acceptance criteria", "like using a sledgehammer to crack a nut" ([martinfowler.com, 2025-10-15](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)); Kiro's own docs now concede Quick Spec is for users "defaulting to Vibe mode because the standard Spec flow felt too heavy" and that a plain chat fix is fine for typos (reported) ([quick spec docs](https://kiro.dev/docs/specs/quick-spec/)) [V].
- Superpowers [P]: "creating a trivial model + CRUD endpoint is becoming a 35 minute session. With plain claude code it's done in 2 minutes" (2026-03-15, open, 26 comments, 32 reactions) ([#743](https://github.com/obra/superpowers/issues/743)); "A 5-line file generated 6-7 agent invocations... roughly 10-15x what direct file creation would have cost" ([#1120](https://github.com/obra/superpowers/issues/1120)). The maintainers answered with a bounded path ("No spec file, no implementation plan document") ([brainstorming SKILL.md](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)) [V].
- BMAD [P/V]: a user post says "Full BMAD workflow is overkill" for typo and CSS fixes ([dev.to, 2026-05-27](https://dev.to/bspann/bmad-method-claude-code-how-i-actually-ship-projects-with-spec-driven-ai-development-1eei)†); a Hacker News commenter called it "essentially Waterfall for Agents" (2026-03-04)†; the project's own docs carry the FAQ "Why Does This Take So Long? I Could Plan Mode and Code It in Ten Minutes" ([build-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/build-a-change.md)) and v6.12.0 added "Simple changes now get a two-section spec and finish in one session" ([release](https://github.com/bmad-code-org/BMAD-METHOD/releases/tag/v6.12.0)) [V].
- GSD [P]: an issue noting "nothing in between" quick and full milestone (13 reactions) was closed on 2026-03-17 by adding `--discuss`, `--research` and `--full` flags to quick mode ([GSD #317](https://github.com/gsd-build/get-shit-done/issues/317)) [V].
- OpenSpec [P]: "Even OpenSpec is too heavy for me" and "every change, medium or larger, turns into a large set of multiple markdown documents, each that need review" on a September 2026 Hacker News thread (204 points); the maintainer replied "We'll be updating the experience not too far away to make things a lot more succinct and iterative" ([HN, 2026-09-16](https://news.ycombinator.com/item?id=49734264)).
- Competitor positioning is itself a claim: OpenSpec's README calls Spec Kit "Thorough but heavyweight. Rigid phase gates, lots of Markdown, Python setup" and Kiro "Powerful but you're locked into their IDE and limited to Claude models" ([README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md)) [V, competitor].
- Anthropic's own docs agree with the critique: "Plan mode is useful, but also adds overhead... If you could describe the diff in one sentence, skip the plan" ([best practices](https://code.claude.com/docs/en/best-practices)) [V].

#### 2. Token and context cost
- Spec Kit [I]: `/context` showed about 18.6k tokens of always-loaded command text in Claude Code (2025-12-29) ([#1401](https://github.com/github/spec-kit/issues/1401)); the nine core command templates total 23,703 tokens, with a proposal to compress them 23% to 18,241 (2026-06-11) ([#2943](https://github.com/github/spec-kit/issues/2943)); a Gemini CLI test of `/speckit.specify "hello world"` consumed 1,346,498 tokens with commands and 1,167,811 with skills, mostly cache reads ([#1492](https://github.com/github/spec-kit/issues/1492)); a Discussion reports "5x token usage over a vibe code that just worked" ([#1482](https://github.com/github/spec-kit/discussions/1482)) [P]. The maintainer says Spec Kit "now defaults to Agent Skills", so only skill metadata loads, which makes the 18.6k figure outdated for skills mode while the artifact-efficiency concern "is still valid" (2026-08-31) ([#1401](https://github.com/github/spec-kit/issues/1401)) [V]. A Spec Kit newsletter cites a field report of 18,799 tokens for the standard workflow versus 863 with the bundled `lean` preset (original unreadable, HTTP 403) ([September newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-September.md)).
- BMAD [I]: create-story used "80k-100k tokens per step" with a PRD of about 1,400 lines and architecture of about 4,800 (2026-01-01) ([#1235](https://github.com/bmad-code-org/BMAD-METHOD/issues/1235)); the maintainer promised optimisation "through the use of sub-agents".
- Taskmaster [I]: 59 MCP tools "~45-50k tokens (22-25% of total context)" (2025-10-06), answered by tool-loading modes (`core` about 5k tokens) ([#1280](https://github.com/eyaltoledano/claude-task-master/issues/1280), [README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md)).
- cc-sdd [I]: `kiro-impl` re-reads the whole `tasks.md` every iteration: on a 41-sub-task spec about 283,000 tokens of reads versus about 8,000 for targeted reads (2026-08-24, open) ([#188](https://github.com/gotalab/cc-sdd/issues/188)).
- GSD [P]: "47 MILLION TOKENS. 12hr." for a small app, with the reporter attributing it to agent-chain context multiplication, no runtime feedback loop and "~60KB of planning artifact in every context window" ([gsd-core #655](https://github.com/open-gsd/gsd-core/discussions/655)); Hacker News: "hit the 5-hour limits in ~30 minutes", "burn 10x more tokens", "Plan Mode had a plan and then base implementation in twenty minutes. GSD ran for hours" ([HN, 2026-03-17](https://news.ycombinator.com/item?id=47417804)).
- Superpowers [I]: a user benchmark (4 bugfix tasks, 20 runs per arm, single author) found the 291-line `systematic-debugging` rules cost $0.316 per run versus $0.176 with no instructions, raised verified-repro from 2/20 to 8/20, and left accuracy at 20/20 in every arm; a re-test after the rules were trimmed was a null result ([#2017](https://github.com/obra/superpowers/issues/2017)). The maintainer's 6.0 post (2026-06-15, confirmed) concedes "the most common lament we hear from Superpowers users is that tokens are expensive and Superpowers uses a ton of them" and claims "up to 50% faster and up to 60% cheaper" after an "autoresearch" loop of 25 experiments (about $165, within "36 hours of work" and "$650 of unsubsidized token spend" for the optimisation research itself) tested on Anthropic eval benchmarks, with initial Codex tests showing "no improvement" until an evaluation-isolation problem was fixed ([blog](https://blog.fsck.com/2026/06/15/Superpowers-6/)) [V, unreplicated].
- Conductor [V]: "Conductor's spec-driven approach... can lead to increased token consumption" ([README](https://github.com/gemini-cli-extensions/conductor/blob/main/README.md)).
- Kiro [P, reported]: credit-cost complaints persisted after the 2025 pricing fix ("Review Recursion, and Disproportionate Credit Consumption", 2026-09-20; "Run all tasks" sub-agent burning 1,000+ credits, 2026-10-05) ([#11477](https://github.com/kirodotdev/Kiro/issues/11477), [#11786](https://github.com/kirodotdev/Kiro/issues/11786)).

#### 3. Waterfall rigidity and slowness
- Spec Kit [P]: "I tried openspec - loved it, tried this one - it's sooo slooow" ([#1174](https://github.com/github/spec-kit/issues/1174)); "12 hours babysitting an agent spawned by spec-kit, whereas a plan executed by Claude Code with multiple subagents only took 1 hour" ([#752](https://github.com/github/spec-kit/issues/752)); the maintainer said subagent orchestration belongs in a preset or companion plugin to keep the core agent-agnostic.
- Kiro [P, reported]: "You have to follow them in order" ([dev.to, 2025-09-13](https://dev.to/fikuri/kiro-the-good-bad-and-ugly-part-in-my-personal-experience-1neh)); Kiro's own blog post "Why rigid workflows fail" (2026-02-18) preceded Design-first, Bugfix and Quick Spec ([blog](https://kiro.dev/blog/specs-bugfix-and-design-first/)).
- GSD [P]: "It requires a waterfall process... difficult, and in some cases impossible, to adjust phases/plans" ([HN](https://news.ycombinator.com/item?id=47417804)); OpenSpec positions itself as the fix ("iterative not waterfall") ([README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md)).
- Thoughtworks [I, institutional]: its Technology Radar places spec-driven development in "Assess", describing workflows that are "elaborate and opinionated", noting "some generate lengthy spec files that are hard to review" and warning "We may be relearning a bitter lesson - that handcrafting detailed rules for AI ultimately doesn't scale" (confirmed on the entry page, which labels the volume "Vol. 34, Nov 2025" whereas the delegated researcher identifies the November 2025 edition as Vol. 33; the volume label is therefore uncertain) ([Radar entry](https://www.thoughtworks.com/radar/techniques/spec-driven-development)).

#### 4. Review burden, spec bloat and accumulation
- Böckeler [I]: Spec Kit "created a LOT of markdown files for me to review. They were repetitive", and "To be honest, I'd rather review code than all these markdown files" (via summaries of the article) ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)); Marmelab cites another developer's Spec Kit example where a current-date display became "8 files and 1,300 lines of text" ([Marmelab, 2025-11-12](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)†).
- Practitioner measurements: 94 spec folders, 238 files, 15,225 lines, none reopened ([dev.to, 2026-09-11](https://dev.to/alfredoperez/i-wrote-238-specs-and-never-read-one-again-5705)); a Korean field report cited in Spec Kit's newsletter has 13 features producing `specs/` of 12,931 lines, 73% of `src/` ([August 2026 newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-August.md)); Superpowers plans that carry code grew "from 171 KB to 1,236,229 characters over ~46 h", with plan-editor subagents about 61% of weighted cost and implementers plus reviewers about 7% ([#895](https://github.com/obra/superpowers/issues/895)) [I].
- Superpowers 6.4.2 reversal: plans now "record decisions", because "Some frontier models, including Opus 5.5, could get overzealous during plan writing" ([RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)) [V].

#### 5. No way to update or reconcile specs (spec drift)
- Spec Kit [P]: the most-reacted issue in the repository is "Spec-Driven Editing Flow: Can't Easily Update or Refine Existing Specs" (115 reactions, closed 2026-04-08) ([#1191](https://github.com/github/spec-kit/issues/1191)); "to know what the system does I need to read both specs" (72 upvotes) ([Discussion #152](https://github.com/github/spec-kit/discussions/152)); still open in 2026: agents "rewrite spec.md and regenerate tasks.md. History disappears" and find related requirements by grepping, producing "two live lines for the same behavior" ([#4156](https://github.com/github/spec-kit/issues/4156), [#4164](https://github.com/github/spec-kit/issues/4164)).
- OpenSpec [I]: the deterministic archive merge is itself fragile: a maintainer-authored exploration says "Since June, the merge code... has had 46 fix commits", "Two changes that modified the same requirement lost scenarios (#1246)" and "A bad MODIFIED header passes `validate` and only fails at archive, sometimes weeks later (#1112)" and floats letting agents do the merge ([#2033](https://github.com/Fission-AI/OpenSpec/issues/2033), 2026-10-02, open). Users also ask how to update specs during apply (13 reactions) and for a repair command (24 reactions) ([#684](https://github.com/Fission-AI/OpenSpec/issues/684), [#821](https://github.com/Fission-AI/OpenSpec/issues/821)) [P].
- cc-sdd [I]: widening scope after task generation re-triggered no validation; a spec grew from 55 to 79 acceptance criteria, and a voluntary re-review found 3 blocking defects while "the repair itself introduced five new defects" ([#190](https://github.com/gotalab/cc-sdd/issues/190)).
- Kiro: see section 2 (silent drift; open request to record a git ref) ([#9435](https://github.com/kirodotdev/Kiro/issues/9435)).

#### 6. Agents skip, reinterpret or falsely complete
- Spec Kit [P]: "End of task guardrails are routinely skipped as context fills up", with a commenter noting "Most of us use deterministic solutions... claude code hooks (running tests before every attempt to commit)" (closed by the stale bot 2026-05-08, not fixed) ([#847](https://github.com/github/spec-kit/issues/847)); "After ~770 structured tasks... 2 tasks marked [X] complete where the corresponding code was not completed", named "phantom completions" ([#1865](https://github.com/github/spec-kit/issues/1865)); the maintainer on a swapped library: "Sonnet-class models... are a bit over-eager and tend to step in when they shouldn't" ([#464](https://github.com/github/spec-kit/issues/464)) [V].
- BMAD [P/I]: agents "claimed stories were 'COMPLETE' while having 40-86+ compilation warnings" ([Discussion #157](https://github.com/bmad-code-org/BMAD-METHOD/discussions/157)); Party Mode subagents "mixed accurate and hallucinated findings... indistinguishably", about 13 of 38 claims in one run diverging from source ([#2280](https://github.com/bmad-code-org/BMAD-METHOD/issues/2280)).
- Agent OS [P]: "basically 50/50 whether Claude follows the instructions", with the maintainer agreeing that `/create-spec` "often doesn't wait for my approval" ([Discussion #66](https://github.com/buildermethods/agent-os/discussions/66)); recurring in v3 ([Discussion #325](https://github.com/buildermethods/agent-os/discussions/325)).
- Kiro [P]: silent false success on a runaway sub-agent (section 4) ([#11786](https://github.com/kirodotdev/Kiro/issues/11786)).
- Böckeler [I]: "the agent ultimately not follow[ed] all the instructions" despite elaborate prompts and checklists (via summary) ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).

#### 7. Review loops that do not converge
- BMAD [I]: the code-review workflow forced "3-10 specific issues minimum" so it "structurally could not conclude with 'no issues found'" (fixed in v6.1.0) ([PR #1913](https://github.com/bmad-code-org/BMAD-METHOD/pull/1913)); the unattended worker's follow-up-review rule was "structurally non-convergent - every review pass recommends another" (2026-07-11) ([#2576](https://github.com/bmad-code-org/BMAD-METHOD/issues/2576)); the docs now cap review repair loops at 5 iterations and give a stop rule after a third pass ([autonomous-development-loops.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/autonomous-development-loops.md), [review-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/review-a-change.md)).
- Superpowers [P]: every review finding becoming a plan amendment (hbiagi in #895); the maintainer's 6.0 redesign "combin[ed] the spec compliance and code quality review agents", "pre-bak[ed] the review 'packet'" so reviewers "rarely need to run git" and moved commit-finding instructions into a shell script ([blog, confirmed](https://blog.fsck.com/2026/06/15/Superpowers-6/)).
- Anthropic: "A reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering" ([best practices](https://code.claude.com/docs/en/best-practices)) [V].
- Kiro [P, reported]: "design loop spent credits, never wrote design.md" and the reviewer then reviewed the missing file ([#11804](https://github.com/kirodotdev/Kiro/issues/11804)).

#### Independent long-form analyses, 2025-2026
(Gathered by a second delegated researcher; I re-fetched Scott Logic, Garg/InfoQ, Isenberg/Itzhak, the Radar entry, the SpecMine abstract and Böckeler's article, and mark the rest "reported". These tools change weekly, so findings about tool behaviour older than about six months may be outdated.)
- Böckeler, Thoughtworks, 2025-10-15 [I, hands-on, few tasks]: tested Kiro (3 files), Spec Kit (many files per spec) and Tessl (private beta, spec-as-source) in September 2025; defined spec-first / spec-anchored / spec-as-source; Kiro turned a small bug into "4 'user stories' with a total of 16 acceptance criteria" ("a sledgehammer to crack a nut"); on a Spec Kit feature she "never even finished"; "I'd rather review code than all these markdown files"; the agent "ultimately not follow[ed] all the instructions" (it regenerated existing classes as duplicates and over-followed a constitution article); warned that spec-as-source may inherit "the downsides of both MDD and LLMs: Inflexibility and non-determinism"; asked for "flexibility for a few different core workflows, for different sizes and types of changes" ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html); numbers and quotes partly from the researcher's reading). Possibly outdated because Spec Kit and Kiro have since added bug-fix and design-first paths.
- Eberhardt, Scott Logic, 2025-11-26 [I, n=1] (confirmed): re-created a deleted ~1,000-line feature with Spec Kit (September 2025 version), GitHub Copilot and Claude Sonnet 4.5. Constitution 4 min (161 lines), specify 6 min (230), plan 8.5 min (2,067 markdown lines in total across the artefacts), implement 13.25 min producing 689 lines of code; totals 33.5 agent minutes and 2,577 markdown lines versus 689 code lines; a second increment (GPS) took 23.5 minutes, produced about 300 lines of code and 2,262 markdown lines, with about 2 hours of review. Baseline with plain iterative prompting: 8 agent minutes, 1,000 lines, 15 minutes of review, 9 minutes of testing. His verdict: "I am a lot more productive without SDD, around ten times faster" (by the researcher's arithmetic of his own figures about 7.6x); "Code is law because it is formal language you can reason about"; "For now, the fastest path is still iterative prompting and review, not industrialised specification pipelines" ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)). He states caveats himself (immature tool, possibly wrong problem size).
- Zaninotto, Marmelab, 2025-11-12 [c, reported]: six problems (context blindness, markdown madness, bureaucracy, misused user stories, "double review", false security when an agent marked "verify implementation" done without writing a unit test); "For large existing codebases, SDD is mostly unusable"; "Most coding agents already have a plan mode and a task list"; built a 3D sculpting tool in about 10 hours with Claude Code and no spec ([Marmelab](https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html)).
- Gonzalez, Haskell for All, 2026-03-17 [c, n=1 replication, reported]: dissected OpenAI's Symphony SPEC.md; asked Claude Code to build it in Haskell and got bugs and a Codex agent that "just spun silently"; argues a spec precise enough to generate reliably "contorts the document into code" ([haskellforall.com](https://haskellforall.com/2026/03/a-sufficiently-detailed-spec-is-code)). Tornhill, CodeScene, 2026-05-28 [c, reported]: "Implementation was never just typing. It's discovery and learning" ([Substack](https://adamtornhill.substack.com/p/a-blast-from-the-past-sdd-and-the)). Kent Beck, relayed by Fowler on 2026-01-08: SDD "encodes the (to me bizarre) assumption that you aren't going to learn anything during implementation that would change the specification" ([Fowler fragments](https://martinfowler.com/fragments/2026-01-08.html)); Fowler on 2026-07-13: "Conformance tests (sensors) are more valuable than specifications (guides)" ([fragments](https://martinfowler.com/fragments/2026-07-13.html)); Frisinger, 2026-07-30: tests are "the only spec that cannot silently diverge" ([dev.to](https://dev.to/tmfrisinger/spec-driven-development-is-the-prose-spec-drift-trap-reborn-4p99)) (all reported).
- Thoughtworks Technology Radar [I, institutional; Vol. 34 entries reported by the researcher from the April 2026 PDF]: OpenSpec praised for "spec deltas rather than defining a complete specification upfront", BMAD called more rigid, Kiro tied to a vendor IDE, and a recommendation to "re-evaluate the need for SDD tooling" as native capabilities grow; GitHub Spec Kit assessed with brownfield caveats ("unnecessary defensive checks and overly verbose markdown outputs that increased cognitive load", trimming templates helped, "experienced engineers... tend to extract the most value"); related blips "Agent instruction bloat" (Caution), "Feedback flywheel" (Assess), "Mutation testing" and "Feedback sensors" (Trial), Superpowers (Assess) ([Vol. 34 PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/04/tr_technology_radar_vol_34_en.pdf)).
- Thoughtworks engineers [c]: a pro-SDD essay concedes "Spec drift and hallucination are inherently difficult to avoid. We still need highly deterministic CI/CD practices" and warns over-formalised specs can slow feedback "just as we encountered in the early stages of waterfall" ([Liu, 2025-12-04](https://www.thoughtworks.com/insights/blog/agile-engineering-practices/spec-driven-development-unpacking-2025-new-engineering-practices)); the "Future of Software Engineering" retreats (February and June 2026, Chatham House, anecdotal) report "Code generation is no longer the bottleneck - verification is", "Conformance tests matter a lot more than the spec", "The tests become deterministic validation for non-deterministic generation", tiering code by blast radius, and that "The best-performing teams do not hand-write their harnesses" but run a "learn" skill and prune ([February PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/report/tw_future%20_of_software_development_retreat_%20key_takeaways.pdf), [June PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/report/tw_future_of_software_engineering_europe_2026.pdf)).
- Böckeler follow-ups [I/c, reported]: "Context engineering for coding agents" (2026-02-05: "there are no unit tests for context engineering"; hooks run "deterministically every single time"), "Harness engineering" (2026-04-02: guides versus sensors, computational versus inferential) and "TDD inside the agent loop" (2026-08-10: a small informal eval, Sonnet 4.6 generating and Opus 4.8 judging, found no quality gain, no better mutation scores and at least 3x tokens, 8.5x on the small task; agents skip or fake the red step; "I've stopped telling my coding agents to write tests first") ([context engineering](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html), [harness engineering](https://martinfowler.com/articles/harness-engineering.html), [TDD in the agent loop](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html)).
- Practitioners with large audiences [c, reported]: Osmani's "How to write a good spec for AI agents" (2026-01-13; six areas, Always/Ask/Never tiers, "adjust spec detail to task complexity"), "Audit your Agent files" (2026-08-27; "if a rule must always hold, encode it in a test, hook, or permission") and "Brownfield Agentic Engineering" (2026-09-14; "Write down what the code can't say, and nothing else"; green/yellow/red zones: "A person draws the map, not the agent"; "Every repeated correction is a missing piece of the harness") (his bio lists Anthropic, so vendor-adjacent) ([good-spec](https://addyosmani.com/blog/good-spec/), [audit](https://addyosmani.com/blog/audit-your-agent-files/), [brownfield](https://addyosmani.com/blog/brownfield-agentic-engineering/)); Willison endorsed Superpowers on 2025-10-10 and promotes red/green TDD ([post](https://simonwillison.net/2025/Oct/10/superpowers/)); Gorman: natural-language specs "are inherently ambiguous" and "having a test gives it something to converge on" ([SE Radio 732](https://se-radio.net/2026/08/se-radio-732-jason-gorman-on-the-effective-use-of-ai-for-software-development/)); Krishnan on InfoQ warns of "SpecFall" and a "markdown monster" and that artefacts with different lifecycles (architecture decisions versus task lists) get mixed ([InfoQ, 2026-02-19](https://www.infoq.com/articles/enterprise-spec-driven-development/)).
- AWS voices [reported]: Marc Brooker knows of no side-by-side comparison with vibe coding and says "the specification flow loads a little bit more work upfront, and so there's no hiding that" ([SE Radio 710](https://se-radio.net/2026/03/se-radio-710-marc-brooker-on-spec-driven-ai-dev/)); CIO reported that Kiro added Design-first and Bugfix workflows because users "didn't want to give up the structure of specs, but found the current flow was not flexible enough", with an analyst calling spec-driven development "intellectually appealing but culturally heavy" ([CIO, 2026-02-20](https://www.cio.com/article/4135314/aws-adds-design-first-and-bugfix-workflows-to-kiro-2.html)).
- Low-quality or pointer-only: the Uvik "SDD Benchmark 2026" (a staff-augmentation vendor; the page is dated "Last updated September 24, 2026" yet reports a run on "October 15, 2026", a future date) claims 50 tickets and a spec benefit only on tasks touching 3+ files; treat as a hypothesis, not evidence ([page](https://uvik.net/spec-driven-development-benchmark/)). Listicles, vendor blogs and agency summaries (2muchcoffee, Allstacks, Latent Space "reviews are dead", codemyspec) were used only as pointers.

#### Tool-by-tool status of independent evidence
- Spec Kit is the most criticised (Böckeler, Scott Logic, Marmelab; Isenberg/Itzhak 2.77/5 in February 2026 on v0.1.6). Kiro: "sledgehammer" on small bugs but easier to review than Spec Kit; AWS has since added lighter workflows. BMAD: heaviest (Radar "more rigid"; full flow 6 days and about $200 in Isenberg's test) but best adversarial review and mid-feature course correction. OpenSpec: best-received independent verdict (Radar; Isenberg 4.00/5) with a bus-factor-1 and no-review-gate caveat. Agent OS, Taskmaster, cc-sdd and GSD: no independent long-form analysis found; Superpowers: endorsed by Willison, Radar "Assess", and its enforced red-green-refactor is what Böckeler's eval questions (researcher's reading of [Isenberg](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/), [Radar PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/04/tr_technology_radar_vol_34_en.pdf)).

#### What independent sources recommend instead
- Right-size the process (Anthropic's one-sentence-diff rule; Osmani; Garg's rule of thumb that spec discipline pays on hard, multi-constraint, regulated or long-lived work and not on throwaways); small increments with fast feedback (Scott Logic, Marmelab, Gorman); tests and conformance suites as the durable executable spec (Fowler, Willison, the Thoughtworks retreats, Anthropic's "A spec may also be a detailed test suite"); disposable per-change specs plus durable "why" (OpenSpec deltas, Scott Logic, Osmani) while "spec-as-living" remains contested (Frisinger, Scott Logic against; Osmani and GitHub for); harness engineering with deterministic hooks over prose, then measure and prune (Böckeler, Radar, Anthropic, Marmelab, Osmani); risk-tiered human review of plans and evidence rather than volume (retreats, Osmani) (researcher's synthesis of the sources above; [Anthropic context post](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)).

### Inferences
- The criticism mix is stable across 14 months and across tools, so it is unlikely to be tool-specific noise: proportionality, cost, drift, and trust in agent self-reports are structural problems of prompt-orchestrated process. wm's answers (triage, small work orders, deterministic gates, BLOCKED) map to themes 1, 6 and 7; themes 2, 4, 5 and 8 are where wm still needs explicit mechanisms (artifact budgets, work-order lifecycle, update commands and migrations).
- Many "fixes" shipped by the frameworks are fast lanes added after complaints, which implies that wm's T0 and T1 should be nearly free of artifacts by default.
- Praise is mostly about process discipline for humans (thinking before coding, onboarding), not about measured agent accuracy; see the next section for the few measurements.

## 8. What measured outcomes exist (case studies, benchmarks, before/after reports) for these frameworks, and how reliable are they?

### Takeaway
There is no large, controlled, independent study of any spec-driven framework against a plain agent. What exists is (a) a handful of small independent experiments with n between 1 and 5 whose direction is consistent (the full ceremony is slower and costlier on small tasks; spec discipline helps mostly weaker models on hard, multi-constraint tasks; spec baselines do not make reviewers find more drift); (b) one transparent but vendor-authored Microsoft evaluation of a Spec Kit extension whose end-to-end autonomous arm scored below a bare one-shot agent; (c) user-run token and cost measurements in issue trackers; (d) maintainer and vendor claims (Superpowers 6.0, Kiro, BMAD) that are mostly unreplicated; and (e) corpus and taxonomy studies that count artifacts but do not measure quality. Adjacent evidence about instruction files, hooks and test-first practice is covered in depth in the sibling notes `enforcement_and_evaluation.md` and `model_routing_and_cost.md`; only the items most relevant to framework design are repeated here. Labels: [I] independent, [V] vendor/maintainer-authored, [P] practitioner self-report; "confirmed" means I re-fetched the source.

### Cited Findings

#### Independent experiments (ordered by methodological strength)
- Garg, InfoQ, 2026-09-10 [I, pilot, n=5 reviewers] (confirmed): within-subject drift review of AI-generated banking services; five reviewers with 3-10 years' experience; ground truth of 11 and 10 adjudicated drifts. Recall was "statistically indistinguishable" with and without an approved spec baseline (0.525 vs 0.518, p=0.69); baseline reviewers attributed 81% of findings to a named clause versus 0% without one; review took 48.4 versus 26.7 minutes (p=0.043). A 90-review automated replication across four frontier models gave recall 0.376 vs 0.377 (p=0.95). In generation, a staged arm (write the spec, then implement in a fresh pass) reached 45% versus 23.8% for a single prompt on a weak model, but "carries a second-pass confound"; a control showed "fifty-nine percent (just write code) to ninety-five percent (reason first) to ninety-two percent (spec first), with spec-versus-reasoning not significant"; on the complex task the weaker model "gained about twenty-one points from spec discipline" and the strong model "roughly two". The author: "Read them as a strong pilot signal, not confirmatory proof" ([InfoQ](https://www.infoq.com/articles/when-spec-driven-development-pays-off/)).
- Eberhardt, Scott Logic, 2025-11-26 [I, n=1] (confirmed): Spec Kit (September 2025 version) with Copilot and Claude Sonnet 4.5 needed 33.5 agent minutes and produced 2,577 markdown lines for 689 lines of code, versus 8 minutes and 1,000 lines for iterative prompting; review 3.5 hours versus 15 minutes plus 9 minutes of testing ([Scott Logic](https://blog.scottlogic.com/2025/11/26/putting-spec-kit-through-its-paces-radical-idea-or-reinvented-waterfall.html)).
- Isenberg (author Itzhak Eretz Kdosha), 2026-04-13 [I, n=1 feature, tested February 2026 on BMAD v6.0.3, Spec Kit v0.1.6, OpenSpec v1.2.0, Cursor with Sonnet 4.5] (confirmed): planning time/cost then implementation time/cost: BMAD Full 2 days/$50 then 4 days/$150; BMAD Quick 5 h/$30 then 1.5 days/$55; Spec Kit 4 h/$30 then 1 day/$45; OpenSpec 3 h/$25 then 1 day/$70; author's own composite scores 3.65, 3.74, 2.77 and 4.00 out of 5, described as "highly opinionated"; "None of these tools is ready for large enterprise adoption without modification" ([ranthebuilder.cloud](https://ranthebuilder.cloud/blog/i-tested-three-spec-driven-ai-tools-here-s-my-honest-take/)). The versions are old, so ranking may have changed.
- Microsoft Cosmos DB team, 2026-09-21 [V-authored but transparent, Spec Kit extension] (confirmed from the repository documents): (1) conformance: generated Cosmos DB code scored +0.10 mean pass-rate with the extension's command guidance, better in 19 of 24 model x language x complexity cells, with the client application-name check +0.79; advisor precision rose from 0.57 to 0.68; (2) delivery: an autonomous agent given a realistic build task with the extension installed "did not invoke the on-demand commands at all (0 of 30 runs)", and delivering the same rules as an always-on context block improved conformance by +0.16; (3) in the full `specify, plan, tasks, implement` flow run autonomously (n of about 137-147 graded attempts per arm per model, five headroom scenarios plus one control), mean behavioural pass-rates were bare one-shot 0.755 (Opus-class) and 0.729 (GPT-5-class), full Spec Kit ceremony without the extension 0.638 and 0.678, ceremony plus the shipped extension 0.573 and 0.645, ceremony plus the modified extension 0.653 and 0.681; only about 15% of attempts invoked a code-generating Cosmos command even though the advisor recommended commands in 71%. The authors say the bare comparison is "the least-controlled", that autonomy removes "the mechanism that repays the ceremony's cost" (a human at the gates) and that tasks were small one-shottable apps ([EFFICACY.md](https://github.com/AzureCosmosDB/spec-kit-cosmosdb/blob/main/EFFICACY.md), [sdd-flow-efficacy.md](https://github.com/AzureCosmosDB/spec-kit-cosmosdb/blob/main/testing/results/sdd-flow-efficacy.md), [Microsoft DevBlogs](https://devblogs.microsoft.com/cosmosdb/spec-driven-development-comes-to-azure-cosmos-db-the-first-database-extension-for-github-spec-kit/)).
- Superpowers user benchmark [I, single author, n=20 runs per arm, 4 small bugfix tasks] (confirmed): no instructions: 2/20 verified repros, 20/20 accuracy, $0.176 per run; a 291-line `systematic-debugging` ruleset: 8/20, 20/20, $0.316; a 31-line repro-first ruleset: 10/20, 20/20, $0.241; a re-test after the ruleset was trimmed 291 to 278 lines was a null result (cost $0.316 to $0.291, repros 8/20 to 9/20). The author warns accuracy was saturated so nothing is said about root-cause quality on real codebases ([issue #2017](https://github.com/obra/superpowers/issues/2017)).
- Spec Kit Agents, arXiv 2604.05278, 2026-04-07 [I, preprint] (confirmed): adding read-only context-probing and validation hooks to a multi-agent Specify-Plan-Tasks-Implement pipeline raised a 1-5 LLM-as-judge composite by +0.15 (+3.0% of the full score; Wilcoxon p < 0.05) over 128 runs on 32 features in five repositories while keeping 99.7-100% repository-level test compatibility; on SWE-bench Lite the hooks added 1.7% to reach 58.2% Pass@1 ([arXiv](https://arxiv.org/abs/2604.05278)).
- Practitioner self-measurements [P]: 94 spec folders, 238 files and 15,225 lines never reopened, rewritten as 14 files and 3,112 lines with "approximately 60 to 68% leaner" specs and "identical correctness scores" (author's claim) ([dev.to](https://dev.to/alfredoperez/i-wrote-238-specs-and-never-read-one-again-5705)); issue-level token counts in section 7 (Spec Kit 18.6k always-loaded tokens and 23,703 across nine templates; cc-sdd about 283,000 tokens of re-reads versus about 8,000 targeted; BMAD 80k-100k tokens per step; a Gemini CLI `hello world` run of 1.35M tokens) ([#1401](https://github.com/github/spec-kit/issues/1401), [#2943](https://github.com/github/spec-kit/issues/2943), [cc-sdd #188](https://github.com/gotalab/cc-sdd/issues/188), [BMAD #1235](https://github.com/bmad-code-org/BMAD-METHOD/issues/1235), [#1492](https://github.com/github/spec-kit/issues/1492)); a Japanese series measured about $31 and about 34 minutes to add one requirement with Spec Kit (301 to 331 tests) (via Spec Kit's August newsletter, original not read) ([newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-August.md)).

#### Corpus and taxonomy studies (count artefacts, do not measure quality)
- SpecMine, CMU, arXiv 2608.25202, 2026-08-25 (confirmed): 470,795 spec files in 73,030 repositories attributed to 17 named tools; Kiro 98,574 files in 12,910 repositories; 5,992 spec-touching pull requests across 581 repositories on 11 tools; 2,421,323 typed cross-references ([arXiv](https://arxiv.org/abs/2608.25202)).
- de Macedo, arXiv 2606.04967, 2026-06-03 (confirmed): compares Spec Kit, OpenSpec, BMAD, GSD, Spec Kitty and Reversa on a six-dimension taxonomy (specification, context, roles, execution, validation, portability); "No framework strongly covers all six dimensions, exposing a structural trade-off between process depth and portability across agents"; recurring risks are "drift between specification and code, excessive trust in generated artifacts, fragility of community extensions, platform dependence and a lack of benchmarks for the complete process" ([arXiv](https://arxiv.org/abs/2606.04967)). The scores are the author's judgement.
- Marmelab, "State of AI Harness Engineering 2026", 2026-09-24 (reported): 63% of 145 large open-source projects ship an agent instruction file, only 4 declare a subagent and there are 14 hooks in total; 60% of 97 testable harnesses have neither a test nor an eval ([Marmelab](https://marmelab.com/blog/2026/09/24/the-state-of-ai-harness-engineering-2026.html)); the researcher cautions that two of its secondary citations are loosely paraphrased.

#### Vendor and maintainer measurements (unreplicated unless stated)
- Superpowers: v6.0 (2026-06-15) "up to 50% faster and up to 60% cheaper" from an optimisation loop of 25 experiments (confirmed, see section 7); v6.4.1 (2026-09-18) probes: sessions ran only the named test file in 11 of 12 runs, "every implementer shipped the same crash on an input the spec implied but never named", the controller on a mid-tier nested subagent "measured about half the cost and wall clock"; v6.4.2: "every plan written by the new skill executed 9/9 against planted-defect probes on Sonnet 5" ([RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). - Kiro (reported, vendor blog posts, not independently verified): parallel "run all tasks" cut one task from "over an hour... to about a quarter of that time" (anecdotal) ([blog, 2026-05-12](https://kiro.dev/blog/faster-smarter-specs/)); the Auto router used 21% fewer credits for typical requests and 36% for demanding ones ([blog, 2025-11-11](https://kiro.dev/blog/making-credits-go-further/)); requirements analysis: across 35 internal projects with 1,400+ acceptance criteria about 60% of first-draft requirements needed refinement ([The New Stack, 2026-05-15](https://thenewstack.io/kiro-requirements-analysis-automated-reasoning/)); AWS's Automated Reasoning Group reported 94 Kani/CBMC pull requests from Nov-Dec 2025 of which 37% merged and 60% were still open, "Kiro can generate PRs faster than the team can review them", with "zero regressions" among those merged ([blog, 2026-09-14](https://kiro.dev/blog/tackling-technical-debt-at-scale-with-autonomous-mode/)); customer stories include Rehrig Pacific ("expected to take roughly 3 years in the last 7 weeks with a single developer"), Siemens (3-4 months to 2 weeks), LMU (2 months to half a day) ([case study](https://kiro.dev/case-studies/rehrig-pacific/), [one-year post](https://kiro.dev/blog/one-year/)). - Anthropic engineering (reported): in a long-running application harness test a solo run took about 20 minutes and $9 versus about 6 hours and $200 for the full harness, and "every component in a harness encodes an assumption about what the model can't do on its own" ([Anthropic, 2026-03-24](https://www.anthropic.com/engineering/harness-design-long-running-apps)).
- Taskmaster: tool-loading modes cut the MCP schema from about 21,000 tokens (36 tools) to about 10,000 (15) or about 5,000 (7) ([README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md)).

#### Adjacent evidence relevant to framework mechanisms (summaries; details and further studies in the sibling notes)
- Instruction and context files: Lulla et al. (arXiv 2601.20404, 2026-01-28): with an AGENTS.md, Codex median runtime fell 28.64% and median output tokens 16.58% across 124 PRs, with correctness explicitly not evaluated ([arXiv](https://arxiv.org/abs/2601.20404), reported); Vercel (2026-01-27, vendor): a compressed docs index in AGENTS.md scored 100% versus 53% baseline on Next.js 16 APIs absent from training data, and skills were never invoked in 56% of cases, which is the figure BMAD's docs repeat ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals), reported); ETH Zurich details (reported): LLM-generated files changed resolution by -0.5 and -2 points and added 20-23% cost, developer-written files gave +2.4 points (not significant) and for Claude Code with Sonnet 4.5 scored 70.3% versus 73.2% with no file ([arXiv v3](https://arxiv.org/html/2602.11988v3)); IFScale: Sonnet 4 followed 94.4% of 100 but 42.9% of 500 keyword instructions ([arXiv](https://arxiv.org/abs/2507.11538), reported); an Anthropic post-mortem says one system-prompt line limiting inter-tool text to 25 words cost 3% on evals ([Anthropic, 2026-04-23](https://www.anthropic.com/engineering/april-23-postmortem), reported).
- Reported versus verified completion: OverclaimBench (arXiv 2609.20812, 2026-09-17, confirmed): across 12 models "agents fail to read every file they were asked to review in 67.9% of runs", "among these incomplete runs, agents are misleading 80.4% of the time (59-96% per model)", forcing delegation to subagents "increases coverage, but a large majority of reviews that remain incomplete are still misleading", and false claimants "miss planted defects at about 1.8 times the rate" ([arXiv](https://arxiv.org/abs/2609.20812)); a workshop paper on 9,876 tau2-bench and 1,879 AppWorld trajectories found 45-48% of failures in single-control domains end in a success claim versus 3% where a second party confirms state, and LLM judges reached at most 0.65 AUROC on false success (reported) ([arXiv](https://arxiv.org/abs/2606.09863)); METR (2026-03-10, confirmed): four maintainers of scikit-learn, Sphinx and pytest reviewed 296 agent pull requests that passed the SWE-bench grader and 47 human patches, and "on average maintainer merge decisions are about 24 percentage points lower than SWE-bench scores" (SE 2.7), citing code quality, repository standards and breakage, with the caveats that agents had no chance to iterate and patches averaged about 17 lines ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)).
- Instruction versus enforcement: Shin (arXiv 2605.01771, 2026-05-03, confirmed): across 2,031 sessions on six models an instruction to read each file individually with no scripts and no agents saw 0% compliance under default framing (Claude Sonnet 4 agreed 10 of 10 times and bypassed in all ten), about 75% compliance once delegation tools were removed (Cohen's d = 2.47), 97% where rationale was rewarded, and nine blinded raters identified "zero of fifteen" compliant sessions from text alone ([arXiv](https://arxiv.org/abs/2605.01771)); ImpossibleBench and METR's reward-hacking note (summarised in the sibling note `enforcement_and_evaluation.md`) show prompts alone leaving high cheating rates while read-only tests and abort options cut it ([arXiv](https://arxiv.org/abs/2510.20270), [METR](https://metr.org/blog/2025-06-05-recent-reward-hacking/)); Anthropic's Sonnet 5 system card reports a "tendency to shortcut human approval, e.g., by creating subagents to approve its work" (reported by the researcher) ([Sonnet 5 card](https://www-cdn.anthropic.com/283ef97c476cf442c91d9a37d5b214242a55bb92/Claude%20Sonnet%205%20System%20Card.pdf)). Practitioner measurements (anecdotal): a sandboxed `claude -p` test found skill activation at 55%/50% with no hook, 59%/50% with a simple instruction hook and 100%/100% with a forced-evaluation hook (22 prompts, two runs) ([Spence, 2026-02-08](https://scottspence.com/posts/measuring-claude-code-skill-activation-with-sandboxed-evals), reported).
- Review and separation: Anthropic's harness post (2026-03-24, reported): "separating the agent doing the work from the agent judging it proves to be a strong lever", yet "out of the box, Claude is a poor QA agent" because it talks itself into approving ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps)); industrial LLM review studies are mixed (Beko: 73.8% of comments resolved but PR closure time rose from 5 h 52 min to 8 h 20 min; Atlassian RovoDev: 38.7% of comments led to code changes and cycle time fell 30.8%) ([arXiv](https://arxiv.org/abs/2412.18531), [arXiv](https://arxiv.org/abs/2601.01129), reported); Greptile (vendor, 2026-07-21) reports cross-model review recall 60-62% versus 50-54% for same-family review ([Greptile](https://greptile.com/blog/model-inversion), reported).
- Roles and routing: Anthropic's advisor strategy (2026-04-09, confirmed): a Sonnet or Haiku executor consulting an Opus advisor mid-run (typically 400-700 text tokens per call) gave "a 2.7 percentage point increase" on SWE-bench Multilingual for Sonnet and cut "cost per agentic task by 11.9%", and the advisor is a tool the executor calls "when it hits a decision it can't reasonably solve", not an up-front plan ([Anthropic](https://claude.com/blog/the-advisor-strategy)); Kim et al. (Google, arXiv 2512.08296, confirmed abstract): across 260 configurations "relative performance change compared to single-agent baseline ranges from +80.8% on decomposable financial reasoning to -70.0% on sequential planning", and independent agents propagate errors more than centrally verified ones (reported detail: 17.2x versus 4.4x amplification) ([arXiv](https://arxiv.org/abs/2512.08296)). Details of planner/executor and routing studies are in `role_splits_in_other_tools.md` and `model_routing_and_cost.md`.
- Learning loop: SkillsBench (arXiv 2602.12670, v1 2026-02-13, v4 2026-06-14, confirmed abstract): 87 tasks, 18 configurations, curated skills raised pass rate "from 33.9% to 50.5% (+16.6 percentage points)", "Focused Skills with at most three modules outperform larger or exhaustive bundles" and "smaller models with Skills can match larger models without them"; the researcher reports from the full text that self-generated skills fell 8-11.5 points below baseline ([arXiv](https://arxiv.org/abs/2602.12670)); ACE (ICLR 2026) found incremental structured playbook edits avoid "context collapse" from rewrites (reported) ([arXiv](https://arxiv.org/abs/2510.04618)).
- Productivity and process context: METR's July 2025 randomised trial (16 experienced developers, 246 issues) found a 19% slowdown, and its 2026-02-24 update (57 developers, 800+ tasks) found -18% time for returning developers (CI -38% to +9%) with METR calling the evidence "very weak" because 30-50% of tasks were withheld (reported) ([2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/), [2026](https://metr.org/blog/2026-02-24-uplift-update/)); DORA 2025 found AI "amplifies" existing strengths and weaknesses and lists working in small batches among seven capabilities (reported) ([Google blog](https://blog.google/technology/developers/dora-report-2025/)); Anthropic's guidance contains no spec-driven measurements ([best practices](https://code.claude.com/docs/en/best-practices)).

### Inferences
- The independent numbers agree on direction even though each is weak: for a small, well-understood change the spec ceremony costs roughly 4x to 10x in agent time and review time (Scott Logic 33.5 vs 8 agent minutes and 3.5 h vs 24 min of human time), and the quality benefit that justifies it has not been demonstrated (Garg's equal recall; Microsoft's bare one-shot ahead; Spec Kit Agents' +0.15 of 5). The measured benefits are conditional: they appear when guidance is delivered always-on or by hooks (Microsoft +0.16 vs +0.10 vs 0 invocations; Spec Kit Agents' read-only hooks) and when a weaker model faces a hard, multi-constraint task (Garg).
- For wm that supports three design choices: keep ceremony off for small changes (T0/T1), deliver rules and guards through mechanisms that do not depend on the agent choosing to call them (path-scoped rules and hooks), and spend the specification effort where the implementer is a cheaper model and the task is multi-constraint, which is exactly the work-order use case. It also argues for wm to measure itself: none of the surveyed frameworks publishes per-task cost, turns and defect rates against a plain-agent baseline.
- The strongest support for wm's specific mechanisms is indirect but consistent: agents overclaim completion at high rates (OverclaimBench 80.4% misleading among incomplete runs; 45-48% of failures ending in success claims), maintainers reject about a quarter to a half of grader-passing patches (METR), instructions that the agent must choose to follow have near-zero compliance in the cases tested while removing the tool or enforcing outside the model works (Shin; Microsoft's 0 of 30), and always-on or enforced delivery beat on-demand guidance. That is the evidence base for a deterministic done-gate, a lead-side re-run of gates and a reviewer that checks evidence rather than the implementer's summary.
- The evidence on size thresholds (Uvik: no gain at 1-2 files and a possible gain at 6+; Garg: gains for a weaker model on hard multi-constraint work; Scott Logic: large loss on a small feature; SLUMP and Laban: a complete spec delivered at once beats incremental disclosure) is weak individually but points the same way for a triage rule: no artifacts for small, well-understood changes; one complete, self-contained work order for multi-file or multi-constraint changes.
- Vendor claims (Superpowers 6.0, Kiro customer stories, BMAD n=7) should be treated as marketing-adjacent until replicated; their value is mostly as a list of mechanisms the vendors believe are worth measuring (review packet pre-baking, plan proportion checks, verification-gap lens).

### Gaps
- No controlled study of Spec Kit, OpenSpec, BMAD, Agent OS, Taskmaster, cc-sdd, GSD or Superpowers against a plain Claude Code baseline on real tasks with human review in the loop; Brooker (AWS) also knows of no side-by-side comparison with vibe coding ([SE Radio 710](https://se-radio.net/2026/03/se-radio-710-marc-brooker-on-spec-driven-ai-dev/), reported).
- No data on how often specs drift, how long they stay useful, or whether drift checks (`converge`, `verify`, retrospective) catch real defects; SpecMine counts artefacts but does not measure these.
- No measurement of Taskmaster's or Agent OS's effect on outcomes; cc-sdd v3's per-task implementer/reviewer loop has only issue-level token measurements.
- The Isenberg numbers use February 2026 tool versions; the Scott Logic run used a September 2025 Spec Kit; both predate the 2026 fast lanes.
- Nothing directly tests an Opus-lead / Sonnet-implementer split with precise work orders, plan mode versus none, or `opusplan`; the Uvik authors list plan-mode and model-tiering arms as future work. Most adjacent studies used 2025-era models (Sonnet 4/4.5, GPT-5.x) and small samples, so they may not hold for Sonnet 5.5 and Opus 5.5.
- Prevalence of lint or type-suppression gaming (as opposed to test gaming) by 2026 models is unmeasured, and whether path-scoped rules load reliably when a file is created rather than opened is untested in what I found.
- Several third-researcher items were not re-fetched (Lulla, Vercel, IFScale details, Greptile, Beko, RovoDev, ACE, METR productivity updates, DORA) and are marked "reported"; Medium articles and Reddit were unreachable.

## 9. Which concrete mechanisms should wm adopt, and which pitfalls should it deliberately avoid?

### Takeaway
As described in the brief, wm's design lines up with where most of the evidence and incident reports point (small human-gated specs, enforcement outside the model, a narrow executor that reports instead of improvising, a separate reviewer), although no study tests this exact Opus-lead / Sonnet-implementer split. The most valuable additions found in other frameworks are (1) size routing that decides after investigating and only escalates, (2) a deterministic work-order lint plus a code-parsed implementer report with typed BLOCKED reasons, (3) done-gates hardened against fail-open behaviour, the 8-block cap and no-op passes, (4) review triage that verifies and logs every finding and stops after a bounded number of passes, (5) a rule admission test with provenance and a shrink-only audit for the learning loop, and (6) a self-test suite and a published benchmark, because no surveyed framework has measured itself against a plain agent. The main pitfalls are ceremony that does not scale down, artifact accumulation, advisory-only enforcement, fail-open hooks, always-loaded context sprawl, and plans or work orders that restate code.

#### Pitfalls observed in the field (with where documented)
- Ceremony that does not scale down (section 7, theme 1): Kiro "sledgehammer", Spec Kit "30 files changed, < 20 actual LOC", Superpowers "35 minute session", BMAD's own FAQ ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html), [#1174](https://github.com/github/spec-kit/issues/1174), [#743](https://github.com/obra/superpowers/issues/743), [build-a-change.md](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/docs/build/build-a-change.md)).
- Artifact accumulation: 238 spec files never reopened; specs at 73% of source size; Superpowers plans growing to 1.2 million characters ([dev.to](https://dev.to/alfredoperez/i-wrote-238-specs-and-never-read-one-again-5705), [newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-August.md), [#895](https://github.com/obra/superpowers/issues/895)).
- Plans or orders that restate code: Superpowers 6.4.2 notes that "Some frontier models, including Opus 5.5, could get overzealous during plan writing and... try to implement the entire project while designing the plan" ([RELEASE-NOTES](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)); Agent OS v3 dropped spec writing ([CHANGELOG](https://github.com/buildermethods/agent-os/blob/main/CHANGELOG.md)); Gonzalez: a spec precise enough "contorts the document into code" ([haskellforall.com](https://haskellforall.com/2026/03/a-sufficiently-detailed-spec-is-code), reported).
- Advisory-only enforcement and false completion: an agent "reasoned past" an advisory ([gsd-write-guard.js](https://github.com/open-gsd/gsd-core/blob/HEAD/hooks/gsd-write-guard.js)); Microsoft's 0 of 30 on-demand invocations ([EFFICACY.md](https://github.com/AzureCosmosDB/spec-kit-cosmosdb/blob/main/EFFICACY.md)); phantom completions ([#1865](https://github.com/github/spec-kit/issues/1865)); Kiro's silent false success ([#11786](https://github.com/kirodotdev/Kiro/issues/11786)).
- Fail-open hooks and gate rot (section 4) ([memo](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/research/2026-10-02-git-probe-timeout-blocking-guards.md), [CHANGELOG 1.16.0](https://github.com/open-gsd/gsd-core/blob/HEAD/CHANGELOG.md), [hooks reference](https://code.claude.com/docs/en/hooks)); dual Bash and PowerShell scripts as a recurring portability bug source ([spec-kit #1156](https://github.com/github/spec-kit/issues/1156), [Agent OS #319](https://github.com/buildermethods/agent-os/issues/319)).
- Reviewer pathologies: quota-driven findings, endless follow-up reviews, reviews of missing artefacts, every finding becoming a plan amendment ([PR #1913](https://github.com/bmad-code-org/BMAD-METHOD/pull/1913), [#2576](https://github.com/bmad-code-org/BMAD-METHOD/issues/2576), [#11804](https://github.com/kirodotdev/Kiro/issues/11804), [#895](https://github.com/obra/superpowers/issues/895)).
- Skill, tool and rule sprawl in always-loaded context: GSD 66 skills at about 60% of a claimed listing budget; Taskmaster 36 tools at about 21k tokens; instruction files adding over 20% cost without general success gains ([memo](https://github.com/open-gsd/gsd-core/blob/HEAD/docs/research/2026-05-12-skill-surface-budget.md), [README](https://github.com/eyaltoledano/claude-task-master/blob/main/README.md), [arXiv](https://arxiv.org/abs/2602.11988)); Thoughtworks lists "Agent instruction bloat" under Caution (reported) ([Radar PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2026/04/tr_technology_radar_vol_34_en.pdf)).
- Shared mutable state and parallel writers: BMAD runs that "commit one another's changes", Taskmaster `tasks.json` without locking, GSD Windows lost writes ([#2849](https://github.com/bmad-code-org/BMAD-METHOD/issues/2849), [#1567](https://github.com/eyaltoledano/claude-task-master/issues/1567), [gsd-core #3780](https://github.com/open-gsd/gsd-core/issues/3780)); Google's study found multi-agent variants lost up to 70% on sequential tasks ([arXiv](https://arxiv.org/abs/2512.08296)).
- Extension ecosystems as supply-chain surface, default telemetry, restrictive licences ([July newsletter](https://github.com/github/spec-kit/blob/main/newsletters/2026-July.md), [OpenSpec README](https://github.com/Fission-AI/OpenSpec/blob/main/README.md), [Taskmaster #1681](https://github.com/eyaltoledano/claude-task-master/issues/1681)).
- Breaking churn without migrations ([Spec Kit v1.0.0 notes](https://github.com/github/spec-kit/releases/tag/v1.0.0), [BMAD #2117](https://github.com/bmad-code-org/BMAD-METHOD/issues/2117), [OpenSpec 1.0](https://github.com/Fission-AI/OpenSpec/releases/tag/v1.0.0)); harness regressions breaking a framework ([GSD #803](https://github.com/gsd-build/get-shit-done/issues/803)).
- Persona theatre ("Remove AI personification") and "I had become a human router" fatigue ([BMAD #719](https://github.com/bmad-code-org/BMAD-METHOD/issues/719), [dev.to](https://dev.to/ndabene/i-stopped-using-bmad-heres-what-replaced-it-25o8), reported).
- Autonomy without a human gate: in Microsoft's study the full Spec Kit ceremony run autonomously scored below a bare one-shot agent (Opus-class 0.638 vs 0.755), though the authors caution the comparison is not apples-to-apples ([sdd-flow-efficacy.md](https://github.com/AzureCosmosDB/spec-kit-cosmosdb/blob/main/testing/results/sdd-flow-efficacy.md)).

### Inferences
Evidence strength tags: [strong] = several independent sources or primary incident reports agree; [moderate] = one good source or consistent but weak sources; [weak] = plausible, mostly vendor or anecdote. These are my recommendations, not findings.

#### Adopt or adapt (ordered by expected value for wm)
1. Done-gate hardening [strong]. Make the gate fail closed on internal errors (exit 2 or `decision: "block"`, never a plain non-zero exit), register generous timeouts for blocking hooks, add a no-op check (the gate examined at least one test or file), keep a canary suite that plants known violations (new suppression, failing test, skipped test) and requires rejection, run the project's full suite rather than the named test files, record attestations (command, exit code, counts), and test the hooks as real subprocesses on macOS, Linux and Windows. Handle Claude Code's 8-continuation Stop cap by turning repeated denials into an explicit BLOCKED handback carrying the gate output, and have the lead re-run the gates after every handback. Sources: GSD incident memo and changelog, spec-gates, Superpowers 6.4.1, Claude Code hooks reference, OverclaimBench, METR.
2. Typed, code-parsed handoff [strong]. Fix the implementer report schema (status, files changed, tests added, gate results, deviations, blocked reason enum, attempted-change patch path) and parse `last_assistant_message` in the SubagentStop hook; deny a handback with an unparseable report once, then BLOCK. Derive "tests run" and "gates green" from hook-captured output, not from the agent's text. Sources: cc-sdd STATUS block, BMAD blocked conditions, GSD parity-test lesson on prose-defined formats, Claude Code SubagentStop fields. Prefer JSON for machine state (Anthropic reportedly found models overwrite Markdown state files more readily than JSON) [weak, reported].
3. Triage that decides after investigating and only escalates [strong direction, weak data]. Compute T0 to T4 from deterministic signals (files touched, protected paths matching rule globs, schema or API change, migration, number of acceptance criteria) plus a short lead judgement, announce the tier so the user can override, never downgrade mid-task, log tier versus actual cost, and give T0/T1 no work-order file at all. Sources: BMAD Build, Superpowers three paths, GSD fast/quick/full, Anthropic one-sentence-diff rule, Scott Logic, Uvik (about 3 files), Garg.
4. Deterministic work-order lint before dispatch [moderate]. Check: every numbered behaviour rule maps to at least one acceptance test; declared file scope and out-of-scope list present; signatures or contracts but no code bodies beyond a threshold; length ratio versus the change; no two parallel orders share a file. Optionally a cheap Haiku pass that restates each rule in two interpretations to expose ambiguity (Kiro Analyze Requirements idea) before the Sonnet implementer returns BLOCKED. Sources: OpenSpec validate, Superpowers conflict scan and proportion check, BMAD ready-for-dev gate, Kiro, Anthropic spec guidance, SLUMP.
5. Review protocol with verify-then-dismiss and a stop rule [strong]. Reviewer in a fresh context, given the order, the diff as a file and the gate output; findings must cite file and line and a verified consequence, be limited to correctness and stated requirements, and be logged with a disposition; allow a verdict "cannot verify from the diff"; at most one re-review, and non-trivial findings on the second pass go back to the order or the rules rather than another pass; never set a minimum number of findings. Add BMAD's verification-gap question ("if this behaviour broke, would any test fail?") for T2 and above. Optionally a second reviewer from another model family for T3/T4 (Kiro Workflows; Greptile vendor data), with a JSON verdict file as the loop gate. Sources: BMAD triage and PR #1913, Anthropic best practices, Superpowers 6.0, Kiro Workflows.
6. Rule admission test, provenance and shrink-only audit for the learning loop [strong]. A review finding becomes a rule only after an observed failure with a link to the finding, a `paths:` scope, an enforcement type (hook, test, lint or prose) and a re-validation trigger (model upgrade or N months); the lead (or user) approves; a periodic audit may only shrink or merge; repeated violations of a prose rule are converted to a hook or lint (hookify precedent). Sources: BMAD record/audit, Anthropic best practices and hookify, SkillsBench (curated beat self-generated), ETH Zurich (generated context files cost more and did not help), Kiro's lesson-store lessons.
7. Preflight and a sanctioned exit [moderate]. Have the implementer's first step verify the order's premises (referenced files and symbols exist, test command runs, contract compiles) and return BLOCKED early with typed reasons; keep the rule "do not work around a spec that conflicts with reality". Sources: cc-sdd "block the task... do not silently work around it", ImpossibleBench abort option, Opus 5.5 system card on missing-file tasks (reported), Zhao et al. on early failures (reported).
8. Guard design details [moderate]. Split compound shell commands before matching so `a && git commit` is caught; protect the hooks, rules and order files themselves (wm's lead-owned-files guard already does this); keep policy outside the implementer's writable paths; key guards on `agent_type`; scan diffs for new suppressions; add a registry check for any newly introduced dependency name even when the lead approves it (slopsquatting defence). Sources: Kiro permission model, GSD guards and Package Legitimacy Gate, Claude Code hook inputs.
9. Context budget discipline [strong]. Few skills with short descriptions, manual-only workflows marked non-model-invocable, procedure bodies loaded on demand, rules path-scoped and tiny, and a `/skill-doctor` check in `/wm:adopt`. Sources: Claude Code skills docs, GSD memo (100-character cap, `--minimal`), Taskmaster tool modes, Spec Kit lean preset field report, ETH Zurich, Anthropic's "convert it to a hook".
10. Model routing hygiene [moderate]. Pin `model:` in every agent file, escalate one tier after repeated failure (the lead takes over or the user approves an advisor call), keep a mid-tier floor for the reviewer, and record tokens, turns and minutes per order so the Sonnet-versus-Opus choice is measured rather than assumed. Sources: Superpowers model-selection rules, GSD dynamic routing, Anthropic advisor strategy (mid-run consultation rather than a pre-written plan), DeepSWE and system-card data (see `model_routing_and_cost.md`).
11. Brownfield `/wm:adopt` [strong direction]. Generate one small verified context block (commands, test/lint/build, boundaries, risk zones, "why" decisions) inside markers, verify every named path, read CI config for the gate commands, ask only what no scan can answer, require approval, never commit, and start with a bounded first change; do not generate repository overviews or whole-system specs. Sources: BMAD project-context, Spec Kit existing-projects guide, OpenSpec brownfield guide, ETH Zurich (overviews not helpful), Osmani.
12. Self-test suite and a published baseline comparison [strong need, no precedent]. Ship headless `claude -p` tests for skills and hooks, canary violations for every gate and guard, parity tests for any duplicated prose, a hook-conformance self-test in `/wm:adopt` (so Claude Code version drift is detected), and a small frozen task set run against plain Claude Code on each model release, reporting cost, turns and defects. No surveyed framework has published such a comparison, and the frameworks that tried to publish numbers (Superpowers 6.0, BMAD n=7) have not been replicated. Sources: Superpowers tests, spec-gates canaries, GSD parity tests, Anthropic harness post ("every component in a harness encodes an assumption about what the model can't do").
13. Bug-type orders with a preservation section [moderate]. For T1/T2 bug fixes use the Kiro triad (Current / Expected / Unchanged behaviour) and require a failing reproduction test recorded before the fix plus characterisation tests for the "unchanged" list. Sources: Kiro bugfix specs (reported), Spec Kit bug extension ("Missing verification is not a successful fix"), Osmani characterisation tests.
14. Disposable work orders and durable knowledge elsewhere [moderate]. After merge, archive or delete the order; behaviour lives in tests, constraints in path-scoped rules, rationale in ADRs; a mechanical "orders whose referenced ADR or rule changed" report and a recorded base git ref per order give the drift signal that Kiro users ask for and Spec Kit lacks. Sources: OpenSpec archive, Spec Kit persistence models, Kiro #9435, Alfredo Perez's accumulation numbers, Thoughtworks Radar.
15. Distribution and maintenance hygiene [moderate]. MIT licence, no telemetry, no network calls in hooks, one cross-platform hook runtime (not parallel Bash and PowerShell), versioned schemas with a migration command and changelog, a CI matrix across operating systems and recent Claude Code releases, and conservative names that do not collide with other plugins. Sources: Taskmaster licence and telemetry reports, Spec Kit and Agent OS script-portability issues, GSD #803, BMAD shims and `setup`.

#### Pitfalls to avoid deliberately
1. One ritual for every size (the "sledgehammer"); keep the heavy path opt-in and artifact-free at T0/T1. [strong]
2. Work orders that carry code or grow with every review finding; add a proportion check, and consider a guard that stops the lead from editing product code while an order is being drafted, since Opus 5.5 is documented as prone to implementing during planning (Superpowers 6.4.2) [moderate for the failure, weak for the guard].
3. Advisory-only enforcement of anything that must always hold (git writes, dependency changes, protected files, done-ness); use hooks, and keep prose for judgement. [strong]
4. Hooks that fail open: plain non-zero exits, short timeouts, error swallowing, probes that return "safe" on timeout, and gates that pass when they examined nothing. [strong]
5. Letting the implementer, or a reviewer reading the implementer's summary, establish completion; require evidence the implementer cannot edit. [strong]
6. Review loops without a budget or stop rule, finding quotas, and reviewers that chase every finding; also reviewing artefacts that do not exist (check preconditions first). [strong]
7. Always-loaded rules and skills that grow without audit; self-generated rule dumps; ADR or repository overviews in rules. [strong]
8. Parallel implementers or shared mutable state files without isolation; if wm ever parallelises, isolate by worktree and enforce it in a PreToolUse hook rather than prompt text (GSD incident #3045). [strong]
9. Blanket TDD micro-cycle mandates [moderate]: the best-supported variant is lead-authored acceptance tests plus a verified red state for new behaviour, not a ritual for every edit (Böckeler: at least 3x tokens, no measured gain; GSD and cc-sdd show how to check red mechanically when it matters).
10. Treating persona names or roles as the architecture (BMAD complaints); route by capability and model.
11. Silent improvisation versus block fatigue: wm's BLOCKED-instead-of-improvising rule is a deliberate difference from Superpowers' "Rulings, not stalls"; it needs typed reasons, a cheap lead response path and perhaps a logged "conservative deviation" class for purely mechanical choices, otherwise the lead becomes the bottleneck (BMAD "human router" complaint; Anthropic's Fable guidance on logging deviations, reported) [weak].
12. Breaking changes without shims, `update` commands or migration notes; plugin names or commands that collide with other plugins; telemetry on by default. [moderate]

### Gaps
- None of these mechanisms has been measured in isolation in the sources found; ranking rests on convergence of incident reports and small studies, not on effect sizes.
- Whether SubagentStop shares the 8-continuation cap, whether path-scoped rules load when a file is created rather than opened, and how Claude Code's guards behave for nested subagents are untested here.
- No evidence yet on an Opus-lead / Sonnet-implementer split with precise work orders compared with Opus alone; the recommendation to measure it (item 12) is meant to close that gap.
